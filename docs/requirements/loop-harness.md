# Loop Harness（反復ループ基盤）要件定義

**作成日**: 2026-07-06
**ステータス**: active
**起点**: Impact Analysis `.claude/docs/impact-analysis/2026-07-06_loop-harness.md`
**関連**: `design:loop-harness`（未作成。本要件を受けて `docs/design/loop-harness.md` を作成予定）

## 1. 背景

2026 年 6 月、「ループエンジニアリング（loop engineering）」という概念が定着した。
Peter Steinberger は「エージェントに投げるプロンプトではなく、エージェントを駆動するループを
設計すべきだ（You should be designing loops that prompt your agents）」と述べ、Anthropic の
Boris Cherny は「自分の仕事はループを書くことだ（My job is to write loops）」と表現した。
Addy Osmani はブログ記事 "Loop Engineering" でこれを Trigger（起動条件）→ Maker（生成）→
Checker（検証）→ 停止判定という反復構造として体系化している。

AI Orchestra は harness engineering（hooks / rules / agent-routing / quality-gates）の部品は
既に揃っているが、これらを束ねて「Trigger → Maker → Checker → 停止判定」の反復ループ本体として
動かす基盤が存在しない。既存資産の中にもループ的な要素は点在する。

- `/review` スキルの Phase 5-7（Pass/Fail 判定 → Auto-Fix → Re-Review）はプロンプト駆動の
  `while` ループであり、LLM が指示書に従って自分でループを繰り返す。停止条件は `max_loops` の
  みで、反復回数・停止判定が決定論的に保証されない。
- `skill-evolution` の `evaluate_stop()` は 4 種のガード（反復上限 / コスト / 過学習 / 発散）を
  持つ決定論的な停止判定だが、`holdout_score` 等スキル改善固有の連続値メトリクスを前提にしており、
  テスト合否のような離散的な Checker 結果にはそのまま使えない。
- fail-logs（失敗蓄積）は失敗の記録に留まり、記録を踏まえて次の反復を駆動する仕組みまでは
  持たない。

これらの部品を土台に、汎用の反復ループ実行基盤として `loop-harness`（仮称）を新設する。
なお LP-2（自律型）は当面ローカルマシン常駐での運用を前提とし、CI（GitHub Actions 等）上での
実行は本要件のスコープに含めない（詳細は 3.2 節）。

## 2. 課題

| #   | 課題                                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------------------------- |
| P-1 | タスクの反復（実装→検証→修正）が人手駆動で、人間がプロンプトを再投入し続ける必要がある                                      |
| P-2 | 既存の `/review` ループはプロンプト駆動（LLM 自己反復）で、反復回数・停止判定が決定論的に保証されない                       |
| P-3 | 停止判定資産（`evaluate_stop()`）は skill-evolution 固有メトリクス前提で、テスト合否のような離散的な Checker 結果に使えない |
| P-4 | Maker（生成）と Checker（検証）が分離されておらず、自己評価バイアス（Nodding Loop）への構造的防御がない                     |
| P-5 | ループの反復履歴・停止理由が構造化記録されず、失敗したループの引き継ぎ・再開ができない                                      |

## 3. スコープ

### 3.1 In Scope

- 汎用ループ実行基盤（ループ定義を宣言的に追加可能。コア改修なしで 2 本目のループを追加できる）
- ファーストユースケース: Issue 消化ループ（Issue 1 件 → worktree 隔離で実装 → 検証 → 修正反復 →
  合格で PR 作成 → PR 上の外部レビュー対応 → 新規指摘解消で完了）
- LP-1: セッション内伴走型ループ（スキル起動、決定論的 Python 制御）
- LP-2: headless 自律型ループ（トリガー検知 → `claude -p` 起動）。ローカルマシン常駐で運用し、
  cron / launchd がトリガーを検知して起動する。認証は既存の Claude Code ログイン認証をそのまま
  利用し、追加のキー管理は行わない。※本要件では詳細設計まで行う
- 並列実行（同時複数 Issue ループ、worktree 隔離、state の排他制御）
- 専用 state/journal（正本）+ audit への `loop_*` イベント相乗り

### 3.2 Out of Scope

| 項目                                             | 理由                                                                                            |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Issue #139（skill-evolution オフライン層）の統合 | 目的が異なる（スキル定義の最適化 vs 開発タスクの消化）。将来の載せ替え候補として ADR に記録     |
| PR の auto-merge                                 | ユーザーの手動マージポリシー（PR レビュー対応反復が完了しても、最終的なマージ判断は人間が行う） |
| core の `log_common`（events.jsonl）への配線     | 既存 2 系統併存（`log_common` / `audit.event_logger`）を悪化させる未使用系統を増やさない        |
| スキル・エージェント定義の自動改善               | skill-evolution の責務                                                                          |
| CI（GitHub Actions 等）上での LP-2 実行          | 将来検討。本要件はローカルマシン常駐（cron / launchd）での運用のみを対象とする                  |
| Codex 以外の外部レビュー指摘への固有対応         | 将来検討。CodeRabbit はレート制限応答の検知と人間引き継ぎだけを FT-13 の対象とし、指摘形式固有の解析・対応は対象外とする |

### 3.3 既存スキルとの関係

既存の `issue-fix` スキルは変更せず現状のまま残す。Issue 消化ループは新スキル `/loop-issue` として
実装し、`issue-fix` の Issue 取得・ブランチ判定ロジックと `pr-create` 資産を再利用する。実装〜検証
〜修正の反復部分のみを `loop-harness` が新たに担う（単発の手動 Issue 対応フローと反復ループフロー
は共存する）。

## 5. 非機能要件

| ID    | 要件                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NF-01 | 既存 CLI コマンド・設定キーの後方互換を壊さない（audit `EVENT_TYPES` 追加は additive のみ）                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| NF-02 | 反復にはコスト・回数の上限が必ず存在し、無限ループ・トークン暴走に陥らない（LP-2 では壁時計時間上限も必須）                                                                                                                                                                                                                                                                                                                                                                                                                               |
| NF-03 | Maker と Checker（LLM レビュー）は別サブエージェント・別コンテキストで実行し、Maker の自己申告を合否判定に用いない。機械検証と Checker の LLM レビュー結果（Critical=0 かつ High=0）の両方を合否の必須条件とし、Maker の自己申告のみでは合格としない。Maker と Checker の LLM レビューが agent-routing の解決次第で同一基盤モデルに解決される場合の評価バイアスは残存しうるが、合否の最終根拠を機械検証と Checker の LLM レビュー結果の両方に置くことで受容する。ループ定義で Checker に Maker と異なるツール解決を指定することを推奨する |
| NF-04 | ループが push・PR 作成する際、秘匿情報をコミット・PR 本文・ログに含めない（既存 secret scan 資産との整合）                                                                                                                                                                                                                                                                                                                                                                                                                                |
| NF-05 | Maker/Checker の生出力はメインオーケストレーターのコンテキストへ返さず、要約と state/journal 参照で受け渡す                                                                                                                                                                                                                                                                                                                                                                                                                               |
| NF-06 | `codex exec` は hooks 非発火（`docs/design/codex-cli-harness.md`）のため、Codex を Maker にする場合も制御はループ側の決定論的検証で成立させる（hooks に依存しない）                                                                                                                                                                                                                                                                                                                                                                       |
| NF-07 | 再利用対象（`issue-fix` の Issue 取得・ブランチ判定、`pr-create`、`failure_detector`、`evaluate_stop` のガード構造）を最大限再利用し、これらと機能重複する新規実装を作らない                                                                                                                                                                                                                                                                                                                                                              |

## 6. 用語

| 用語                          | 説明                                                                                                                                                                                                                    |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ループエンジニアリング        | Trigger → Maker → Checker → 停止判定の反復構造としてエージェント駆動を設計する考え方                                                                                                                                    |
| ループ定義（Loop Definition） | trigger / maker / checker / 停止条件 / 成功出口 / 失敗出口を宣言的に記述した定義                                                                                                                                        |
| ループラン（Loop Run）        | 1 つのループ定義に基づく 1 回分の実行（1 Issue に対する実装反復と、成功出口後の PR レビュー対応反復を合わせた一連の処理すべてを指す単位）                                                                               |
| 反復（Iteration）             | ループラン内の 1 周（Maker 実行 → Checker 実行 → 停止判定の 1 サイクル）                                                                                                                                                |
| Trigger                       | ループ起動の契機（スキル手動起動、cron、ラベル付き Issue キュー等）                                                                                                                                                     |
| Maker                         | 実装・修正を生成するエージェント/プロセス。agent-routing の解決に従って選定される                                                                                                                                       |
| Checker                       | Maker の成果物を検証するエージェント/プロセス（機械的検証 + 任意で LLM レビュー。ただし Issue 消化ループでは LLM レビュー層も必須。合格基準は選定された全レビュアーの Critical=0 かつ High=0。FT-06 参照）              |
| CheckResult                   | Checker が返す検証結果（合否、失敗シグネチャ、詳細）                                                                                                                                                                    |
| PR レビュー対応反復           | 成功出口での PR 作成後、PR 上の外部自動レビューの指摘に対応するための反復。実装反復とは別のカウンタ・別のガード（反復上限・無進捗検知）を持つ。新規指摘が 0 になった時点で完了し、以降のマージ判断のみ人間に委ねる      |
| 失敗シグネチャ                | 失敗の同一性判定に使う正規化キー。`failure_detector.analyze()` の failure_type + error_type の 6 分類に加え、失敗テスト識別子（失敗テスト名の集合等）を含める。比較キーの詳細仕様は設計フェーズで確定する（申し送り）   |
| 無進捗（No-Progress）         | (a) 実装反復: 同一の失敗シグネチャが連続して発生し、反復を続けても改善が見込めない状態。(b) PR レビュー対応反復: 同一指摘（正規化した指摘シグネチャ）が再提起され続ける、または新規指摘件数が前回反復から減少しない状態 |
| ガード                        | 無限反復・暴走を防ぐための停止条件（反復上限、無進捗検知等）。評価順序は合格判定 → 無進捗判定 → 反復上限判定                                                                                                            |
| 成功出口・失敗出口            | 停止判定が合格/不合格いずれに至った場合の後続処理（成功出口: PR 作成、失敗出口: Draft PR）                                                                                                                              |
| LP-1（伴走型）                | セッション内でスキルとして起動し、決定論的な Python 制御でループを回す実行形態                                                                                                                                          |
| LP-2（自律型）                | ローカルマシン常駐で cron / launchd がトリガーを検知し、headless（`claude -p`）で自律的にループを起動する実行形態。認証は既存の Claude Code ログイン認証を利用する                                                      |
| Memory Spine（state/journal） | ループ ID 単位で反復履歴・停止理由を永続化する専用ファイル群（正本）。再開可能な形式で保持する                                                                                                                          |
| Nodding Loop                  | Maker と Checker（または LLM 同士）が互いに頷き合い、欠陥を見逃す自己評価バイアス                                                                                                                                       |

## 7. 受け入れ基準

- `/loop-issue <N>`（FT-02）を実行すると worktree が作成され、反復上限内でテスト合格すると PR が作成される（FT-02, FT-03, FT-05, FT-12）。
- 同一セッションで複数の `/loop-issue` を並列実行しても、worktree・state ファイルが競合しない（FT-03）。
- Issue 消化ループの `auto` Maker は `cli-tools.yaml` の `agents.<name>.tool` 解決結果に従い、
  `maker.allowed_agents` で編集不能ロールを除外する。初回選定結果は state に固定し、設定・ラベルの変化で
  反復間に揺れない。その他のループではフェーズ固有の `maker.agent` を維持する（FT-04）。
- Checker の機械的検証（テスト + lint）は `failure_detector.analyze()` の結果に基づいて合否判定される（FT-05）。
- Issue 消化ループの Checker は `code-reviewer` をベースラインとし、認証関連ファイル（`auth`/`token`/`secret` 等）を変更するループでは `security-reviewer` が追加選定されるなど、`skill-review-policy` のレビュアー選定ガイドに準拠して専門レビュアーが追加される（FT-06）。
- Issue 消化ループでは、選定された全レビュアーの Critical=0 かつ High=0 でなければ合格としない（機械検証との両層必須、いずれか一方の省略や High 指摘の残存では合格判定されない）（FT-06）。
- この Critical=0 かつ High=0 の合格基準は LP-1（セッション内伴走型）で実行した場合にも同様に適用され、人間による「High の理由付き受容」での合格判定は行われない（FT-06）。
- 同一 Issue に対して手動と cron から同時にループが起動されようとした場合、2 件目はロック取得に失敗し起動できない（TTL 経過後は再取得可能）（FT-07）。
- 反復が不合格の場合、合格判定 → 無進捗判定 → 反復上限判定の順でガード評価され、無進捗による停止が反復上限到達より先に成立し得る（FT-08）。
- 同一失敗シグネチャ（failure_type + error_type + 失敗テスト識別子の正規化キー）が 2 回連続すると、反復上限未到達でも無進捗停止として失敗出口に至る（FT-09）。
- `.claude/config/loop-harness/loop-harness.local.yaml` でガード既定値（`max_iterations` 等）や LP-2 同時実行数上限を上書きできる（FT-09, FT-18）。
- ループ実行中、ループ ID 単位の state/journal ファイルに反復回数・Checker 結果・停止理由が記録され、セッション中断後も参照でき、当該ファイルから再開できる（FT-10, FT-22）。
- ループ実行によって audit のセッションログに `loop_start` / `loop_iteration` / `loop_stop` イベントが記録され、既存 `EVENT_TYPES` の他の値には影響しない（FT-11）。
- 成功出口では commit → push → PR 作成が行われ、auto-merge は付与されず、worktree は保持される（FT-12, FT-23）。
- PR 作成後、外部自動レビューが未実行・実行中の間はループが待機し、レビュー提出イベントや check-run 完了等の明示的な完了シグナルを検知して初めて「完了かつ指摘ゼロ」または指摘取得へ進む（コメントの有無だけでは完了と判定しない）。通常の timeout は無進捗としてガードに乗る。信頼済み CodeRabbit のレート制限応答を検知した場合、Codex 等の代替経路があれば timeout まで正常完了を優先して待ち、正常シグナルが来なければ無進捗へ加算せず人間の確認・マージ判断へ引き継ぐ（FT-13）。
- 取得した外部レビュー指摘に対してループが修正・再プッシュを行う「PR レビュー対応反復」が回り、Critical/High 相当の指摘は理由記録による見送りができず対応が必須となる。Medium/Low 相当の指摘のみ、対応しない場合に理由が記録され見送られる。新規指摘が 0 になった時点で PR 対応完了として報告され、以降のマージ判断のみが人間に委ねられる（auto-merge は行われない）（FT-14）。
- PR レビュー対応反復は実装反復とは別カウンタ・別上限のガード（反復上限・無進捗判定〔同一指摘の再提起、または新規指摘件数が前回反復から減少しない場合〕）を持つ。ガードで打ち切られた場合は PR が Draft に変換され、未解消指摘の一覧と反復履歴が PR コメントに残り、対象 Issue への結果コメントとローカル通知（FT-19）が発火する（FT-15）。
- `max_iterations`（既定 3）に到達すると Draft PR が作成され、各反復の Checker 結果を含む反復履歴が残る（FT-09, FT-10, FT-16）。
- 2 本目のループ定義を宣言的な定義ファイルの追加のみで登録でき、`loop-harness` のコア実装に変更を加える必要がない（FT-01）。
- LP-2 のトリガー（cron またはラベル付き Issue キュー）を検知すると、ローカルマシン常駐の cron / launchd から headless（`claude -p`）でループが起動し、既存 Claude Code ログイン認証がそのまま使われる（追加のキー入力・API キー設定が不要）（FT-17）。
- LP-2 の同時実行ループ数が既定の上限に達すると、それ以上の新規ループは起動されない（FT-18）。
- LP-2 のループが停止・完了すると、対象 Issue へ結果コメント（成功可否・停止理由・反復サマリ）が投稿され、ローカルマシンに macOS 通知が届く（FT-19）。
- 状況確認コマンドで実行中/完了済みループの一覧を確認でき、完了済みループの state/journal を purge できる（FT-20）。
- LP-2 実行では壁時計時間上限に到達すると強制停止し、失敗出口相当の記録が残る（NF-02）。
- 既存のテストスイートがすべて通り、既存の `.claude/config/**` のキーに変更が生じていないことを確認できる（NF-01）。
- Checker の LLM レビューが Maker とは別のサブエージェントとして起動されたことを、audit の `loop_iteration` イベント（サブエージェント識別情報）から確認できる（NF-03）。
- Maker 自身の自己申告のみに基づく合格判定は行われず、機械検証結果と Checker の LLM レビュー結果（Critical=0 かつ High=0）の両方が揃って初めて合格と判定される（NF-03）。
- ループが作成したコミット・PR 本文が既存 secret scan 資産を通過する（機密情報が検出されない）（NF-04）。
- Codex を Maker にした場合でも、hooks が発火しない前提のもとでループ側の機械検証（Checker）のみで合否判定が完結する（NF-06）。

## セルフチェック

- **ID 一意性**: P-1〜P-5、FT-01〜FT-23、NF-01〜NF-07 はすべて一意かつ欠番なし。重複なしを確認済み。
- **must 網羅**: ユーザー確定要件の must 級 19 項目（FT-01〜FT-19）はすべて対応付けられ、脱落なし。should 級 4 項目は定義済み（うち FT-20, FT-22, FT-23 の 3 件は受け入れ基準でもカバー。FT-21 は対象外）。
- **受け入れ基準の検証可能性**: 各基準は「操作 → 観測可能な結果」の形式で記述し、実装後にテスト・目視確認いずれかで検証できる粒度に揃えた。FT-01〜FT-19（must 全件）に加え、ユーザー決定済みの should 項目（FT-20, FT-22, FT-23）も受け入れ基準でカバーしている。
- **NF の受け入れ基準カバレッジ**: NF-01（既存テスト・既存 config キー無変更）、NF-02（壁時計時間上限での強制停止）、NF-03（Maker/Checker 別サブエージェントを audit イベントで確認）、NF-04（secret scan 通過）、NF-06（Codex Maker 時もループ側機械検証で合否完結）の 5 件を受け入れ基準に追加済み。NF-05・NF-07 は実装・設計判断（出力受け渡し方式、既存資産再利用の徹底）であり、外部から直接観測可能な受け入れ基準化が難しいため、レビュー・設計突合で確認する運用とする。
