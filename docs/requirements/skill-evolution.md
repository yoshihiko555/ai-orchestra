# Skill Evolution（スキル改善候補の受け渡し）要件定義

**作成日**: 2026-07-01
**改訂日**: 2026-11-08（v2: 改善候補を集めて meta-harness に渡し、昇格後も追う役に絞る）
**ステータス**: draft
**起点**: Issue #5（v1）、2026-11-04〜11-08 の対話（v2）
**関連**: `design:skill-evolution`（`docs/design/skill-evolution.md`）、`req:meta-harness`、`req:fail-logs`

## 1. 背景

v1（ADR-20260701-028）は、スキル実行ごとに自己申告と機械計測を記録し、学び（lessons）を次の実行へ注入し、
オフライン層の反復ループでスキル自体を改善する設計だった。2026-11-04 時点の実データでは次のとおりで、
改善は回っていない。

- 記録は 3 か月で 77 実行。成功 69 件は自己申告で、`[critical]` の基準を持つスキルは無い。
  自己申告の 70 件中 65 件は `tool_uses: 0` で、機械が測っているのは所要時間だけ
- lessons は 2 ファイルで、中身は 7 月の状態行 1 つ。自己申告が欠けた失敗は lessons に書かれず、
  lessons は worktree ローカルなので worktree と一緒に消える。起動の閾値（20 件）には届かない
- オフライン層は未実装（Issue #139）。一方、改善案の生成・holdout 付きの比較・人の PR による昇格は
  meta-harness（`target=skill:<slug>`）が既に持っている。ただし meta-harness は skill-evolution の記録を読まず、
  シナリオは手書きで、スキルの昇格がマージされた例はまだ無い（#374 は環境への過学習で閉じた）
- 自己申告の指示は、スキルを呼ぶたびにコンテキストへ注入されている

外部の自律改善の仕組み（Hermes Agent、hermes-agent-self-evolution、ACE、skill-creator の評価、Voyager、DGM 等。
`.claude/docs/research/autonomous-self-improvement.md`）と比べると、評価を通してから採用する後半は
meta-harness が既に持っている。足りないのは次の 2 つである。

- **前半**: 実運用で問題を見つけ、どのスキルの実行で起きたかを特定し、改善候補として溜め、シナリオにする
- **後**: 採用した改善が効いたかを確かめる

v2 では skill-evolution をこの前半と後の担当に絞り、改善そのもの（改善案の生成・評価・昇格 PR）は meta-harness に任せる。

## 2. 課題

| #   | 課題                                                                               |
| --- | ---------------------------------------------------------------------------------- |
| P-1 | 実運用で起きた失敗が、どのスキルの実行で起きたかが分からない                       |
| P-2 | 改善すべきこと（証拠と再発回数）を溜める場所が無い                                 |
| P-3 | 実運用の失敗が meta-harness のシナリオにならず、シナリオは実運用の証拠と切れている |
| P-4 | 昇格した改善が効いたかを確かめる手段が無い                                         |
| P-5 | v1 の自己申告は成功の根拠にならず、スキルを呼ぶたびにコンテキストを消費している    |

## 3. 用語

| 用語           | 意味                                                                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 実行範囲       | 1 回のスキル実行の始まり（Skill ツールの呼び出しか、利用者の `/<skill>` での直接起動）から観測の区切り（Stop / SubagentStop）までの区間と、その識別子 |
| 帰属           | 失敗などの証拠を、ある実行範囲（＝あるスキルのある実行）に結び付けること                                                                              |
| 証拠           | fail-logs・audit・`/review-respond` の記録のうち、改善の根拠になりうるもの。原データではなく参照で持つ                                                |
| 観測           | 帰属が確定した証拠 1 件の記録。まだ「直すべき点」と認められていない                                                                                   |
| 出来事         | 再発回数を数える単位。同じ証拠や同じ失敗の重複は 1 件と数える                                                                                         |
| 改善候補       | 人が「スキルに直すべき点がある」と認めた仮説と、それを支える観測・状態の組。単に「候補」とも書く                                                      |
| 同じ欠陥       | 候補と同じ原因でスキルが失敗したと人が確認した観測。照合は自動で提案してよいが、確定は人が行う                                                        |
| シナリオ下書き | 候補の証拠から、改善案を作る側とは別のセッションの LLM が書いた再現シナリオ（学習用と holdout）                                                       |
| 受け渡し       | 承認済みシナリオを meta-harness に渡し、評価・提案・昇格 PR・マージまでを候補に紐付けて記録すること                                                   |
| 該当する機会   | 昇格がマージされた後の版（スキルのハッシュが一致する版）で、そのスキルが実行された実行範囲                                                            |
| 再開           | 昇格した改善のマージ後、同じ欠陥がマージ後の版で確認されたときに候補を開き直すこと                                                                    |
| outcome        | 実行の結果。外部の確認がある場合だけ `success` / `failure`、それ以外は `unknown`                                                                      |
| proposer       | meta-harness の、改善案（オーバーレイ）を作るエージェント                                                                                             |
| facet スキル   | facet の composition（`facets/compositions/skills/<slug>.yaml`）から生成されるスキル。meta-harness に受け渡せるのはこれだけ                           |

## 4. スコープ

### 4.1 In Scope

- スキルの実行範囲の記録（Skill ツール経由と、利用者が `/<skill>` で直接起動したものの両方）
- 証拠の読み込みと帰属（人による確定を主、記録から一意に決まるものだけ自動）
- 改善候補の台帳（証拠への参照・再発回数・状態と遷移の履歴）
- シナリオの下書き（別セッションの LLM）と人による承認、承認した内容とスイートの結び付け
- meta-harness への受け渡しの記録（facet スキルに限る）
- 昇格のマージ後の再発の確認と再開
- 人が候補を確認するスキル（`/skill-candidates`、仮称）
- v1 の機能の廃止と、導入先の互換性を保った移行

### 4.2 Out of Scope

| 項目                                                           | 理由・担当                                                                                                               |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 失敗の収集                                                     | fail-logs の責務。skill-evolution は読むだけで、原データを複製しない                                                     |
| スキル横断の教訓と、その昇格                                   | fail-logs と `/lessons` の責務（ADR-20261103-063 は変えない。振り分けは §5.2）                                           |
| 改善案の生成・評価・昇格 PR の作成                             | meta-harness の責務（§5.1）                                                                                              |
| facet でないスキル（導入先独自・個人・plugin）の改善の受け渡し | meta-harness は facet の composition を持つスキルしか扱えない。観測と候補の記録までは行い、直すのは人が手で行う（FT-18） |
| スキルの直接編集、人の承認を経ない反映                         | 改善は必ず人の目を通す（2026-11-08 利用者の決定）                                                                        |
| 改善の率（成功率など）による測定とダッシュボード               | 実行数が少なく（3 か月で 77 回）、率は誤差に埋もれる                                                                     |
| 失敗の自動の分類（クラスタリング）                             | 件数が少ないうちは人の確認で足りる。後回し                                                                               |
| スキル以外の改善（ハーネス本体・ルーティング）                 | meta-harness の他のターゲット（`claude-harness` / `routing-config`）                                                     |
| 旧データ（v1 の lessons と metrics）の移行・取り込み           | 根拠にならないため使わない（2026-11-08 利用者の決定。FT-15）                                                             |
| meta-harness の評価用の自己申告の廃止                          | meta-harness が独自に持つ評価の仕組み（§5.1 D-04）で、実運用の自己申告とは別物                                           |

## 5. 機能要件（FT）

| FT-02 | 実行範囲に、hook の入力から取れる場合だけ、Skill 呼び出しの tool_use_id・エージェント ID・モデルを記録できる。取れない値は空とし、各値をどこから得たかを残す                                                                                                                                              | must   |
| FT-03 | 実行の outcome の既定は `unknown` とし、実運用の自己申告から成功を判定しない                                                                                                                                                                                                                              | must   |
| FT-04 | fail-logs の失敗記録と教訓候補（`/review-respond` が作ったものを含む）、audit のセッション記録を読み、証拠ごとに帰属先になりうる実行範囲（同じセッションで時刻が重なるもの）を示し、人が帰属を確定できる。実行範囲を特定できない証拠（PR のレビュー指摘など）は、人がスキルだけを指定して帰属を確定できる | must   |
| FT-05 | 記録から対応が一意に確かめられる証拠だけを、自動で実行範囲に帰属できる。自動で帰属させてよいのは、そのセッションのその時刻に開いている実行範囲が 1 つだけで、次のどれにも当たらない場合に限る                                                                                                             | should |
|       | 入れ子の実行範囲（スキルの中で別のスキルが動いた）、区切りより前の親の再開（A → B → A の続き）、スキルが起動したサブエージェント、Stop を何度もまたぐ長い実行、再開したセッション                                                                                                                         |        |
| FT-06 | 帰属が `unknown` の証拠は残し、再発回数に数えない。人が帰属を確定したら、その時点から観測として数える                                                                                                                                                                                                     | must   |
| FT-07 | 観測と候補を、証拠への参照・伏せ字済みの短い抜粋・出来事の件数とともに台帳に記録できる。同じ証拠は二重に数えない                                                                                                                                                                                          | must   |
| FT-08 | 候補の状態と遷移の履歴を記録できる。状態と遷移は次のとおり                                                                                                                                                                                                                                                | must   |
|       | 主経路: 観測 →（人が認める）候補 → シナリオ下書き → シナリオ承認 → 改善中 → 昇格 PR → 昇格済み                                                                                                                                                                                                            |        |
|       | 戻り: シナリオの差し戻し（シナリオ承認 → シナリオ下書き）、改善案が採用基準を満たさない（改善中 → 候補）、昇格 PR がマージされずに閉じられた（昇格 PR → 候補）                                                                                                                                            |        |
|       | 分岐: 却下（どの状態からも）、再開（昇格済み → 候補）、archive（FT-16）                                                                                                                                                                                                                                   |        |
| FT-09 | 同じ原因と自動で推定された観測（推定は提案で、確定は人が行う）が別々のセッションか PR で 2 件そろったら、候補にするかを利用者に知らせられる（観測 1 件でも、人は候補にできる）                                                                                                                            | should |
| FT-10 | 人が選んだ候補について、proposer とは別のセッションの LLM が、証拠から再現シナリオ（学習用と holdout を各 1 本以上）を下書きできる。下書きはスイートの外に置く                                                                                                                                            | must   |
| FT-11 | 人が承認したシナリオの内容（ハッシュ）を記録し、その内容だけをスイートに入れる。meta-harness で評価する前に、スイートの中身が承認したハッシュと一致することを確かめる。承認前・不一致のシナリオは評価に使われない                                                                                         | must   |
| FT-12 | 受け渡し（候補 → 承認したシナリオとスイートのハッシュ → meta-harness の評価の実行 ID と候補 ID → 昇格 PR → マージの SHA）を候補に紐付けて記録できる                                                                                                                                                       | must   |
| FT-13 | 昇格済みの候補について、人が同じ欠陥を確定したら候補を再開できる。確定が無いあいだは、該当する機会の回数と、該当する機会と同じセッションの帰属 `unknown` の証拠の件数を添えて「確認された再発なし」と示す                                                                                                 | must   |
| FT-14 | 昇格がマージされた後の版で起きた観測のうち、候補と同じ原因と推定されるものを、人に確認を促せる                                                                                                                                                                                                            | should |

| FT-19 | facet スキルの候補を、観測したプロジェクトから ai-orchestra リポジトリでの受け渡しまで運べる                                                                                                                                                                                                              | should |

### 5.1 依存する他パッケージの機能

v2 は次の meta-harness の機能に依存する。2026-11-08 時点のコードで確かめた。不足は meta-harness の要件の変更として扱う。

| ID   | 依存する機能                                                                                                                                                                                  |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-01 | スキルごとのシナリオ置き場（`target=skill:<slug>`。パッケージ内の YAML を探すだけ）と、学習用と holdout の区別（各 1 本以上が必要）                                                           |
| D-02 | baseline の評価、評価の実行 ID（`--focus-run`）を指定した改善案の生成、昇格 PR の作成とマージの確認                                                                                           |
| D-03 | proposer の読み取り制限: proposer は用意された読み取り範囲だけを読める。シナリオのファイルと holdout の実行記録は読めない。学習用の実行記録（プロンプトと採点の説明を含む）は設計どおり読める |
| D-04 | 評価用の自己申告（meta-harness が独自に配布・解析する。v2 の FT-03・FT-21 の影響を受けない）                                                                                                  |
| D-05 | ターゲットにできるのは facet の composition（`facets/compositions/skills/<slug>.yaml`）を持つスキルだけ                                                                                       |

- meta-harness は、スイートの中身が人の承認したものかを確かめない（承認の来歴を持たない）。FT-11 の一致の確認は skill-evolution 側で行う
- meta-harness の `evaluate --json` は、評価の ID・スイートのハッシュ・評価の仕組みのハッシュを出さない（meta-harness の台帳にだけある）。FT-11・FT-12 のため、これらを出力に足す（meta-harness の変更）
- meta-harness は昇格 PR を origin/main から作り、昇格の時点で、評価したときとスイートのハッシュが同じかを確かめる。そのため承認したシナリオは、評価の前に PR で main に入れる。スイートのハッシュはシナリオ置き場の全ファイルから作られるので、承認はシナリオを入れた後のスイート全体の状態に対して記録する
- meta-harness の要件のうち、オフライン層からの委譲を前提にした記述（§3.1 の「skill-evolution オフライン層（未実装）への委譲による責務統合」と FT-09）は、
  「skill-evolution の承認済みシナリオと受け渡しの記録を受け付ける」趣旨に改める

### 5.2 fail-logs との振り分け

同じ失敗が fail-logs の教訓候補（`/lessons`）と skill-evolution の観測（`/skill-candidates`）の両方に現れることはある。どちらで扱うかは人が決める。

- 原因が特定のスキルの手順・指示にあり、スキルを直せば防げる → `/skill-candidates`（スキルの改善）
- 原因がスキルに依らない落とし穴・規約 → `/lessons`（AGENTS.md・rule・ガードへの昇格）
- skill-evolution は fail-logs の教訓候補を作らず、状態も変えない。それぞれの台帳の中で、同じ証拠を二重に数えない
- `/review-respond` の指摘のうち fail-logs に入らないもの（一般化しない指摘）は、v2 の証拠に含めない

## 6. 非機能要件

| ID    | 要件                                                                                                                                                                                                 | 計測基準                                                                                                                                                                             |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| NF-01 | スキルを呼ぶたびのコンテキストの注入を無くす                                                                                                                                                         | v2 のスキル起動の hook が返す追加コンテキストが 0 文字                                                                                                                               |
| NF-02 | hook は記録だけを行い、失敗しても Claude Code を止めない                                                                                                                                             | 例外・不正な入力・書き込み失敗のとき、終了コード 0 で出力なし                                                                                                                        |
| NF-03 | 改善の反映には 2 回の人の承認（シナリオの承認、昇格 PR のマージ）を必須とする                                                                                                                        | 承認の記録が無い候補は「シナリオ承認」に、マージの確認が無い候補は「昇格済み」に遷移できない                                                                                         |
| NF-04 | holdout のシナリオと採点基準は proposer から守る。学習用のシナリオのプロンプトと採点の説明は、meta-harness の設計どおり proposer に見えてよい                                                        | proposer の読み取り範囲に、シナリオのファイル・holdout の実行記録・holdout の採点基準の文面が含まれない                                                                              |
| NF-05 | 台帳に入れる抜粋は fail-logs と同等以上の伏せ字を通し、原データを複製しない                                                                                                                          | 抜粋は伏せ字の処理を通った文字列だけで、1 件あたりの上限文字数を超えない                                                                                                             |
| NF-06 | 帰属を誤るより `unknown` を選ぶ（安全側）                                                                                                                                                            | FT-05 の条件に当たらない証拠は、自動では帰属させない                                                                                                                                 |
| NF-07 | 導入先の互換性: 設定キーと `*.local.yaml` の上書き、hook の登録、`orchex sync` / `orchex uninstall` を非推奨期間中に壊さない                                                                         | 非推奨期間中に v1 の設定を置いたままでも sync と uninstall が成功する（期間の長さは設計で決める）                                                                                    |
| NF-08 | 台帳と受け渡しの記録は、worktree を消しても残る                                                                                                                                                      | root worktree に集約して保存し、worktree を削除しても失われない                                                                                                                      |
| NF-09 | 証拠から作るシナリオ下書きと、その固定データにも伏せ字を通し、下書きには上限（本数・大きさ・費用）を持つ。承認したシナリオは公開リポジトリに入るので、実データの写しではなく再現用に作ったものにする | 人の承認に出す前の下書きが伏せ字の処理を通っており、上限を超える下書きは作られない。承認の確認項目に「公開してよい内容か」と「実行される行（準備のコマンド・検査のコマンド）」がある |

**受け入れるリスク**:

- 台帳と受け渡しの記録は git 管理外のマシンローカルに置くため、マシンの故障やディレクトリの削除で失われる（fail-logs の教訓候補の台帳と同じ扱い）。承認済みシナリオは git で管理するので失われない
- 帰属 `unknown` の証拠は、人が確定するまで再発回数に数えないので、確定を待つあいだは見逃しがありうる
- 学習用のシナリオの採点の説明は proposer に見えるので、改善案が学習用のシナリオに合わせ込まれることはありうる。holdout で採否を決めることで抑える

## 7. 受け入れ基準

- Skill ツール経由でも `/<skill>` の直接起動でも、実行範囲の記録に FT-01 の値が入り、追加コンテキストは注入されない（FT-01、NF-01）
- hook の入力に無い tool_use_id・エージェント ID・モデルは空で記録され、取れた値にはどこから得たかが残る（FT-02）
- 自己申告の有無で outcome が変わらず、外部の確認が無い実行は `unknown` で記録される（FT-03）
- fail-logs の失敗 1 件について、同じセッションで時刻が重なる実行範囲が帰属先として示され、人が確定すると観測になる（FT-04、FT-06）
- 開いている実行範囲が 1 つだけで FT-05 の除外に当たらない失敗は自動で帰属し、入れ子・親の再開・サブエージェント・長い実行・再開したセッションに当たる失敗は帰属 `unknown` になって再発回数に入らない（FT-05、FT-06、NF-06）
- 同じ失敗を 2 回読み込んでも、出来事の件数は 1 のまま（FT-07）
- FT-08 の主経路・戻り・分岐の各遷移ができ、表にない遷移は拒否される（FT-08）
- 人が選んだ候補から、学習用と holdout を各 1 本以上含むシナリオ下書きがスイートの外に作られ、下書きを書いたセッションは proposer と別のセッションである（FT-10）
- 承認したハッシュと一致しないシナリオがスイートにあると、評価の前に止まる。人の承認の記録が無い候補は「シナリオ承認」に遷移できない（FT-11、NF-03）
- 1 つの候補について、承認したシナリオとスイートのハッシュ、meta-harness の評価の実行 ID と候補 ID、昇格 PR、マージの SHA を、候補から辿れる（FT-12）
- 昇格済みの候補で人が同じ欠陥を確定すると候補が「再開」になり、確定が無いときは該当する機会の回数と帰属 `unknown` の件数つきで「確認された再発なし」と示される（FT-13）
- `/skill-candidates` から、FT-15 の各操作ができる（FT-15）
- facet の composition を持たないスキルの候補は「受け渡しの対象外」と示され、シナリオ下書きに進めない（FT-18）
- 壊れた入力や書き込みできない保存先を与えても、hook は終了コード 0 で出力なしに終わる（NF-02）
- meta-harness が proposer に渡す読み取り範囲に、シナリオのファイル・holdout の実行記録・holdout の採点基準の文面が含まれない（NF-04）
- 台帳の抜粋とシナリオ下書きは伏せ字の処理を通り、上限を超えない（NF-05、NF-09）
- v2 の hook は lessons を読みも書きもせず、`check-trigger` は lessons の件数でオフライン層の起動を勧めない（FT-21）
- v1 の設定ファイルを置いたままの導入先で、`orchex sync` と `orchex uninstall skill-evolution` が成功し、hook は旧データを削除しない（FT-22、NF-07）
- worktree で作業して worktree を削除しても、候補と受け渡しの記録が残る（NF-08）
