# fail-logs（失敗からの学習ループ）要件定義

**作成日**: 2026-11-03
**ステータス**: draft
**起点**: Issue #82（失敗ログから教訓を昇格するフロー）、Notion タスク「失敗やレビュー指摘を自動抽出して、何度も指摘されている内容はルール化する」
**関連**: Issue #84（ユーザーによる修正・差し戻しの検知。FT-07 が包含する）、Issue #332（作業直前の標的型注入。FT-16）、ADR-20260612-025（fail-logs 新設）、ADR-20260630-027（再発失敗サマリーの注入）、ADR-20260927-057（memory-layers）
**影響範囲分析**: `.claude/docs/impact-analysis/2026-11-03_failure-lessons.md`

## 1. 背景

fail-logs は「失敗を記録し、次の作業に活かす」学習ループの入口として導入した。現状は次の 2 段までしかない。

- 記録: テスト・lint の失敗を出力パターンで検知し、`failures.jsonl` に追記する
- 活用: 直近の再発失敗を SessionStart で注入する

2026-11-03 時点の実データと既存の教訓から、次の問題が分かっている。

- **記録の取りこぼし**: 蓄積 433 件はすべてテスト・lint の出力パターン検知で、コマンドの非ゼロ終了・ツールエラー・外部 CLI の失敗は 0 件。ツール呼び出しの失敗が記録経路に届いていない
- **回数と教訓は別物**: 記録の大半は作業中のテスト失敗（TDD の red 等）で、再発回数が多くても教訓があるとは限らない
- **価値の高い合図が拾えていない**: auto-memory に残っている教訓 27 件の出どころは、ユーザーの訂正 8・その場のツールエラー 7・エラーの出ない副作用や後から判明した誤り 8・CI とレビュー 3・実験 1。fail-logs から生まれた教訓は 0 件
- **教訓化と昇格が手作業**: 教訓は Claude Code が auto-memory に書くか、人が「ルールに書いて」と頼んだときだけ残る。auto-memory は Claude Code 専用で、Codex / Antigravity には届かない。AGENTS.md への昇格は、依頼されたときの手動の棚卸しに限られている（ADR-20260927-057）

## 2. 目的

人が「この失敗をルールにして」と言わなくても、失敗から教訓候補が溜まり、繰り返し現れる候補が昇格候補として示され、人が承認するだけで、教訓が効くべき CLI に届くルールやガードに反映できる状態にする。

## 3. 対象と前提

- **利用者**: orchex を導入して Claude Code で開発する開発者（このリポジトリの開発を含む）
- **プラットフォーム**: Claude Code の hook とスキル。記録と教訓化の対象は Claude Code のセッション。Codex に委譲した作業は、Claude Code のセッションに返ってきた結果（コマンドの失敗、利用者の訂正など）の範囲で対象になる
- **前提**: fail-logs パッケージを拡張する（新パッケージは作らない）。fail-logs は「失敗を貯め、そこから昇格させる」ためのパッケージと位置づける

## 4. 用語

| 用語             | 定義                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 失敗             | 意図と結果がずれ、手戻り・損失・ユーザーの介入が起きたもの（§5）                                                                                     |
| 合図             | 失敗が起きたことを示すもの。機械・即時 / 機械・遅れて / 人間の介入 / エージェントが気づいたずれ の 4 種                                              |
| 失敗イベント     | hook が記録する機械的な合図 1 件。`failures.jsonl` の 1 行。人間の介入とずれは失敗イベントにならず、セッションの記録から読み取る                     |
| セッションの記録 | 1 セッションの会話・ツール呼び出し・結果の全記録（Claude Code の transcript）                                                                        |
| 前段判定         | 教訓化の前に、LLM を使わずに、失敗イベントとセッションの記録から合図の有無を判定する処理                                                             |
| 教訓化           | 失敗と、その後どう直したかの組から、教訓候補を作ること                                                                                               |
| 教訓化セッション | 教訓化のために裏で行う LLM の呼び出し。利用者のセッションとは別で、道具（シェル・ファイル・ネットワーク）を持たない                                  |
| 教訓候補         | 事象・原因・回避策・根拠・再発回数・対象範囲・状態をひとまとまりにしたもの                                                                           |
| 根拠             | 教訓候補のもとになったセッション・失敗イベント・PR と指摘への参照                                                                                    |
| 重大度           | 教訓候補のもとになった失敗の影響の大きさ。データの消失・取り消せない操作・機密情報の漏えいを「重大」とし、それ以外を「通常」とする。教訓化で判断する |
| 再発回数         | 同じ教訓の根拠になった、異なるセッションまたは異なる PR の数。同じセッション・同じ PR の中で何度起きても 1 と数える                                  |
| 対象範囲         | 教訓が効く CLI の範囲。Claude Code 固有か、全 CLI 共通か。教訓化で提案し、昇格の際に人が確定する                                                     |
| 候補の状態       | 候補 / 昇格中（昇格先に書き込んだが、統合ブランチへの反映を確認していない）/ 昇格済み / 却下                                                         |
| 候補の置き場     | 教訓候補を保存するローカルの場所。git で追跡せず、root worktree に集約する                                                                           |
| 提示             | 昇格の基準を超えた教訓候補を、人に知らせること                                                                                                       |
| 昇格             | 人が承認した教訓候補を、昇格先に書き込むこと                                                                                                         |
| 昇格先           | AGENTS.md の記述欄 / プロジェクト独自の `.claude/rules` / ガード（テスト・hook・lint。Issue を作るところまで）                                       |

## 5. 失敗の定義

**失敗 = 意図と結果がずれ、手戻り・損失・ユーザーの介入が起きたもの。**

| 合図                       | 例                                                                        | 入口                                                   |
| -------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------ |
| 機械・即時                 | コマンドの非ゼロ終了、ツールエラー、auto mode の拒否、テスト・lint の失敗 | 失敗イベント（hook）                                   |
| 機械・遅れて               | CI の失敗、bot や `/review` の指摘、revert、同じ箇所の直し直し            | PR 単位の区切り（`/review-respond` など）              |
| 人間の介入                 | 訂正・差し戻し、ツール呼び出しの手動の拒否、中断                          | セッションの記録（前段判定で兆候を拾い、教訓化で読む） |
| エージェントが気づいたずれ | エラーの出ない副作用、誤った結論に後から気づいたもの                      | セッションの記録（教訓化で読む）                       |

ツール呼び出しの手動の拒否は hook に届かない。中断は hook に届く場合があるが、届かない場合もあるため、どちらも失敗イベントとしては記録せず、セッションの記録から拾う。

教訓候補にしないもの:

- **意図した失敗**: TDD の red、存在確認・検索の不一致・差分の有無の確認のための非ゼロ終了など、失敗を想定して実行したもの
- **一過性の失敗**: ネットワークの瞬断、rate limit など、同じ操作をやり直せば成功し回避策のないもの

失敗イベントとして記録すること自体は妨げない（記録と教訓化は別の段で判断する）。

## 6. スコープ

### 6.1 In Scope

- 合図の収集の拡張（FT-04・FT-05）
- セッション終了時の教訓化（FT-06〜FT-08）と、レビュー指摘の教訓化（FT-09）
- 教訓候補の蓄積・合流（FT-11・FT-12）
- 提示と、人の承認による昇格・却下（FT-13〜FT-15）
- memory-layers ルールの改訂と ADR（FT-18）
- Could の FT-10・FT-16・FT-17 は、Must / Should の完了後に扱う

### 6.2 Out of Scope

| 項目                                   | 理由                                                                    |
| -------------------------------------- | ----------------------------------------------------------------------- |
| Codex 直接実行・TAKT の失敗の収集      | 対象はまず Claude Code（2026-11-03 決定）。Codex 側は hook が発火しない |
| 人の承認なしの昇格（無人での書き込み） | 昇格先は全セッションに効くため、承認と書き込みは人が行う                |
| auto-memory の自動書き換え             | ADR-20260927-057 決定 5（配布する hook でメモリを書き換えない）を維持   |
| skill-evolution の lessons への昇格    | 昇格先に含めない（2026-11-03 決定）                                     |
| orchex が管理する部分への書き込み      | AGENTS.md の管理ブロックと配布される rule は生成物のため                |
| claude-mem の設定                      | orchex の管理外                                                         |

### 6.3 将来検討

- fail-logs を `essential` プリセットに含めるか（現状は `all` のみ。昇格スキルも `essential` の利用者には届かない）
- Codex 直接実行・TAKT の失敗の収集
- 候補の置き場を git で共有するか
- 異常終了でセッション終了時の hook が動かなかったセッションの回収
- 候補の置き場の肥大化への対処（古い候補の期限切れ・件数の上限）

## 8. 機能要件（FR）

受け入れ条件のうち、LLM の判断に依存するものは「判定」と付け、§9.1 の方針で確かめる。それ以外は自動テストで確かめる。

### FR-04: ツール呼び出しの失敗の記録

- **対応機能**: FT-04
- **優先度**: Must
- **概要**: 実行したコマンドが非ゼロで終了したとき、またはツールがエラーを返したときに、失敗イベントを記録する
- **ユースケース**:
  1. エージェントがコマンドを実行し、コマンドが非ゼロで終了する
  2. 失敗の種別・コマンド・終了コード・エラーの抜粋（機密情報を伏せたもの）が失敗イベントとして記録される
- **受け入れ条件**:
  - [ ] 非ゼロ終了したコマンド 1 回につき、終了コードを含む失敗イベントが 1 件記録される
  - [ ] 1 回のコマンド失敗が、再発サマリーの集計で 2 回に数えられない（既存の出力パターン検知と重なる場合を含む）
  - [ ] 意図した非ゼロ終了の典型（検索の不一致、存在確認、差分の有無の確認）は、再発サマリーの集計に入らない
  - [ ] 非ゼロ終了の記録が増えても、既存のテスト・lint の再発が再発サマリーの集計対象から押し出されない
  - [ ] 既存の失敗イベントの形式を変えず、それを読む利用者（再発サマリーの注入、loop-harness、quality-gates、評価セット）が動き続ける

### FR-05: auto mode の拒否の記録

- **対応機能**: FT-05
- **優先度**: Should
- **概要**: auto mode がツール呼び出しを拒否したときに、失敗イベントを記録する
- **ユースケース**:
  1. auto mode でエージェントがツールを呼び、拒否される
  2. 拒否された呼び出しと拒否の種別が失敗イベントとして記録される
- **受け入れ条件**:
  - [ ] auto mode の拒否 1 件につき、拒否であることが分かる種別の失敗イベントが 1 件記録される

### FR-06: セッション終了時の教訓化

- **対応機能**: FT-06
- **優先度**: Must
- **概要**: 教訓化が有効なとき、セッションの終了時に裏の処理を起動する。裏の処理は前段判定を行い、合図があったときだけ教訓化セッションを呼んで教訓候補を作る
- **ユースケース**:
  1. 利用者がセッションを終える。セッション終了時の hook は裏の処理を起動してすぐ戻り、利用者は待たされない
  2. 裏の処理が前段判定を行う。失敗イベント、セッションの記録にあるツールエラー・手動の拒否・中断・訂正の兆候のいずれかがあれば「合図あり」とする
  3. 合図があれば、セッションの記録から機密情報を伏せた抜粋を作り、教訓化セッションに渡す
  4. 教訓化セッションの出力を形式検査したうえで、候補の置き場に保存・合流する（FT-11・FT-12）
- **受け入れ条件**:
  - [ ] 教訓化が無効（`distill.enabled: false`）のときは、何も起動しない（既定は有効。2026-11-03 改訂）
  - [ ] 前段判定で合図がないときは、LLM を呼ばない
  - [ ] 手動の拒否・中断のいずれかを含むセッションは、必ず「合図あり」と判定される（固定の評価用記録で 100%）
  - [ ] ツールエラー・失敗イベント（意図した非ゼロ終了を除く）は、未解決のまま終わった・同じ失敗を一定回数以上繰り返した（回数の基準はテスト・lint とそれ以外で分け、それ以外の方を低くする）、のいずれかに当たるときだけ合図とする。TDD の red → green だけのセッションは「合図なし」と判定される（固定の評価用記録で 100%）。1 回で解決したテスト・lint 以外の失敗は合図にしない（2026-11-03 の設計レビューで決定。LLM の呼び出しと雑音を抑えるため）
  - [ ] 機械的な失敗がなく訂正だけを含むセッションの 8 割以上が「合図あり」と判定される（固定の評価用記録 5 件以上）
  - [ ] 同じセッションの同じ範囲を 2 回教訓化しない。再開したセッションが再び終わったときは、前回の教訓化以降の部分だけを対象にする
  - [ ] 裏の処理が失敗しても利用者のセッションに影響せず、失敗の理由が記録される（NF-08）

### FR-07: 人間の介入とずれの抽出

- **対応機能**: FT-07
- **優先度**: Must
- **概要**: 教訓化セッションは、セッションの記録の抜粋から、ユーザーの訂正・差し戻し・手動の拒否・中断と、エージェントが自分で気づいたずれを読み取り、「何がずれていて、どう直したか」を教訓候補にする
- **ユースケース**:
  1. 利用者がエージェントの作業を「そうじゃない」と訂正し、エージェントがやり方を変えて解決する
  2. 教訓化セッションが、訂正の前後から教訓候補を作る
- **受け入れ条件**:
  - [ ] 判定: 訂正と解決を含む評価用記録（5 件以上）の 8 割以上から、訂正の内容と回避策を含む教訓候補が作られる
  - [ ] 判定: 訂正も失敗も含まない評価用記録（5 件以上）から教訓候補が作られる割合が 2 割以下
  - [ ] 判定: データの消失・取り消せない操作・機密情報の漏えいを含む評価用記録（5 件以上）の 8 割以上で、作られた候補の重大度が「重大」になる。それ以外の失敗を含む評価用記録（5 件以上）で「重大」になる割合が 2 割以下

### FR-08: 意図した失敗・一過性の失敗の除外

- **対応機能**: FT-08
- **優先度**: Must
- **概要**: §5 の「教訓候補にしないもの」に当たる失敗からは、教訓候補を作らない
- **ユースケース**:
  1. TDD でテストを先に書いて落とし、実装して通す
  2. 教訓化セッションは、この失敗を意図した失敗と判断し、教訓候補を作らない
- **受け入れ条件**:
  - [ ] 判定: TDD の red → green だけを含む評価用記録（5 件以上）から教訓候補が作られる割合が 2 割以下
  - [ ] 判定: ネットワークの一過性エラーとやり直しだけを含む評価用記録（5 件以上）から教訓候補が作られる割合が 2 割以下

### FR-09: レビュー指摘の教訓化

- **対応機能**: FT-09
- **優先度**: Should
- **概要**: `/review-respond` で採用と判断した指摘のうち、この変更に限らず一般化できるものを教訓候補にする（既存の候補と同じなら合流させる）。実行中のセッション自身が判断するため、追加の LLM 呼び出しは発生しない
- **ユースケース**:
  1. 利用者が `/review-respond` で bot のレビュー指摘に対応する
  2. 採用した指摘のうち教訓になるものが教訓候補になり、根拠として PR と指摘への参照が残る
- **受け入れ条件**:
  - [ ] 採用しなかった指摘は教訓候補にならない
  - [ ] 同じ PR の複数の指摘が同じ教訓に合流しても、再発回数は 1 として数える
  - [ ] 候補の保存に失敗しても、`/review-respond` は止まらず、返信・resolve を続ける
  - [ ] 保存した候補は `/review-respond` の再実行時の処理判定に使わない（既存の冪等性の原則を保つ）

### FR-10: CI の失敗・revert の教訓化（Could）

- **対応機能**: FT-10
- **優先度**: Could
- **概要**: PR の CI の失敗や revert を、教訓候補の材料にする。取得の入口は基本設計で決める

### FR-11: 教訓候補の保存

- **対応機能**: FT-11
- **優先度**: Must
- **概要**: 教訓候補を、人が読めて他の CLI にも渡せるテキスト形式で、候補の置き場に保存する。他の CLI に自動では読み込ませない（未承認の候補のため）
- **ユースケース**:
  1. 教訓化セッション（FT-06）または `/review-respond`（FT-09）が教訓候補を作る
  2. 教訓候補が root worktree の候補の置き場に保存される
  3. 後日、利用者が候補の置き場のファイルを開いて溜まった教訓候補を読む。必要なら Codex にファイルを渡して読ませる
- **受け入れ条件**:
  - [ ] 教訓候補が、事象・原因・回避策・根拠（根拠ごとの日時を含む）・再発回数・重大度・対象範囲・状態（状態が変わった日時を含む）を持つ
  - [ ] linked worktree で作業しても root worktree の置き場に保存され、worktree を削除しても残る
  - [ ] 候補の置き場は git で追跡されず、所有者だけが読み書きできる権限で作られる
  - [ ] テキスト形式（Markdown または JSON Lines）で保存される
  - [ ] 保存された内容に、既知の機密情報のパターンが原文で残らない（NF-03）

### FR-12: 再発した教訓の合流

- **対応機能**: FT-12
- **優先度**: Must
- **概要**: 新しく作った教訓候補が既存の候補と同じ教訓なら、新しい候補を作らず、既存の候補の再発回数と根拠を足す
- **ユースケース**:
  1. 別の日の別のセッションで、sandbox 内で一時ファイルを作れず失敗し、同じ回避策で解決する
  2. 教訓化セッションが作った候補は、既存の「sandbox 内の一時ファイル作成」の候補と同じ教訓と判定される
  3. 既存の候補の再発回数が 1 増え、今回のセッションが根拠に加わる
- **受け入れ条件**:
  - [ ] 同じ教訓と判定された候補が異なるセッションから 2 回作られたとき、候補は 1 件のままで再発回数が 2、根拠が 2 件になる
  - [ ] 同じ根拠（同じセッション・同じ PR）から同じ教訓が再び作られても、再発回数は増えない
  - [ ] 昇格中・昇格済み・却下の候補に合流した場合も、再発回数と根拠は足される
  - [ ] 判定: 同じ教訓の言い換えの組（5 組以上）の 8 割以上が合流し、異なる教訓の組（5 組以上）が誤って合流する割合が 1 割以下

### FR-13: 昇格候補の提示

- **対応機能**: FT-13
- **優先度**: Must
- **概要**: 昇格の基準を超えた候補を、セッション開始時に一覧で知らせる
- **ユースケース**:
  1. 利用者がセッションを始める
  2. 基準を超えた候補があれば、件数・各候補の要約・昇格スキル（FT-14）の案内が示される
- **提示の基準**:
  - 状態が「候補」で、再発回数が閾値（設定で変える。既定値は基本設計で決める）以上のもの
  - 状態が「候補」で、重大度が「重大」のもの（再発回数が 1 でも示す）
  - 状態が「昇格済み」で、昇格後に閾値以上再発したもの（昇格したのに効いていない教訓として示す）
  - 状態が「昇格中」のまま一定期間（設定で変える）を過ぎたもの（反映の確認を促す。閉じられた PR の教訓が昇格中のまま埋もれないようにする）
- **受け入れ条件**:
  - [ ] 基準を超えた候補がないときは、何も示さない
  - [ ] 示す一覧の内容が前回示したものから変わったときは示す。同じ内容の一覧は、同じ root で 1 日 1 回までにする（worktree をいくつ開いても同じ内容を繰り返さない）
  - [ ] 状態が「却下」の候補と、期間内の「昇格中」の候補は示さない
  - [ ] 示す件数と文字数が設定の上限を超えない
  - [ ] 示す内容は無害化される（NF-04）
  - [ ] 重大度が「重大」で再発回数が 1 の候補は、見出しなどの文面を示さず、件数と ID だけを示す（人が確認していない LLM の文を、再発の裏付けなしにエージェントの文脈へ入れないため）
  - [ ] 非対話のセッション（`-p` での実行、自律実行の基盤からの起動）では示さない

### FR-14: 昇格スキル

- **対応機能**: FT-14
- **優先度**: Must
- **概要**: 人が教訓候補を確認し、昇格先を選び、書き込む差分を承認して反映するスキルを提供する。書き込みは作業中の worktree の昇格先に行い、コミットと PR は通常の手順で行う
- **ユースケース**:
  1. 利用者が昇格スキルを呼ぶ
  2. 昇格候補の一覧から 1 件を選ぶ（提示されていない候補・却下した候補も一覧で選べる）
  3. 対象範囲を確定し、昇格先（AGENTS.md の記述欄 / プロジェクト独自の `.claude/rules` / ガード）を選ぶ
  4. 書き込む差分（ガードの場合は Issue の本文）が示され、利用者が承認すると書き込まれる
  5. 候補の状態と昇格先が記録される
- **状態の遷移**:
  - 候補 →（承認してファイルに書き込む）→ 昇格中 →（統合ブランチへの反映を確認）→ 昇格済み
  - 昇格中 →（書き込みを含む PR が閉じられたと確認）→ 候補
  - 候補 →（ガードの Issue の作成に成功）→ 昇格済み（Issue への参照を記録）
  - 候補 →（却下）→ 却下。却下 →（利用者が戻す）→ 候補
  - 昇格中の確認は昇格スキルを実行したときに行う
- **受け入れ条件**:
  - [ ] 利用者が承認しない限り、昇格先のファイルに書き込まない（候補の状態の更新は除く）
  - [ ] AGENTS.md の管理ブロックと、orchex が配布する rule には書き込まない
  - [ ] ガードを選んだときは Issue の作成までを行い、テスト・hook・lint のコードは書かない。Issue の作成に失敗したら状態を変えず、理由を示す
  - [ ] 対象範囲が Claude Code 固有の候補を AGENTS.md に書こうとしたとき、および全 CLI 共通の候補を `.claude/rules` に書こうとしたときは、届く CLI が変わる旨を示して確認する
  - [ ] 昇格先に同じ内容がすでにあるときは、書き込まずに「昇格済み」にすることを提案する
  - [ ] 昇格する文面は、要約せずにそのまま承認画面に示す。昇格先に書く文面には根拠（セッション ID・PR への参照）を含めない
  - [ ] 書き込む直前に、昇格する文面へ伏せ字を再びかけ、URL・メールアドレス・ホームディレクトリのパスなどを見つけたら差分に警告を出す
  - [ ] 公開リポジトリに書き込む（AGENTS.md・`.claude/rules`）・Issue を作るときは、公開であることを示して明示的に確認する

### FR-15: 昇格・却下の結果の記録

- **対応機能**: FT-15
- **優先度**: Must
- **概要**: 昇格スキルでの昇格・却下の結果を候補の状態に記録し、提示に反映する。却下は利用者が戻すまで続く
- **ユースケース**:
  1. 利用者が昇格スキルで候補を見て、「この教訓は今回限りの事情で、ルールにする必要はない」と却下する
  2. 候補の状態が「却下」になり、以降のセッション開始時に示されなくなる
- **受け入れ条件**:
  - [ ] 却下した候補は、以降のセッション開始時に示されない
  - [ ] 却下した候補と同じ教訓が再び作られたときは、却下した候補に合流し（再発回数は足す）、提示されない
  - [ ] 却下した候補は、利用者の操作で「候補」に戻せる
  - [ ] 昇格後の再発として示した候補は、利用者が昇格スキルで確認すると、その後さらに閾値以上再発するまで示されない
  - [ ] 昇格中・昇格済みの候補には昇格先が記録されている

### FR-16: 作業直前の注入（Could）

- **対応機能**: FT-16
- **優先度**: Could
- **概要**: 候補の段階でも、関連する操作の直前に該当する教訓を、未承認の候補であることを明示して注入する（Issue #332 の方向）。人が承認していない文をエージェントの判断材料にするため、注入の範囲と無害化は NF-04 と同等以上とする

### FR-17: auto-memory からの複製（Could）

- **対応機能**: FT-17
- **優先度**: Could
- **概要**: auto-memory の feedback のうち落とし穴と回避策に当たるものを、教訓候補として候補の置き場へ複製する。auto-memory の書き換え・削除は行わず、整理は人が memory-layers の棚卸しの手順で行う

### FR-18: 運用規約の改訂

- **対応機能**: FT-18
- **優先度**: Must
- **概要**: 記憶の層の分担と昇格の手順を、本要件に合わせて改訂する
- **ユースケース**:
  1. エージェントが作業中に教訓を得たとき、memory-layers ルールを読んで、落とし穴と回避策は候補の置き場、利用者の好みは auto-memory と書き分ける
  2. 利用者が昇格の手順を確かめるとき、memory-layers ルールから提示と昇格スキルの流れが分かる
- **受け入れ条件**:
  - [ ] memory-layers ルールに、候補の置き場（層）・fail-logs を昇格の入口とすること・提示の自動化・昇格先の範囲が書かれている
  - [ ] memory-layers ルールの「パッケージの hook が自動で記録するログは対象外」と「昇格の書き込み先は記述欄だけ」の記述が、本要件と矛盾しない形に改訂されている
  - [ ] 新しい ADR が、ADR-20260927-057 の対象外 2 項目（fail-logs を昇格の入口にすること、昇格・棚卸しの自動化）と決定 4（昇格の書き込み先は AGENTS.md の記述欄だけ）を部分的に置き換えると明記している
  - [ ] ADR-20260927-057 に、部分的に置き換えられた旨の注記がある
  - [ ] `docs/adr/DECISIONS.md` に新しい ADR の行がある

### 9.1 LLM の判断に依存する受け入れ条件の確かめ方

- LLM を使わない部分（前段判定の機械的な合図、保存、合流での再発回数の計算、状態の遷移、上限、権限）は、CI のテストで LLM を呼ばずに確かめる
- LLM の判断（「判定」と付けた受け入れ条件）は、固定の評価用記録（合成データでよい）に対して手動で実行し、合格率で判定する。CI では実行しない
- 評価用記録の置き場と形式は基本設計で決める

## 10. 制約

- 振る舞いを変えるため、評価セットを実装より先に改訂し、人のレビューを経る（evaluation-set-policy）
  - `docs/evaluation/fail-logs.md`（記録の契約、重複を排除しない旨の観点、非ブロッキングの観点を新しい部品にも課すか）
  - `docs/evaluation/skills/review-respond.md`（FT-09 で手順を変える場合。冪等性の観点）
  - 昇格スキルの評価セットを `docs/evaluation/skills/` に新設する
- 失敗イベントの検知部品は loop-harness と quality-gates も使う共有部品のため、その入力と戻り値を変えない（変える場合は利用者側の回帰を確認する）
- 設定ファイルを変えたら `.claude/orchestra.json` の台帳を同じコミットで更新する
- 状態を変える操作（昇格・却下・Issue の作成）の入口は、エージェントが使う入口と分け、利用者に許可リストへ入れないよう案内する
- スキルを足したら、パッケージの manifest に登録し、`facet build` の生成物をコミットする
- `docs/reference/hooks.md`・`docs/reference/logging.md`・`packages/fail-logs/README.md`・`docs/design/fail-logs.md` を追従させる

## 11. 未確認事項（基本設計で確かめる）

- 訂正の兆候を LLM を使わずに検出する方法と、その評価用記録
- 前段判定の誤検知の抑え方と、1 日の上限に達しそうなときの優先順位（合図の強い順など）
- 非対話のセッション（`-p` での実行、自律実行の基盤からの起動）を hook が見分ける方法（FR-13）
- 同じ教訓かどうかを判定する方法（合流の鍵）と、昇格の基準の既定値
- 教訓化セッションの呼び出し方法（LLM の経路、認証、hook と道具の無効化、標準入出力の扱い）
- ツール呼び出しの失敗時に hook へ届く入力の実際の形（エラーの書式、sandbox の拒否の届き方）
- セッション終了時の hook に実際に使える時間
- 機密情報を伏せる仕組みとして、既存の実装のどれを使うか（fail-logs は audit に依存しない方針との兼ね合い）
- 統合ブランチへの反映と PR が閉じられたことの確認方法（FR-14）
- CI の失敗・revert の取得の入口（FT-10）
