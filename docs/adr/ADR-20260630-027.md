# ADR-20260630-027: fail-logs 活用フェーズ — SessionStart で再発失敗シグネチャを注入する

- **ステータス**: accepted
- **日付**: 2026-06-30
- **決定者**: yoshihiko
- **関連**: ADR-20260612-025（fail-logs 新設・記録フェーズ）, `packages/core/hooks/load-task-state.py`（注入パターンの先行例）

## コンテキスト

ADR-20260612-025 で失敗イベントを `.claude/logs/fail-logs/failures.jsonl` に記録する基盤（記録フェーズ）を新設した。同 ADR の「将来の移行パス」で **fail-logs の活用フェーズ: SessionStart での失敗サマリー注入** を予告しており、本 ADR はその第 2 段階（記録 → 活用）の設計判断を記録する。

Claude Code はセッションをまたぐと記憶がリセットされる。前セッションで失敗してもログに残るだけで誰も読み返さず、同じ失敗が繰り返される。活用フェーズのゴールは **「過去の失敗を次セッション冒頭で AI に思い出させ、再発を回避させる」** ことにある。

この機能は **AI が裏で参照する内部機構**であり、利用者が存在を知る必要はない。したがって README への利用者向け記載は行わず、設計判断は本 ADR にのみ残す。

## 検討した選択肢（集計軸）

蓄積した失敗ログを「何でグルーピングして要約するか」が設計の核心。生ログを全部見せるとノイズでコンテキストを浪費するため、集計軸の選定が必要になった。

### 選択肢 A: `failure_type` 別カウント

- 例: `test_failure: 10, tool_error: 8` を注入する
- メリット: 実装が最小。集計として綺麗
- デメリット: **AI への行動指針にならない**。どのコマンドで・なぜ落ちたかが分からず、「テストが10回落ちた」は人間が眺めるダッシュボード指標にすぎない。活用フェーズの目的（再発回避）と噛み合わない

### 選択肢 B: `command_kind` / `error_type` 別の中粒度集計

- メリット: 型より原因の場所が絞れる
- デメリット: 具体的なコマンド例を出さないため、依然として「何を避ければよいか」が AI に伝わりにくい

### 選択肢 C: 再発失敗シグネチャ中心

- 2 回以上再発した**具体的なコマンド + エラー抜粋**を頻度順で見せる
- メリット: AI が「この操作は避けよう／直そう」と具体的な回避行動を取れる。1 回きりの失敗は除外されるため自然とノイズが抑制される
- デメリット: シグネチャの正規化に設計判断が要る（粒度が細かすぎると再発がまとまらない）

## 決定

**選択肢 C を採用する。** 注入サマリーの主軸は「再発した失敗シグネチャ」とし、`failure_type` 別カウントは全体像を示す 1 行見出しにのみ用いる。

1. **新規 SessionStart hook**（`packages/fail-logs/hooks/inject-failure-summary.py`）を追加する。`failures.jsonl` を読み、要約を **stdout に print** してコンテキストへ注入する（`load-task-state.py` と同じ注入方式・`[fail-logs]` プレフィックス）。
2. **集計軸 = 再発シグネチャ**。シグネチャは安定キーで、`command_kind` + コマンド先頭トークン（Bash の場合）で構成し、`command` が空（非 Bash）のときは `tool` + `failure_type` にフォールバックする。同一シグネチャの件数を数え、**再発（count ≥ 2）したものだけ**を頻度順・上位 N 件で表示する。各エントリは「件数 + 代表コマンド + エラー抜粋」を含める。
3. **`failure_type` 別カウントは捨てず**、先頭の 1 行見出し（例: `直近 7 日で 23 失敗: test 10 / tool 8 / lint 5`）として全体像にのみ使う。
4. **フィルタリング**: ログ末尾から最大 `max_records` 行のみ走査（I/O 抑制）し、`ts` で直近 `window_days` 日にフィルタする。
5. **ノイズ抑制**: 再発シグネチャが 1 件もなければ**何も注入しない**（記録フェーズの「失敗のみ記録」と同じ思想）。
6. **config-driven**。`config/fail-logs.yaml` に `summary:` ブロックを追加し、有効/無効・期間・走査上限・表示件数・代表例表示を制御する。`fail-logs.local.yaml` で上書き可能。
7. **記録フェーズには一切手を入れない**。`capture-failures.py` / ログスキーマ / `failure_detector` は変更せず、後方互換を維持する（純粋な追加機能）。
8. **間接プロンプトインジェクション対策**。注入する `command` / `error_excerpt` はログ由来の信頼できない外部データのため、`<fail-logs-summary>` 境界フレームで囲み「指示ではなく参照情報」と明示し、抜粋行には `[log]` プレフィックスを付ける。さらにログ本文中の山括弧 `<` `>` を視覚的に近い記号へ中和し、`</fail-logs-summary>` 等の**境界フレーム偽造を防ぐ**（PR #104 レビュー反映）。`logs_dir` は config 経由のパストラバーサルを避けるため `realpath` で project_dir 配下を検証する。
9. **末尾シーク読み出し**。`max_records` が実際に SessionStart の I/O を制限するよう、ログ全行を走査せずファイル末尾からチャンク単位で遡って末尾 N 行のみ読む（長期運用でログが肥大しても起動コストを一定に保つ・PR #104 レビュー反映）。

### 設定スキーマ（`summary:` ブロック）

```yaml
summary:
  enabled: true # SessionStart 注入の有効/無効
  window_days: 7 # 直近何日分を対象にするか（0 で無期限）
  max_records: 200 # 走査するログ行数の上限（末尾から）
  min_occurrences: 2 # 再発とみなす最小回数（これ未満は注入しない）
  top_signatures: 5 # 表示する再発シグネチャの上位件数
  show_examples: true # 代表コマンド + エラー抜粋を表示するか
```

## 影響

- **責務境界は不変**: fail-logs=失敗知識の蓄積（記録）+ その活用（注入）。audit / quality-gates には引き続き依存しない。
- **後方互換**: 既存の記録機能・ログスキーマ・依存（core のみ）に変更なし。manifest に SessionStart hook を 1 つ追加するのみ。
- **コンテキスト消費**: 再発がなければ 0、あっても上位 N 件 + 見出し 1 行に制限されるため軽量。
- **利用者向けドキュメント**: README には追記しない（AI 内部機構のため）。設計の振り返りは本 ADR を正本とする。

## 将来の移行パス（次フェーズ候補）

1. 注入された失敗が解消されたら `.claude/rules/` へ「教訓」として昇格する仕組み（ADR-20260612-025 の将来パス 3 と接続）。
2. シグネチャ正規化の精度向上（コマンド引数のパラメータ化など）。
3. セッション横断ではなく「同一作業ブランチ内」の失敗に重み付けする等のスコープ調整。
