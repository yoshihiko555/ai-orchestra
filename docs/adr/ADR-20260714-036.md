# ADR-20260714-036: 固定 CLI の beta allowlist と最小 request envelope を broker で強制する

- **ステータス**: accepted
- **日付**: 2026-07-14
- **決定者**: yoshihiko（2026-07-14 承認）
- **更新**: 2026-07-19（Issue #261 の再検討記録、および PR #273 bot レビューによる
  bypassPermissions 例外の記録を追記。決定本体は不変）

## コンテキスト

ADR-20260712-034 は、scenario container の Claude Code CLI を ephemeral broker 経由の Claude Max OAuth で
実行すると決定した。`target=skill:<slug>` の M0 実測で、次の二点が判明した。

1. broker が CLI の `anthropic-beta` を全て剥離して OAuth feature だけを送ると、CLI 2.1.207 の request body
   と header capability が不一致になり、upstream は `context_management: Extra inputs are not permitted`
   の 400 を返す。これは認証失敗や subscription 利用制限ではない。
2. CLI の既定 tool schema と 64,000 output token をそのまま公開すると、broker の保守的な単発 request
   上限は約 $8.40 となり、標準の $3 run budget を upstream 送信前に拒否する。tool 公開を skill 実行に
   必要な集合へ絞り output を 4,096 token にすると、同じ上限は約 $2.29 まで下がる。

この upstream 送信前拒否は broker 自身が返すローカル 429 であり、Max subscription の利用制限ではない。
また `$` 表示は subscription 経路でも run 内の比較・暴走防止に用いる等価コストで、PAYG 課金経路を
示すものではない。

また `/handoff test` は `Skill` を permission allowlist に含めなくても正本の Step 1 を展開し、Bash tool で
script 起動を選択した。skill 発火そのものに追加の従量課金 API や Python import 結合は不要だった。

## 検討した選択肢

### 選択肢 A: 予算だけを引き上げ、client beta を任意転送する

- メリット: CLI request を加工せず通しやすい。
- デメリット: candidate が任意 beta を upstream へ渡せ、covert channel と未知機能の有効化面が広がる。
  tool schema と output 上限の無駄も残る。

### 選択肢 B: 固定 CLI beta の完全 allowlistと scenario 別 request envelope を使う

- メリット: pin 済み CLI の互換性を保ちつつ、未知 beta と不要 tool/output を fail-closed にできる。
  $3 budget を維持し、Claude Max subscription の OAuth 経路だけを使える。
- デメリット: CLI pin を更新するたびに beta allowlist と envelope の再スパイクが必要になる。

### 選択肢 C: 全 request を Token Count API で事前計測する

- メリット: body byte数による上限より精密に input token を算出できる。
- デメリット: preflight 自体が追加 endpoint・追加 request・失敗モードを持ち、M0 で必要性が確認されていない。

## 決定

**選択肢 B を採用する。** broker は固定 CLI 2.1.207 が送る既知 `anthropic-beta` feature と
`oauth-2025-04-20` の和集合だけを転送し、未知・重複・不正値を拒否する。scenario runner は
`allowed_tools` の presence semantics から `--allowedTools` と `--tools` を構成し、
`CLAUDE_CODE_MAX_OUTPUT_TOKENS` を scenario budget から設定する。

`--tools` は model に利用可能な tool schema を提示するだけで、実行 permission を付与しない。
`--allowedTools` だけが permission allowlist である。skill target では slash command の解決に必要な
`Skill` schema を `--tools` に提示するが、`Skill` を `--allowedTools` へ暗黙追加しない。

CLI 2.1.207 に対する client beta allowlist は次の10種に固定する。

- `claude-code-20250219`
- `context-1m-2025-08-07`
- `interleaved-thinking-2025-05-14`
- `thinking-token-count-2026-05-13`
- `context-management-2025-06-27`
- `prompt-caching-scope-2026-01-05`
- `mid-conversation-system-2026-04-07`
- `advisor-tool-2026-03-01`
- `effort-2025-11-24`
- `structured-outputs-2025-12-15`

従量課金 API key への fallback は設けない。Token Count API の事前計測は、最小 envelope でも正当な
scenario が継続的に拒否される実測が得られるまで導入しない。

## 影響

- Claude CLI image/pin 更新時は、client beta 一覧・slash skill 発火・broker 上限見積もりを M0 で再検証する。
- skill scenario は必要最小限の `allowed_tools` と `budget.max_output_tokens` を明示する。
- 固定 CLI の `/messages` と `/messages/count_tokens` の重なりは、1件だけ待機させて直列化する。
  追加の並行要求は anomaly として拒否し、同時 upstream 1件の上限を維持する。
- slash skill 発火のために `Skill` schema は公開するが、`Skill` permission を暗黙付与しない。
- Max subscription OAuth が利用不能な場合は fail-closed とし、PAYG API へ自動切替しない。
- ADR-20260712-034 の Docker + ephemeral broker という基本構造は変更しない。

## 再検討記録（2026-07-18〜19, Issue #261）

Phase A bootstrap の実 backend smoke で、本 ADR の保守的見積り式（1 byte = 1 token・カテゴリ最大単価）と
シナリオ予算・既定モデル価格の較正ずれが重なり、routing-config シナリオが 1 リクエストも通らず全滅した
（Issue #261）。これを受けて選択肢 C（Token Count API による事前計測）を含む見積り式の緩和を
Codex 設計相談（2026-07-18）で再検討し、次のとおり判断した。

- **見積り式は緩めない（再確認）**: bytes→tokens の `/4` 換算緩和は、adversarial な高エントロピー payload に
  対する保守上限を失うため不採用。「軽い request で信頼を作って次で悪用する」パターンに耐性がない
  adaptive 見積りも不採用。
- **cache prefix の分離課金は不採用**: pre-admission 時点で cache hit/miss を判定できない。主因はモデル tier
  ずれであり効果も小さい。
- **`DISABLE_PROMPT_CACHING` は不採用**: キャッシュヒットによる節約まで失う。
- **較正ずれ側の解消で unblock**: evaluate/judge のモデル pin（`claude-sonnet-5`）と broker pricing 上限の
  Sonnet 単価再較正 + model allowlist の fail-closed 検証（PR #263 / #265）、
  `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` の scenario/judge/capability smoke 3 経路伝播（PR #269）、
  シナリオ予算再較正（6-turn $1.50 / 3-turn $0.90、PR #270）。実 backend 再検証で 3-turn $0.90 は
  worst-case 前課金に届かず broker 429 で cost latch する事例が確認されたため、PR #273（Issue #261
  PR6）で 6-turn と同額の $1.50 に再統一した。
- **Token Count API（選択肢 C）は Phase B で再検討**: 導入条件は「決定」節の
  「最小 envelope でも正当な scenario が継続的に拒否される実測」に加え、Phase A 較正後も
  カテゴリ最大単価 × バイト数の上限マージンが評価コスト効率を実質的に阻害する実測が得られた場合の
  精密化手段とする。preflight 追加 endpoint の失敗モードと追加 request コストの評価を伴うこと。

補足:

- **cache TTL 二重性の明文化**: prompt cache write は 5m / 1h の 2 種の単価を持つ。broker の
  `cache_creation` 上限単価は 1h cache write（Sonnet $6.0/MTok）を上限として採用しており、
  5m write（$3.75/MTok）はこの上限に包含される。
- **1M context beta の扱い**: client beta allowlist の `context-1m-2025-08-07` は残置する
  （allowlist は「許可」であり「必須」ではない）。1M context の要求自体は CLI 側 env
  （`CLAUDE_CODE_DISABLE_1M_CONTEXT=1`）で抑止する。

## 再検討記録（2026-07-19, PR #273 bot レビュー — bypassPermissions 例外）

task-state 2 シナリオ（`mark-task-done` / `record-architecture-decision-holdout`）と handoff 2
シナリオ（`create-handoff` / `create-handoff-holdout`）の計 4 シナリオに限り、`--allowedTools`
だけが実効 permission であるという meta-harness の原則（EV-51）の例外として
`permission_mode: bypassPermissions` を導入した。

- **対象**: `packages/meta-harness/scenarios/skill/task-state/mark-task-done.yaml` /
  `record-architecture-decision-holdout.yaml`、`skill/handoff/create-handoff.yaml` /
  `create-handoff-holdout.yaml` の 4 シナリオのみ。他の全シナリオは既定の `acceptEdits` のまま。
- **理由**: これら 4 シナリオは `.claude/Plans.md`（task-state の対象）または
  `.claude/handoffs/`（handoff の成果物）という `.claude/` 配下の Claude Code protected path
  への書込みを必要とするが、公式 docs（code.claude.com/docs/en/permission-modes.md
  "Protected paths"）で裏取りした通り、protected-path のチェックは allow ルール（`Edit(path)` /
  `Write(path)` いずれの記法でも）の評価より**先に**実行されるため、`--allowedTools` に個別の
  path 指定を追加しても解除できない。非対話（ヘッドレス `claude -p`）で解除できる唯一の手段が
  `--permission-mode bypassPermissions` であり、これはシナリオ単位の明示 opt-in（schema-enforced
  enum、既定は変わらず `acceptEdits`）として実装した（Issue #261 PR6 bot レビュー対応、詳細設計
  §2-2・§4）。
- **補償コントロール**（bypass によって失われる allow ルールの代替として、この 4 シナリオに限り
  多層で防御する）:
  1. **コンテナ隔離（ADR-20260712-034）**: candidate は internal network で直 egress を持たず、
     資格情報はコンテナに置かれない。bypass の影響範囲は使い捨てコンテナ内の bind mount に限定。
  2. **最小 `--tools`**: `allowed_tools` は `Read`/`Edit`/`Write`（task-state）または
     `Bash(python3 *)` の narrow 派生 + `Write`（handoff）のみを公開し、それ以外の tool は
     bypass 下でも `--tools` の presence semantics（EV-51）で公開されない。
  3. **collateral-scope oracle**（`assert-task-state-outcome.py`）: bypass で書込み可能になった
     `.claude/` 配下について、tracked file の変更が想定パス以外に無いこと・新規 untracked file
     が想定 prefix 以外に生成されていないことを `git diff --name-status -z` /
     `git status --porcelain -z` で検証する。
  4. **Plans.md 内容一致 oracle**: task-state は Plans.md 全文を canonical fixture と突合、
     handoff は Plans.md が seed 内容から不変であることを別途検証する（`.claude/Plans.md` は
     repo `.gitignore` 対象のため collateral-scope の diff/untracked 検査の死角になる。PR #273
     bot レビュー4巡目対応）。
  5. **symlink 拒否**: collateral-scope は検出した全パス（tracked 変更・untracked 新規の両方）に
     ついて symlink を無条件で unexpected 扱いにする。`ln -s <既存ファイル> .claude/handoffs/x.md`
     のような、許可 prefix 下だがリンク先の内容で content oracle を騙す迂回を防ぐ（PR #273
     最終レビュー、security High）。
  6. **run metadata への監査記録**: `permission_mode` / `permission_mode_source`
     （`scenario`/`global` の決定根拠）を `allowed_tools_source` 等と同じパターンで
     run metadata へ永続化し、bypass が使われた run を事後追跡できるようにする。
  7. **Phase A human merge**: この 4 シナリオを含む候補の promotion は Phase A の人間承認
     マージを経ないと main へ反映されない（自動昇格しない）。
- **今後**: 5 シナリオ目以降で bypass が必要になった場合も、同じ 7 層の補償コントロール一式を
  必須とし、対象シナリオを本節に追記すること。bypass 対象を増やす場合は「allow ルールで本当に
  解除不能か」を都度公式 docs で再確認すること（Claude Code のバージョンアップで protected path
  の扱いが変わる可能性があるため）。
