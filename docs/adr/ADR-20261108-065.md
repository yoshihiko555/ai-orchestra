# ADR-20261108-065: skill-evolution は改善候補を集めて meta-harness に渡し、昇格後の再発を確かめる役だけを担う

- ステータス: 採用（accepted。2026-11-08）
- 決定日: 2026-11-08
- 決定者: yoshihiko
- 関連: [ADR-20260701-028](./ADR-20260701-028.md)（置き換え元）、[ADR-20260728-046](./ADR-20260728-046.md)（前提。台帳の置き場はこの「決定」3 に従う）、
  [ADR-20261103-063](./ADR-20261103-063.md)（前提。fail-logs の教訓候補の扱いは変えない）、`req:skill-evolution`、`design:skill-evolution`、`req:meta-harness`

## 背景

ADR-20260701-028 は、スキル実行ごとに自己申告と機械計測を集めて学び（lessons）を次の実行に注入するオンライン層と、
停止条件付きの反復でスキル自体を改善するオフライン層の二層構成を決めた。2026-11-04 に、このリポジトリの root の
`.claude/logs/skill-evolution/metrics/` と `.claude/skill-evolution/lessons/` を集計した結果、改善は回っていなかった
（マシンローカルの記録の集計。metrics の 1 行を 1 実行と数え、`success` と `self_report`・`machine.tool_uses` の値で分けた）。

- 記録は 2026-08-07〜11-04 の 77 実行。成功 69 件はすべて自己申告による。自己申告の 70 件中 65 件は `tool_uses: 0` で、
  機械が測れていたのは所要時間だけだった
- lessons は 2 ファイルで、中身は 7 月の状態行 1 つだった。lessons は worktree ごとに置かれ、worktree と一緒に消える
- オフライン層は実装されていない（Issue #139）。自己申告の指示だけが、スキルを呼ぶたびにコンテキストに注入されていた

一方、改善案の生成・holdout 付きの比較・人の PR による昇格は、meta-harness（`target=skill:<slug>`）が既に持っている。
ただし meta-harness は skill-evolution の記録を読まず、シナリオは人が手で書いており、スキルの昇格がマージされた例は
2026-11-08 時点で無い（Issue #374 は評価環境への過学習で閉じた）。

外部の自律改善の仕組み（Hermes Agent、ACE、Voyager、Darwin Gödel Machine、skill-creator の評価など）も、2026-11-04 に調べた
（調査メモはマシンローカルの `.claude/docs/research/autonomous-self-improvement.md`）。いずれも、実運用の実行から失敗を拾って
改善の材料にする前半と、評価を通してから採用する後半と、採用した後に効いたかを確かめる部分を持っていた。このリポジトリでは、
評価を通してから採用する後半は meta-harness が持っており、足りないのは前半と、採用した後の確認の 2 つだった。

決定にかかわる制約:

- 決定者（yoshihiko）の方針（2026-11-08）: スキルの改善は、反映の前に必ず人が確認する。スキルはそれを使うすべてのセッションの
  振る舞いを変え、誤った改善は失敗として表に出にくいため、評価の数値だけで採用しない
- fail-logs の失敗の記録はエージェント ID を持たない（`packages/fail-logs/hooks/capture-failures.py`）。Claude Code の hook の入力にも、
  サブエージェントの親を示す値は無い（<https://code.claude.com/docs/en/hooks>、2026-11-08 確認）
- meta-harness が改善の対象にできるのは、facet の composition（`facets/compositions/skills/<slug>.yaml`）を持つスキルだけ
  （`packages/meta-harness/lib/skill_targets.py` の `resolve_skill_target`）
- meta-harness は昇格 PR を origin/main から作り、昇格の時点で、実行している checkout のスイートのハッシュが評価のときと同じかを確かめる
  （`packages/meta-harness/lib/promoter.py` の `_has_current_hash_pair`）。スイートの中身が人の承認したものかは確かめない
- このリポジトリは公開されている（`gh repo view`、2026-11-08 確認）。スイートに入れたシナリオは公開される

## 選択肢

### A. v1 のオフライン層を実装する（不採用）

- skill-evolution が自分で改善案を作り、評価し、反映する。meta-harness と同じ仕組み（候補の生成・holdout 付きの評価・昇格）を
  2 つ持つことになり、評価の隔離も二重に作ることになる

### B. skill-evolution を廃止し、前半も meta-harness に持たせる（不採用）

- meta-harness の評価は、proposer に実運用のログを読ませない隔離を前提にしている。実運用のログを読んで帰属させる役を同じパッケージに
  入れると、読んでよい範囲の境界が混ざる

### C. 改善候補の置き場を fail-logs の教訓候補にする（不採用）

- 教訓候補は、スキルに依らない落とし穴を AGENTS.md・rule・ガードへ昇格するためのもの（ADR-20261103-063）。シナリオ・受け渡し・
  再発の確認の状態を持たせると、その範囲を超える

### D. skill-evolution を前半と後の担当に絞り、改善は meta-harness に任せる（採用）

- 改善の仕組みを 1 つに保てる。skill-evolution は、meta-harness が持っていない、実運用の証拠をシナリオまで運ぶ部分と、
  マージ後に効いたかを確かめる部分だけを持つ

### 部分ごとの選択肢

| 論点             | 採用                                                                 | 不採用と理由                                                                                              |
| ---------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 成功の判定       | 実運用の outcome の既定は `unknown`。自己申告から成功を判定しない    | 自己申告を続ける: 上の集計で成功の根拠にならず、毎回のコンテキストを消費していた                          |
| 帰属             | 人の確定を主にし、記録から一意に決まるものだけ自動で帰属させる       | 時刻の重なりで自動で帰属させる: 入れ子の実行・サブエージェントの失敗を、親の値が無いため誤って帰属させる  |
| シナリオの作り方 | proposer と別のセッションの LLM が下書きし、人が承認したものだけ使う | 人が手で書く: 実運用の証拠とつながらない。proposer に作らせる: 改善案を作る側が採点の基準を作ることになる |
| 効いたかの測り方 | マージ後の版での実行の回数と、人が確定した同じ欠陥の有無で示す       | 成功率: 実行数が少なく（3 か月で 77 回）、率は誤差に埋もれる                                              |
| v1 のデータ      | 読まず、人が実行する移行の手順で削除する                             | v2 に取り込む: 自己申告の成功を根拠に混ぜることになる                                                     |

## 決定

**skill-evolution は、実運用の証拠をスキルの実行に結び付けて改善候補として溜め、人が承認したシナリオにして meta-harness に渡し、
昇格のマージ後に同じ欠陥の再発を確かめる役だけを担い、改善案の生成・評価・昇格は meta-harness に任せる。**

1. skill-evolution と meta-harness はコードを import し合わない。両者は、シナリオのファイルの形、スイートのハッシュの計算方法、
   meta-harness の CLI の入出力だけで結ぶ
2. スキルを呼ぶたびのコンテキストの注入をやめ、スキルの実行に付く hook は記録だけを行う。Skill ツール経由の実行と、利用者の
   直接起動（`/<skill>`）の両方を記録する
3. 実運用の outcome の既定は `unknown` とし、自己申告から成功を判定しない
4. 証拠の帰属は人の確定を主にする。自動で帰属させるのは、記録から対応が一意に決まる場合だけにする。帰属できない証拠は `unknown` で残し、
   再発回数に数えない
5. 改善の反映には、シナリオの承認と昇格 PR のマージの 2 回の人の承認を必須とする。シナリオの承認では、承認した内容のハッシュを記録し、
   評価の前にスイートの中身が承認の後の状態と一致することを skill-evolution の側で確かめる。シナリオのうち評価のときに実行される行は、
   LLM の下書きには決まった形（既存の検査のスクリプトの呼び出しと、作業ディレクトリの中のファイルの作成）だけを許し、それ以外は人が書く。
   下書きの材料になる実運用の抜粋に攻撃の文字列が混ざっても、それが評価のときに実行されないようにするため
6. meta-harness に渡せるのは facet の composition を持つスキルの候補だけとし、それ以外は観測と候補の記録までにする
7. 観測・候補・受け渡しの記録は、ADR-20260728-046 の「決定」3 に従って root worktree に集約し、git 管理外に置く
8. v1 の機能（自己申告と lessons の注入、lessons の追記、自己申告による成功判定、オフライン層の起動の閾値、オフライン層の構想）を廃止する。
   導入先の互換性のため、hook のファイル名と manifest の登録は v2 の役割で使い続け、v1 の CLI のサブコマンドと設定のキーは、
   v2 を含むリリースの次のマイナーリリースまで残す。
   v1 のデータは hook が自動で消さず、人が実行する移行の手順で削除する

## 検証

- 成功の条件: スキルを呼ぶたびの追加コンテキストが 0 文字になる。1 つの候補が、観測から昇格済みまでの主経路を一周し、承認したシナリオと
  スイートのハッシュ・meta-harness の評価と候補の ID・昇格 PR・マージのコミットを、候補から辿れる
- 結果: 未検証（実装は未着手）

## 影響

- 良い影響: 改善の仕組みが meta-harness の 1 つになる。実運用の失敗が、承認済みのシナリオとして meta-harness の評価に入るようになる。
  スキルを呼ぶたびのコンテキストの消費が無くなる
- 悪い影響・トレードオフ: 人が判断する場面が増える（帰属の確定、観測を候補にすること、シナリオの承認、昇格 PR のマージ、同じ欠陥の確定）。
  実行数が少ないうちは回る量と判断した。帰属 `unknown` の証拠は人が確定するまで数えないので、その間は再発を見逃しうる
- 台帳はマシンローカルにあるので、故障やディレクトリの削除で失われる。承認したシナリオは git に残る
- 学習用シナリオの採点の説明は proposer に見えるので、改善案が学習用シナリオに合わせ込まれることはある。holdout で採否を決めて抑える
- 運用で気をつけること: 承認したシナリオは公開リポジトリに入るので、実データの写しにせず、承認のときに公開してよい内容かを確かめる。
  シナリオは評価のときに実行されるコマンドを含み、下書きは LLM が書くので、承認のときに実行される行を確かめる

## 決定しないこと

- 導入先のプロジェクトで観測した facet スキルの候補を、ai-orchestra リポジトリへ運ぶ仕組み（`req:skill-evolution` の FT-19）:
  最初の実装は ai-orchestra リポジトリでの観測だけを対象にする。導入先の facet スキルの欠陥を受け渡したくなった時点で、
  `docs/design/skill-evolution.md` の改訂で決める
- 最初に流れを一周させるスキル: 実装の後、台帳で人が欠陥と確定したスキルから選ぶ
- 外部の確認（成果物の検査や人の確認）で outcome を `success` / `failure` にする方法（FT-20）: 外部の確認の手段が決まった時点で、
  `docs/design/skill-evolution.md` の改訂で決める
- モデルの変化によるシナリオの再実行の勧め: hook の入力にモデルが無い（SessionStart を除く）。Claude Code がモデルを hook に渡すようになった時点で決める
- 失敗の自動の分類（クラスタリング）: 観測の件数が人の確認で追いきれなくなった時点で決める
- 非推奨のものを消す具体的な手順: `docs/design/skill-evolution.md` の「v1 の廃止と移行」に従う

## 追記（2026-11-10）: 非推奨期間を 1 リリースにし、`purge-v1` も同時に外した

「決定」8 の「v2 を含むリリースの次のマイナーリリースまで残す」を、利用者の決定で短くした（Issue #554）。

- 非推奨期間は v2 を含む v0.3.8 の 1 リリースとし、次のリリースで `skill_evolution.py`（v1 のサブコマンドと `purge-v1`）、
  v1 の設定のキー（`storage.dir`・`lessons`・`pending`・`offline`・`trigger`）、`gitignore_sync.py` の
  `.claude/skill-evolution/metrics/`・`pending/` を外した（CHANGELOG に **BREAKING**）
- `purge-v1` も残さない。残った v1 のデータは自動では消さず、人が消す（場所は `docs/reference/logging.md` §2）
- hook のファイル名と manifest の hook のエントリは、v2 の役割で使い続けるので残す。v1 のキーを `.local.yaml` に残した導入先でも、
  設定の読み込み・`orchex sync`・`orchex uninstall skill-evolution` は成功する（値は使われない）
