# ADR-20260715-040: 共有 facet の変更を cross-skill 回帰バッチで hard gate する

- **ステータス**: accepted
- **日付**: 2026-07-15
- **決定者**: yoshihiko（2026-07-14 承認）

## コンテキスト

`target=skill:<slug>` の改善対象を専有 instruction/script に限定すると安全だが、複数 skill が参照する
policy・output contract・knowledge を改善して全体へ還元できない。一方、共有 facet を通常の own suite だけで
評価すると、対象 skill が改善しても別 skill の critical を壊した候補が frontier や promote に到達できる。

回帰 run を既存 `run_completed` として記録すると、`target == suite_id` の既存不変条件、target 別 frontier、
quality/cost 集計を汚染する。また最後の holdout run だけを見る promote 判定では、影響 suite A の fail 後に
suite B が pass した場合に誤って通過し得る。

## 検討した選択肢

### 選択肢 A: 共有 facet を引き続き禁止する

- メリット: 既存の target 分離と評価コストを維持できる。
- デメリット: 共有ポリシーの改善を skill-evolution から全体へ還元できない。

### 選択肢 B: 回帰を警告として記録し own suite だけを gate にする

- メリット: 評価失敗や suite 不在で探索が止まりにくい。
- デメリット: critical 回帰を持つ候補が frontier/promote に進み、共有 facet 解放の安全条件を満たさない。

### 選択肢 C: evaluation batch サマリで cross-skill critical を hard gate にする

- メリット: own と影響 suite の結果を一つの判定単位に固定し、frontier・promote・予算へ一貫して反映できる。
- デメリット: ledger event、freshness、suite 別 hash、evaluation 単位の予算管理が必要になる。

## 決定

**選択肢 C を採用する。** `regression.enabled=true` を既定とし、pre-overlay baseline の composition 逆写像で
影響 skill を決定する。通常 evaluate は train、promote 前提の holdout evaluate は holdout を同じ
`evaluation_id` で実行し、`own_critical_pass AND regression_critical_pass` を合成 verdict とする。

回帰 run は `regression_run_completed`、評価単位は `evaluation_completed` で記録する。frontier と promote は
後者を eligibility authority とし、未完了バッチや一部 suite の fail を通さない。suite 不在は
`unverified_impacts` として記録・警告するが fail-closed にはしない。

## 影響

- `regression.enabled=false` は専有 facet allowlist へ縮退する互換モードとして残す。
- promote は最新 `origin/main` baseline で impact context を再計算し、不一致なら再評価を要求する。
- 回帰 run のコストは evaluation 上限と loop 予算の両方へ算入する。
- quality/cost frontier 軸は own `run_completed` のみを使い、回帰 run は混入させない。
- suite 不在 skill は PR 本文で明示し、人間が未検証の blast radius を確認できるようにする。
