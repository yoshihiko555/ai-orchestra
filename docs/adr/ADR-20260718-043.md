# ADR-20260718-043: Docker action の cleanup 失敗と実行取消を安全停止として扱う

- **ステータス**: accepted
- **日付**: 2026-07-18
- **決定者**: yoshihiko

## コンテキスト

Issue #211 Phase 4 のレビューで、action 本体が結果を生成した後の cleanup 失敗が通常の
infrastructure failure に変換され、Checker の sealed artifact を置き換えたり、Maker の CAS 完了後に
同じ action を再試行させたりする可能性が確認された。また、lease 喪失・wall-clock timeout 時の
host-side kill-tree は `docker exec` client を停止するが、scenario container 自体を直接取り消す契約を
持っていなかった。

一方、Docker/broker/container の失敗を黙殺したり host execution へ降格したりすることは、
ADR-20260712-035 と Issue #211 Phase 4 の fail-closed 原則に反する。成功扱いを維持するだけでは、
cleanup 未確認のリソースを残したまま loop を進めることになる。

## 検討した選択肢

### 選択肢 A: cleanup 失敗を警告だけにして action 結果を採用する

- メリット: 正常に生成された結果を再利用でき、loop の停止を避けられる。
- デメリット: broker/network/container 残骸や metrics 未取得を黙殺し、fail-closed 原則を弱める。

### 選択肢 B: cleanup 失敗を通常の infrastructure failure として action 結果を置き換える

- メリット: 既存の retry 経路を利用できる。
- デメリット: sealed artifact や Maker CAS と返却結果が不整合になり、完了済み作業を再試行し得る。

### 選択肢 C: 結果と確定済み Git 更新を保持し、cleanup failure で安全停止する

- メリット: cleanup 失敗を黙殺せず、完了済み成果物も上書きしない。手動確認まで再試行を防げる。
- デメリット: 一時的な cleanup 障害でも loop が停止し、運用者の確認が必要になる。

## 決定

**選択肢 C を採用する。**

1. scenario container の削除を確認できない場合は、Maker/Checker/classifier の種別を問わず
   `container_cleanup_unconfirmed` 系の `DockerActionSafetyStop` とする。Maker は従来どおり finalize/CAS
   を禁止する。
2. scenario 削除確認後は、Maker の finalize/CAS を実行する。broker/network/settings/ephemeral runtime
   の cleanup は後続を省略せず全て試行する。
3. action 結果生成後に cleanup error が残った場合、結果や sealed artifact を infrastructure failure で
   上書きせず、`action_cleanup_failed` で安全停止する。これを成功扱いや best-effort 警告にはしない。
4. lease 喪失・wall-clock timeout は、host-side child kill に加えて選択中 executor の `cancel()` へ
   伝播する。Docker executor は取消要求を即時 latch し、実行中の scenario container を
   `docker rm -f` で破棄する。scenario の `docker run` と trusted idle-baseline capture 中は start/cancel
   の競合を避ける lock が優先されるため、実削除はその bounded start section 完了直後まで待つが、
   `docker exec` 開始前には必ず取消を再検査する。取消と finish/abort は冪等かつ race-safe にする。
5. cancel/cleanup の失敗は host execution へ fallback せず、既存の run error / safety-stop 境界へ流す。
6. Maker worktree 内の base config を protected-path として一律禁止しない。実効 base config は driver
   自身の `package_root()/config/loop-harness.yaml`、実効 local override は root worktree の
   `.claude/config/loop-harness/loop-harness.local.yaml` から読み、いずれも action worktree の rw mount
   外にある。action worktree にある同名 base config は次 dispatch の設定源にならないため、通常の
   tracked config 更新を禁止せず、このパス分離を回帰テストで固定する。ただしこの判断は、全ての
   LP-2 起動経路が `loop_driver.main()` または `LoopDriver` constructor の runtime-source guard を通る
   ことを必須条件とする。wrapper/self-hosting を含め、driver entrypoint・definition module・実効 base
   config の実パスが action worktree 配下なら config 読込・action 実行前に起動拒否し、この guard を
   bypass する別起動経路はサポートしない。

## 影響

- cleanup failure 後の自動 retry は行われず、運用者が残骸と確定済み成果物を確認してから再開する。
- Checker の既存 sealed artifact と Maker の確定済み CAS は、cleanup failure 用の偽結果で置き換えない。
- heartbeat thread からの取消は例外を外へ漏らさず、driver dispatch 側で typed error として回収する。
- action worktree 内の base config 更新は通常の Maker 成果物として review 対象に残るが、実行中 driver
  の `execution_backend` を変更しない。
- self-hosting では root worktree 上の runtime source を許可する一方、同じ action の rw worktree 内から
  runtime/config を読み込む構成は明示的に起動拒否する。
- unit test に cleanup failure の artifact/CAS 保持、全 action 共通 safety-stop、cancel race を追加し、
  opt-in containment E2E で長時間 `docker exec` の cgroup 回収を検証する。
