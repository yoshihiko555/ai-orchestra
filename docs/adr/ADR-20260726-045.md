# ADR-20260726-045: 永続イメージライフサイクルの脅威モデル再評価と異常系 stale cleanup の追加

- **ステータス**: proposed
- **日付**: 2026-07-26
- **決定者**: （人間承認待ち）

## コンテキスト

Issue #231 は「meta-harness の反復実行で OrbStack の Docker image / BuildKit cache が肥大化する」
不具合として起票された。主因は `scenario_docker_cli.py` の `_ensure_image()` が `auto_build` 時に
毎回 `docker build --no-cache -t <固定タグ>` を実行し、旧イメージをタグ上書きで dangling 化させ、
かつ BuildKit の build cache を一切 prune していなかったことにある（`docs/design/loop-harness-isolation.md`
§5.1）。

この根本原因は、Issue #250 の設計・実装（PR #306）で先行して解消された。`packages/docker-runtime/lib/docker_runtime_image.py`
の `ensure_recipe_image()` が、recipe-addressed タグ（`{repo}:sha-{digest[:12]}`）・ディスク manifest
＋ `fcntl` ロックによるプロセス間再利用・owner label 限定の世代 prune（既定 keep 3）・専用 buildx
builder・build 成功時の BuildKit cache GC（既定 168h / 10g）を備えた永続イメージライフサイクルへ
scenario/broker image の管理を移行した（`docs/evaluation/meta-harness.md` EV-94〜97）。`--no-cache`
build は廃止され、meta-harness と loop-harness（`packages/loop-harness/lib/loop_docker_image.py`）が
同一の共有モジュールを namespace 注入で利用する構成になっている。

この移行は実装が先行し、ADR としての追認・脅威モデルの再評価が行われていなかった。加えて、
実装後に次の異常系ギャップが残っていることが判明した:

- **シナリオ 2（クラッシュ中断）**: `docker buildx build --load` が成功した直後、manifest への
  書き込み前にプロセスが SIGKILL 等で終了すると、そのタグは manifest に未登録のまま Docker 上に
  残り続ける。次回以降の `ensure_recipe_image()` は manifest に記録がないため再利用も削除も行わず、
  リークしたイメージが蓄積する。
- **シナリオ 3（同一タグへの再ビルド）**: 同一 recipe hash への再ビルドでタグを置き換えた場合、
  置き換えられた旧イメージは dangling（`<none>:<none>`）化するが、`_prune_image_family()` は
  タグ付きイメージだけを走査するため dangling image を回収しない。

本 ADR はこれらを記録し、(1) `--no-cache` から recipe-addressed reuse への移行が意図した保証を
再評価し、(2) 上記 2 シナリオに対する pending journal ベースの stale cleanup 設計を追認し、(3)
意図的にスコープ外とした事項を制限事項として明記する。

## 検討した選択肢

### 脅威モデルの再評価: `--no-cache` が担っていた保証は何だったか

`--no-cache` 方式は「毎回ゼロからビルドする」ことで以下を暗黙に保証していた:

1. **鮮度**: ビルドコンテキストの変更が必ず新しいイメージに反映される（キャッシュ汚染がない）。
2. **単純な所有権**: 固定タグを直接上書きするため、「今 Docker 上にあるそのタグ = 今回ビルドした
   もの」という前提が常に成立する（プロセス間の再利用を考慮しなくてよい）。

recipe-addressed reuse へ移行すると、この 2 点は形を変えて別の保証で代替される必要がある:

1. **鮮度 → recipe hash**: `recipe_hash()` がビルドコンテキストの内容・`--build-arg`・
   `docker_label`・platform/target の全てをハッシュ化し、タグに埋め込む
   （`{repo}:sha-{digest[:12]}`）。内容が変われば別タグになるため、古い内容のイメージを
   「今回のビルドの結果」として誤って再利用することは構造的にない。
2. **所有権 → 検証済み image ID の pin**: `ensure_recipe_image()` は manifest 記録の `image_id` が
   現在の Docker 上の実体と一致することを `docker image inspect` で確認してから返す。さらに
   `scenario_docker_cli.ensure_images_detailed()` はこの検証済み `image_id` を含む `EnsuredImage` を
   呼び出し元へそのまま返し、run/preparation/broker 経路はその `image_id` を直接使う（タグの再
   inspect を挟まない）。これにより、共有タグに対する並行 retag（他プロセスの同時ビルド等）が
   発生しても、ensure が確保した image と異なる image を誤って起動対象にする TOCTOU を防ぐ
   （旧 `ImageCache.trusted_image_ids` への登録方式は #317 のリファクタでこの直接伝搬方式に
   置き換えられ、当該 alias は削除済み。PR #320 レビュー指摘）。

この対比により、`--no-cache` の 2 つの暗黙保証はいずれも recipe-addressed 方式でも成立している
と判断する。一方で `--no-cache` 方式には存在しなかった新しいリスク（プロセス間で状態を共有する
ことに由来する「manifest と Docker 実体の乖離」）が生じるため、それに対する stale cleanup が
別途必要になる。

### 選択肢 A: pending journal による所有証明 + opportunistic cleanup（採用）

- 概要: manifest とは別ファイル（`<manifest_stem>.pending.json`）に、ビルド開始前にタグを
  「in-flight」として記録する。ビルド成功と manifest 書き込みが完了した時点でエントリを消し込む。
  `ensure_recipe_image()` の**冒頭**（キャッシュヒットで再利用するだけの呼び出しも含む）で、
  この journal をもとに stale なタグ・owner label 付き dangling image を best-effort に回収する。
- メリット:
  - manifest のスキーマを変更しない（journal は sidecar として分離）。
  - 「このプロセスが今ビルドしようとしているタグ」という所有証明を、manifest 書き込み前の
    区間でも持てるため、クラッシュ後も次回呼び出しで確実に検出できる。
  - dangling image の回収は owner label のみで判定でき、pending journal の記録有無に関わらず
    安全に削除できる（tag を持たないため他所有者と衝突しようがない）。
  - 呼び出しのたびに実行されるため、専用の定期ジョブを新設する必要がない。
- デメリット:
  - 呼び出しのたびに `docker image ls` 等を実行するコストが発生するため、TTL
    （`CLEANUP_TTL_SECONDS`、既定 6h）で間引く必要がある。pending journal に記録が残っている
    場合は TTL を無視して必ず実行し、リークの検出を遅らせない。

### 選択肢 B: 定期外部ジョブによる cleanup（不採用）

- 概要: `ensure_recipe_image()` とは独立した cron 相当のプロセスが stale image を定期的に走査・
  削除する。
- デメリット: meta-harness/loop-harness はどちらも「オンデマンドの CLI プロセス」であり、
  常駐プロセスを前提とする設計は ADR-20260712-035 が確立した「常駐させない」方針と矛盾する。
  新しい実行主体・スケジューリング機構を追加するコストも大きい。

### 選択肢 C: manifest 書き込みをビルドより先に行う（不採用）

- 概要: `--load` の前に manifest へ「ビルド中」フラグ付きでエントリを先行登録し、成功後にフラグを
  下ろす。
- デメリット: manifest のスキーマ変更が必要になり、`ManifestEntry` を読む既存ロジック
  （cache-hit 判定、prune 対象抽出）がすべて「ビルド中」状態を意識する必要が生じる。所有証明の
  責務を manifest に持たせると、他 family の再入可能な短時間ロックとの整合も複雑化する。
  pending journal を別ファイルに分離した方が既存ロジックへの影響が小さい。

## 決定

**選択肢 A（pending journal + opportunistic cleanup）を採用する。**

1. `_record_pending_build()` は `_build_image()` 呼び出しの**前**に、per-family build lock を
   保持した状態でタグを pending journal（`digest` / `family` / `repository` / `docker_label` /
   `started_at` を記録）へ書き込む。
2. ビルド成功・manifest 書き込みが完了した直後（同じロック区間内）に `_clear_pending_entry()` で
   journal からエントリを消し込む。
3. ビルド失敗時（`_build_image()` 以降の例外）は `_best_effort_remove_pending_tag()` が journal
   エントリと当該タグを回収してから、元の例外をそのまま re-raise する（cleanup の失敗が build
   失敗のエラーメッセージを上書きしない）。
4. `_cleanup_stale_owned_images_best_effort()` は `ensure_recipe_image()` の**冒頭**（再利用パス
   を含む）で常に呼び出され、(a) pending journal に残ったまま manifest に未登録のタグ、
   (b) owner label 付きの dangling image、を回収する。owner label が一致しない、または pending
   journal に記録のないタグ付きイメージ（他プロジェクトが同じ repository/label を共有した
   ビルド）は削除対象にしない。
5. cleanup 自体は全域 best-effort とし、`docker image rm` の失敗は warning に留めて次回呼び出しに
   持ち越す。cleanup 内の予期しない例外も `ensure_recipe_image()` 全体を失敗させない
   （`_cleanup_stale_owned_images_best_effort` の outer try/except）。
6. cleanup の回収数・BuildKit cache 使用量を INFO ログへ出力し、観測性を確保する
   （既存の hard-fail する build path 側の `_prune_buildkit_cache` の挙動は変更しない）。

## 影響

- `packages/docker-runtime/lib/docker_runtime_image.py` は pending journal の読み書き・stale
  cleanup・ログ出力の追加により大きく拡張された（具体的な行数はレビューのたびに変動し陳腐化する
  ため本文には記載しない）。manifest のオンディスクスキーマは変更していない。
- `packages/meta-harness/lib/scenario_docker_cli.py::ensure_images_detailed()` は `ensure_recipe_image()`
  が返した検証済み `EnsuredImage`（`image_id` を含む）をそのまま呼び出し元へ返し、
  `run_preparation_command`/`_start_broker` はこの `image_id` を直接使う。後方互換の
  `ensure_images()` は引き続き `tuple[str, str]`（tag のみ）を返す薄いラッパーとして残る
  （#317・PR #320 レビュー指摘。旧 `ImageCache.trusted_image_ids` 登録方式は本文書更新時点で
  既に削除済み）。
- meta-harness・loop-harness はいずれも `packages/docker-runtime/lib/docker_runtime_image.py` を
  共有しているため、本 cleanup は両方の harness に等しく適用される。Issue #231 本文は
  「loop-harness は Docker build を実行しない」としているが、これは現在不正確である。
  `loop_docker_image.py`（`DOCKER_LABEL = "ai.orchestra.loop-harness"`、専用 builder
  `loop-harness-builder`）は meta-harness と同じ `ensure_recipe_image()` を呼び出しており、
  namespace（label・manifest/lock パス・builder 名）は独立しているが cleanup ロジックは共通基盤
  由来で自動的に適用される。監査結果の詳細は `docs/design/loop-harness-isolation.md` §5.4 に記録する。

### 既知の制限（意図的にスコープ外）

- **BuildKit cache の失敗時蓄積**: build 失敗が連続した場合の BuildKit cache 蓄積は、本 ADR の
  cleanup では扱わない。次回 build 成功時に既存の `_prune_buildkit_cache()`（age-based prune +
  size 上限超過時の無条件 prune フォールバック）が上限を強制するため、失敗が続いても次の成功時に
  自己回復する。失敗時点での即時 prune は追加しない（build 失敗の頻度・原因調査を優先すべきで、
  cleanup コストを毎失敗ごとに払う設計にはしない）。
- **docker context 往復による再 build churn**: manifest は 1 recipe あたり 1 つの `image_id` しか
  保持できないため、`desktop-linux` ⇔ `orbstack` のように daemon（docker context）を切り替える
  たびに、直前の manifest 記録が新しい daemon 上では drift として扱われ再ビルドが走る。本 ADR の
  cleanup はこの再ビルド自体で生じたリーク（旧 daemon 側の孤立イメージ等）を回収する対象では
  ない点に注意（孤立イメージは切替先の daemon には元々存在しない）。churn そのものは既知の制限
  として受容し、daemon 単位で manifest を分割する等の対応は将来のフォローアップとする。
- **recipe-addressed の限界**: `recipe_hash()` が計算する context hash はファイル内容のみを
  対象とし、symlink の有無や file mode（実行ビット等）の変化を考慮しない。依存関係（base image
  以外の外部依存）の完全な pin も本 ADR のスコープには含まない。

## 追記（2026-07-26）: pending journal 判定のレース修正

レビューで、上記「決定」§4 の初期実装に Critical 1 件・High 1 件の指摘が入った。

### 問題

`_cleanup_stale_owned_images()` は manifest lock のみを保持して実行され、`_record_pending_build()`
（build 開始前の記録）から manifest 書き込みまでの区間 —— つまり **別プロセスがまさにその
family を build 中の区間** —— にある pending エントリと、クラッシュ残骸によるエントリを
区別していなかった。`_partition_pending()` は「manifest に未登録 = stale」としか判定しておらず、
journal に記録済みの `started_at` はどこからも参照されていなかった。

このため、ある label を共有する複数 family（例: meta-harness の `scenario` build 中に `broker` の
`ensure_recipe_image()` が呼ばれる、または同一 family への同時呼び出し）が実行されている最中に、
その in-flight タグを stale と誤判定して `docker image rm` してしまう可能性があった。`_tag_latest()`
より前に消えれば偽陽性の build 失敗、後であれば不要な再ビルドを誘発する。

さらに、pending journal に**何らかの**エントリが存在するだけで TTL を無視して毎回 cleanup 一式
（`docker image ls` + `buildx du`）を実行していたため、build が継続している間はホット・リユース
パスの呼び出しすべてが cleanup コストを払うことになっていた（TTL 本来の「間引き」目的が
並行 build 時に機能しない）。

### 対策（多層防御）

1. **family lock による liveness チェック（主判定）**: 削除候補ごとに `entry["family"]` の
   per-family build lock（`_family_lock_path()`）を非ブロッキング（`LOCK_EX | LOCK_NB`）で
   取得試行する（`_family_build_in_progress()`）。取得できなければ「build 中」とみなしスキップ、
   取得できれば即座に解放して削除候補に進める（build はこのロックを区間全体で保持するため、
   非ブロッキング取得成功 = in-flight build なしを意味する）。ロックの probe 自体が manifest
   lock を保持したまま行われるため、非ブロッキングであることが必須（ブロッキングにすると、
   同じ manifest lock を待っている build 側の `_record_pending_build()` とデッドロックし得る）。
2. **`started_at` の猶予期間（副次防御）**: family lock probe が何らかの理由で誤って「解放中」と
   判定した場合に備え、`started_at` から `BUILD_TIMEOUT_SECONDS + PENDING_LIVENESS_GRACE_SECONDS`
   （既定 15分 + 5分）未満のエントリは無条件でスキップする（`_pending_entry_is_recent()`）。
   `started_at` がパース不能な場合も安全側（= in-flight とみなす）に倒す。
3. **stale 候補ゼロ時の TTL 早期リターン**: pending の存在有無ではなく、上記 2 チェックを経た
   **stale 候補が 1 件でもあるか**、または TTL が経過しているかのいずれかでのみ `docker image ls`
   等を実行する。stale 候補ゼロかつ TTL 未経過なら Docker コマンドを一切発行せず即座に return する
   （journal の resolved エントリ消し込みのようなファイルI/Oのみの後処理は行ってよい）。
4. **lock 保持時間の短縮**: 削除候補の確定（journal 読み込み + `docker image ls`）は manifest lock
   保持下で行うが、`docker image rm` のループ自体は lock を解放したあとに実行し、成功した
   エントリの消し込みだけ再度短時間ロックして行う。
5. **journal 由来タグの形式検証**: `docker image rm` に渡す前に、`recipe_tag()` が生成し得る形式
   （`<repository>:sha-<12桁hex>`）と厳密に一致するかを検証する（`_is_removable_tag_reference()`）。
   一致しないエントリは journal から消し込むのみで、Docker コマンドには一切渡さない。

dangling image（owner label 付き・タグなし）の回収ロジック自体（決定§4(b)）は本追記の対象外とする。
本追記ではレースの修正のみを行い、dangling 回収の判定条件（owner label 一致のみで削除可）は
変更していない。dangling 回収のスコープ（checkout/worktree 横断で削除してよいか）についての
最終判断は次の追記（2026-07-26 E2E 追記）で確定した。

## 追記（2026-07-26 E2E）: dangling 回収のスコープ確定、および実機検証で判明した2件のバグ修正

### dangling 回収は owner label 一致であれば checkout/worktree 横断で削除する（意図した動作）

上記「決定」§4(b) の dangling image 回収は、`main_root` や checkout/worktree では一切スコープせず、
`recipe.docker_label` の一致のみを削除条件とする。これは意図的な設計であり、以下の根拠による:

1. **dangling はタグ不在のため、そもそもどの checkout からも再利用不能な純粋なゴミである**。
   `ensure_recipe_image()` のキャッシュヒット判定はタグ（`{repo}:sha-{digest[:12]}`）を起点に
   行われる。dangling image（`<none>:<none>`）は定義上タグを持たないため、削除しても「別の
   checkout が参照していたタグを奪う」ことは構造的に起こらず、他 checkout に再ビルドを誘発しない。
2. **実行中コンテナが参照する image は Docker 自身が rm を拒否する**。仮に何らかの理由で dangling
   image が実行中コンテナの base として参照されていても、`docker image rm` は
   `image is being used by a running container` 相当のエラーで失敗し、本実装は best-effort として
   それを警告に留めて次回に持ち越す（既存の `_remove_image_best_effort` の失敗時挙動）ため、
   誤って稼働中の資産を破壊することはない。
3. **`main_root` 等で checkout 固有にスコープする代替案は不採用**。dangling image はタグを持たず
   `main_root` のようなメタデータとも紐付いていないため、スコープを絞るには pending journal と
   同様の「どの checkout が作ったか」を記録する仕組みを新設する必要があり、タグ自体は
   `manifest_path`/`lock_path` を共有する複数 checkout 間で再利用される設計（Issue #250）と
   衝突する。スコープを誤って狭めると、他 checkout が正当に持つはずの dangling 回収機会を奪い、
   ゴミの蓄積を許すリスクの方が大きいと判断した。

### バグ 1（実機 E2E で確認）: `docker image ls` に `--all` がなく dangling 回収が常に no-op

`_list_label_owned_images()` の `docker image ls --filter label=...` に `--all`/`-a` が付いておらず、
実 Docker では `-a` なしの `docker image ls` は dangling を**デフォルトで除外**するため、
`_dangling_image_ids()` は常に空リストを受け取り、上記の dangling 回収パスが実機で一度も発火しない
ことが OrbStack 上の E2E で確認された。単体テストの `FakeDocker` は `-a` の有無を区別せず常に
`image_ls_output` をそのまま返していたため、この欠落を検出できていなかった。

修正: `_list_label_owned_images()` のコマンドへ `--all` を追加した。`FakeDocker` も実 Docker の
挙動（`--all` がない呼び出しでは dangling エントリを返さない）を模倣するよう更新し、
`test_cleanup_removes_dangling_owner_labelled_image` に実行コマンドへの `--all` 存在チェックを追加
することで、`--all` が再び失われた場合に検出できる回帰にした。

### バグ 2（実機 E2E で確認）: 一度も image 化されなかった pending 記録が journal に永久残留

build プロセスが `--load` に到達する前に死んだ場合（image が daemon に一度も作られない）、
cleanup の `docker image rm <tag>` は「No such image」で失敗し続け、`_remove_image_best_effort()`
はこれを通常の失敗と区別しなかったため、journal エントリが消し込まれず毎回 warning を出し続ける
ことが確認された。

修正: `docker_runtime_cli.reports_missing_resource()` に `kind="image"`（`"no such image:"` 検出）
を追加し、`_remove_image_best_effort()` が rm 失敗時にこれで「対象がそもそも存在しない」ことを
判定した場合は、削除成功と同等に扱って journal から消し込むようにした（in-use 等それ以外の失敗は
従来どおり次回再試行に持ち越す）。

## 追記（2026-07-26 PR レビュー）: bot レビュー指摘 7 件の反映

PR #320 に付いた CodeRabbit / codex-connector の指摘のうち採用した 7 件の対応。

1. **stale タグ削除直前の family lock 再 probe（CodeRabbit, High）**: `_partition_pending` の
   liveness 判定は manifest lock 保持下で行われるが、実際の `docker image rm` はロック解放後
   （lock 保持時間短縮のため）に走る。この間に同一 family の別プロセスがビルドを開始し得るため、
   rm ループの各タグについて `_family_build_in_progress` を再評価し、in-flight なら削除をスキップ
   するよう修正した。
2. **checkout 間調停（codex-connector, P1・部分対応）**: 別 checkout/worktree が同じ
   repository/tag を共有する場合、その family lock・pending journal はこのプロセスから見えない。
   完全な調停は別 checkout の状態を横断的に参照する仕組みが必要でスコープ外だが、部分緩和として
   rm 直前に対象タグの `docker image inspect --format {{.Created}}` を確認し、liveness 窓
   （`BUILD_TIMEOUT_SECONDS + PENDING_LIVENESS_GRACE_SECONDS`）以内に作成された image は
   スキップするようにした（`_image_recently_created`）。inspect 失敗時は安全側（スキップ）に倒す
   が、image が既に存在しない場合は保護対象がないため削除を試行する（`_remove_image_best_effort`
   が「存在しない」を成功扱いする既存挙動と整合）。
   - **既知の制限（意図的にスコープ外のまま）**: 上記 2 つの緩和策（family lock 再 probe は
     ローカルの family lock のみ、CreatedAt チェックは liveness 窓のみ）をもってしても、「別
     checkout が長時間セッション中の健全なタグを、古い pending 記録を持つ checkout が削除する」
     ケースは理論上残る（例: 別 checkout が liveness 窓を超えて `--load` 後 manifest 書き込み前に
     長時間停止した場合）。この場合、削除された側の checkout は次回 `ensure_recipe_image` 呼び出し
     で manifest drift（EV-15）として検出し自動的に再ビルドすることで自己回復する。checkout を
     横断した完全な調停（例: Docker daemon 上で共有されるロック機構の新設）は、複雑さに見合う
     実害の頻度（そもそも稀な TOCTOU）ではないと判断し、本 PR のスコープには含めない。
3. **`_REPOSITORY_RE` の registry ポート対応（codex-connector, P2）**: `registry.example:5000/team/scenario`
   形式（loop-harness の `image` config で既にサポート）が repository 検証の正規表現に一致せず
   malformed 扱いされ、crash 後の pending エントリが回収不能になっていた。`:port` を伴う先頭の
   registry host コンポーネントを許容するよう `_REPOSITORY_RE` を修正した（tag 区切りの `:` 以外で
   コロンが許容されるのはこの先頭コンポーネントのみ、という制約は維持）。
4. **build 失敗時の rm 失敗で pending を保持（codex-connector, P2）**: `_best_effort_remove_pending_tag`
   が journal エントリを先に消してから `docker image rm` を試みていたため、rm がデーモンの一時
   障害等で失敗すると再試行の手がかりが失われ、タグ付き・manifest 未登録の image が恒久的に
   残留し得た。`_remove_image_best_effort` が成功（または「存在しない」）を返した場合にのみ
   journal から消し込むよう順序を入れ替えた。
5. **走査失敗時に TTL を進めない（codex-connector, P2）**: `docker image ls` が失敗した場合も
   `last_cleanup_at` を現在時刻へ進めていたため、デーモン復旧後も最大 `CLEANUP_TTL_SECONDS`
   の間 dangling 走査が抑制されたままになっていた。走査が実際に成功した場合にのみ
   `last_cleanup_at` を更新するよう修正した。
6. **EV-36 の実装契約への整合（codex-connector, P2）**: `docs/evaluation/docker-runtime.md` の
   EV-36 が「pending journal に記録があれば TTL を無視して必ず実行する」という誤った契約を
   記載していた（実装は `_partition_pending` 後の stale 候補ベースで判定しており、live pending
   のみの場合は TTL が効く）。要件を「stale 候補がある場合」に修正し、対応テストへ
   `test_cleanup_issues_no_docker_commands_when_pending_entry_is_live_within_ttl` を追加した。
   `docs/evaluation/docker-runtime.checks.yaml` の該当エントリも追従。
7. **実行中セッションが pin した dangling image の保護（codex-connector, P1）**: 同一タグの
   再ビルドで旧 scenario/broker image が dangling 化した際、既に `ensure_recipe_image()` が
   その image_id を返し、呼び出し元（meta-harness の `scenario_docker.py`）がコンテナ起動前後で
   保持している場合、Docker 自身はそのウィンドウでは rm を拒否できない（起動前はどのコンテナも
   参照していないため）。対応として、manifest と同じディレクトリに pin 予約 ledger
   （`<manifest_stem>.pins.json`）を新設し、`ensure_recipe_image` が `EnsuredImage` を返す直前
   （3 箇所すべての return: fast reuse path・family lock 下の reuse path・fresh build path）に
   `image_id` を `IMAGE_ID_LEASE_TTL_SECONDS`（既定 6h、`CLEANUP_TTL_SECONDS` と同じ長さの
   独立した定数）の lease 付きで記録する（`_lease_image_id`）。dangling 回収時は
   `_purge_expired_pin_leases` で失効エントリを掃除しつつ有効な lease の image ID を除外対象から
   外す。
   - **既知の制限（2 と同じ節）**: この pin lease ledger は manifest/journal と同じく
     checkout ローカルであり、別 checkout がリースした image ID はこのプロセスから見えない。
     dangling 回収スコープはチェックアウト横断のまま（上記「dangling 回収は owner label 一致で
     あれば checkout/worktree 横断で削除する」の設計方針を維持）なので、別 checkout がリースした
     image ID を誤って削除する可能性は理論上残る。この場合も 2 と同様、削除された側は次回の
     `ensure_recipe_image`/コンテナ起動時に image_id 不整合として検出でき、`ensure_recipe_image`
     を再度呼び出せば `_reuse_cached_image`/再ビルド経由で自己回復する。真に checkout 横断で
     安全にするには、pin ledger 自体を dangling 回収スコープと同様に共有ファイルへ格上げする必要が
     あり、本 PR のスコープには含めない。

## 追記（2026-07-26 PR レビュー第3弾）: inspect の3値化・ledger の fail-closed 化・sidecar namespace 再設計

PR #320 に付いた bot レビュー第3弾（7件、全件採用）と、それに伴い自主的に洗い出した予防的
fail-safe 強化の記録。共通パターンは「一時的な失敗（`docker image inspect`/ファイル I/O エラー）を
『不存在』と同一視して破壊的動作（`docker image rm`・journal 消し込み・lease 無視）へ進んでいた」
ことであり、対応はすべて「不明な場合は何もしない（fail-safe）」への統一。

### 1. `docker image inspect` の3値化（found / missing / indeterminate）

`_inspect_image_id()` は「見つかった」と「不存在」を区別できても、「不存在」と「一時的な daemon
エラー・timeout」の両方を `None` として扱っていた。破壊的判断の材料にする箇所ではこの区別が
必須なため、`_inspect_image_id_with_confidence()`（`tuple[str | None, bool]`。`bool` は
indeterminate か否か）を新設し、以下 3 箇所を fail-safe化した:

- **build 前の `pre_build_image_id` 取得**（`ensure_recipe_image`）: 事前 inspect が indeterminate
  だった場合、build 失敗時の cleanup（`_best_effort_remove_pending_tag`）は「このタグを今回の
  build が変更した」と証明できないため、削除を一切行わない。
- **build 失敗時の「現在の image_id」再 inspect**（`_best_effort_remove_pending_tag`、予防的強化）:
  こちらが indeterminate な場合も同様に、journal の消し込み・復元のどちらも行わず、
  pending エントリをそのまま次回の cleanup に委ねる（中途半端な journal 操作を避ける）。
- **`_pending_entry_is_resolved` → `_pending_entry_resolution`**（`bool | None` へ変更）:
  resolved 判定の inspect が indeterminate な場合は `None` を返し、`_partition_pending` はその
  エントリを resolved にも stale 候補にも進めず、そのラウンドでは素通りする（従来は
  `_inspect_image_id` が `None` を返すと unresolved 扱いとなり、そのまま stale 判定へ流れて
  誤削除し得た）。

### 2. build 前 inspect の indeterminate 時は既存タグを削除しない、かつ再試行時に pending 記録を保持

`_record_pending_build()` は上書き前の既存エントリを返すよう変更し（`previous_pending_entry`）、
`_best_effort_remove_pending_tag()` は「このタグを今回の build attempt が実際に mutate したか」
（`tag_was_mutated_by_this_attempt`。pre-build inspect が indeterminate なら常に `False`）を
判定してから:

- mutate した（かつ削除成功）→ 今回の journal エントリを消し込む。
- mutate していない（別 checkout の既存タグに触れていない、または pre-build inspect が
  indeterminate）→ 削除は一切行わず、`previous_pending_entry` があればそれを journal へ復元する
  （なければ今回のエントリを消し込む）。

これにより、「前回プロセスが `--load` 後に停止し pending 記録を残した状態で、同じ recipe を
liveness 窓内に再試行し、その新しい試行がタグ未変更のまま失敗する」ケースでも、前回の
所有権証明（旧 image の pending エントリ）が新しい試行の失敗処理に巻き込まれて消えることはない。

### 3. pin ledger は読取失敗時に fail-closed

`_load_pin_ledger()` は `_load_pending_journal()` と異なり、ファイル不存在（正常な空状態）と
既存ファイルの読取/JSON 解析失敗を区別するよう変更した。後者は `DockerImageError` を送出し、
`_cleanup_stale_owned_images_best_effort()` の outer try/except が cleanup ラウンド全体を中止する。
pending journal は「不読 = 何もしない（安全側）」で十分だが、pin ledger は「不読 = lease なし
= dangling 削除に進む（危険側）」になってしまうため、非対称な扱いが必要だった。

### 4. stale タグ削除直前の owner label 検証

`_partition_pending`/`_hold_family_lock_if_free` の各種 liveness チェック（family lock・
CreatedAt）を通過したタグでも、journal は自己申告の `docker_label`/`digest` しか持たないため、
クラッシュ後に無関係な image へ retag された場合を検出できなかった。削除直前に
`docker image inspect --format '{{json .Config.Labels}}'` で実 image の owner label
（`<docker_label>=image`）と recipe digest label（`<docker_label>.recipe-sha256=<digest>`）を
確認する `_image_owner_label_matches()` を追加し、一致しない場合は削除しない（EV-34 の
「pending 記録と owner label の両方による所有証明」契約を削除時点でも維持）。ただし image が
**確認された不存在**の場合はこの限りでなく削除へ進む（scenario 2: build が `--load` 前に死んで
タグが一度も作られなかったケースを、`_remove_image_best_effort` の既存の「不存在 = 成功」処理へ
橋渡しするため）。

### 5. sidecar namespace を専用サブディレクトリへ再設計（P1）

従来の `<manifest_stem>.pending.json`/`<manifest_stem>.pins.json`（manifest と同じディレクトリの
兄弟ファイル）は、**別の** policy が同じディレクトリ内で `manifest_path`/`lock_path` に偶然
同名を設定していた場合に衝突しうる。この衝突は 1 つの policy 内のパスしか比較しない
`_validate_distinct_cache_paths` では検出不能であり、後勝ちの `_atomic_write_json`（temp-file +
`os.replace`）が相手 policy の manifest を journal/ledger の JSON で上書きしてしまう。

対応として、sidecar を `<manifest_path 全体>.sidecars/` という**専用サブディレクトリ**へ移動した
（`_sidecar_dir()`。`PENDING_JOURNAL_SUFFIX`/`PIN_LEDGER_SUFFIX` 定数は廃止し
`_SIDECAR_DIR_SUFFIX`/`_PENDING_JOURNAL_FILENAME`/`_PIN_LEDGER_FILENAME` に置き換え）。
ディレクトリパスは、他 policy が自身の `manifest_path`/`lock_path`（ファイル）として設定し得る
名前と構造的に衝突しない。既存の `_validate_distinct_cache_paths`（policy 内の manifest/lock と
sidecar パスの相互比較）はロジック変更なしで新方式に自動追従する（この検証は依然として
「1 policy 内」の衝突しか検出できない点は変わらないため、上記の**別 policy との**衝突は
namespace 再設計そのもので構造的に防ぐ、という役割分担になる）。本 PR 内で新設したファイルの
namespace 変更のため、後方互換の移行処理は不要と判断した。

### 予防的整合性掃除

- 上記 1〜4 は文字どおりの bot 指摘（7件中5件）に対する修正だが、`_best_effort_remove_pending_tag`
  内の「現在の image_id」再 inspect（bot 指摘外）にも同型のリスクを発見し、同じ fail-safe を
  自主的に適用した（上記「1」参照）。
- `docker_runtime_image.py` 内の他の inspect 呼び出し（`_reuse_cached_image`・
  `_load_valid_manifest` の `verify_digest` 検証・`_ensure_immutable_image`）も洗い出したが、
  これらは inspect 失敗時に「再ビルド」または「エラー終了」に倒れるだけで rm/journal 消し込み/
  lease 無視のような破壊的操作には繋がらないため、変更不要と判断した。
- `_load_pending_journal`（pin ledger と異なり）は読取失敗を「何もしない」方向にしか作用させない
  （stale 候補が減るだけで、誤って何かを消すことはない）ため、pin ledger と同じ fail-closed 化は
  意図的に見送った（安全性のために cleanup を過剰に停止させるのは非対称なコストになるため）。
- ドキュメント側は `docs/design/meta-harness-detailed.md`・本 ADR 冒頭の「所有権 → 検証済み image
  ID の pin」節・「## 影響」節に残っていた「`ensure_images()` が `trusted_image_ids` へ登録する」

  変更していない。

## 追記（2026-07-26 PR レビュー第4弾）: lease 書き込みの fail-closed 化・journal 破損の隔離・既知の制限の明記

push 前ドライアウトレビュー（adversarial・code-reviewer・Codex CLI の 3 本）の統合指摘に対する
対応。前弾までで確立した「fail-safe = 破壊的動作へ進まない」方針を、書き込み系の失敗（lease
記録・journal 破損）と、意図的に対応しないと決めたスコープ外事項の明文化にも拡張した。

### 1. pin lease 書き込み失敗は fail-closed（best-effort ではなく例外伝搬）

> **この決定は第5弾追記で上書きされた**（可用性回帰: 健全な image がある状態で lease 書き込みの
> みが失敗し続けると `ensure_recipe_image` が恒久的に失敗し続ける）。詳細は「## 追記（2026-07-26
> PR レビュー第5弾）」§1 を参照。以下は当時の決定の記録として残す。

`_lease_image_id()` はこれまで書き込み失敗を warning ログのみで握りつぶし、lease なしの
`EnsuredImage` を呼び出し元へそのまま返していた。これは本 ADR が既に確立した「読み取り失敗時の
fail-closed」（pin ledger の§3参照）と非対称であり、書き込み失敗（`ENOSPC` 等）が起きた場合、
保護されていない image_id を呼び出し元に渡してしまい、直後の同一タグ再ビルドによる dangling
cleanup がそれを削除し得た。best-effort で握りつぶすのではなく `DockerImageError` を伝搬させ
`ensure_recipe_image()` 自体を失敗させるよう変更した。書き込み失敗を引き起こす環境
（ディスク枯渇・権限異常）は既に何らか劣化しており、「保護なしの image を静かに返し、後から
消えるかもしれない」よりも「今すぐ失敗を表面化する」方を優先する判断である。

### 2. pending journal の破損ファイルは隔離（quarantine）してから空扱いに復帰

`_load_pending_journal()` は既存ファイルの JSON parse に失敗した場合、これまで単に空の journal
として扱っていた。この直後の呼び出しはほぼ確実に read-modify-write（`_record_pending_build`／
cleanup の journal 更新）であり、壊れたファイルが実は**他の family の有効なエントリ**を含んで
いた場合、空から再構築した journal で上書きすると、その有効なエントリを永久に破壊してしまう。
対応として、parse に失敗した既存ファイルは `os.replace` で `<path>.corrupt-<timestamp>` へ退避
（証拠保全）してから、空の in-memory journal で処理を継続するようにした（`_quarantine_corrupt_sidecar`）。
退避自体が失敗した場合（権限異常等）も best-effort とし、警告ログのみで空 journal による続行を
妨げない。

### 3. 既知の制限として受容し、コード変更しない事項

以下 2 点は Codex CLI レビューで指摘されたが、設計上のトレードオフとしてスコープ外のまま受容し、
コード変更は行わない。

- **pin ledger は checkout ローカルであり、daemon 全体で共有されない（Codex P1-3、棄却）**:
  pin lease ledger（`<manifest_path>.sidecars/pins.json`）は本 ADR の 2 弾目追記で既に「checkout
  ローカル」である旨を明記済みの制限を踏襲する。ledger を daemon-global（例えば `/tmp` 配下の
  共有ファイルや Docker ラベルそのものへの lease 記録）へ格上げすれば、別 checkout がリースした
  image_id もこのプロセスから可視化できるが、複数 checkout 間でファイルロックの取り合いが発生し
  読み取りパスにも常にファイル I/O コストが乗る設計変更になる。dangling 回収は「owner label 一致
  であれば checkout/worktree 横断で削除する」設計（2 弾目追記参照）を維持しており、別 checkout の
  lease を見落として誤って削除しても、削除された側は次回の `ensure_recipe_image`/コンテナ起動時に
  image_id 不整合として検出し自己回復する。この自己回復性がある以上、daemon-global 化のコストに
  見合う実害の頻度ではないと判断し、本ラウンドでも見送る。
- **owner label 確認から `docker image rm` までの残存 TOCTOU 窓（Codex P1-6、部分受容）**:
  同一 checkout 内では、stale タグ削除ループが `_hold_family_lock_if_free` で対象 family の build
  lock を確認から削除完了まで保持し続けるため、この窓は構造的に閉じている（第3弾追記の対策1参照）。
  一方、別 checkout がまさにこの窓（owner label 一致を確認した直後、`docker image rm` が実行される
  直前）で同じタグを retag した場合、その別 checkout の変更は検出できない。この cross-checkout の
  残存窓は、上記「pin ledger が checkout ローカル」であることの帰結であり、対応も同じ理由（自己
  回復性がある低頻度 TOCTOU に daemon-global な調停機構を追加するコストは見合わない）で見送る。
  同一 checkout 内の TOCTOU（本ラウンドの fix A で追加した、build 失敗パスへの liveness window /
  owner label 保護）とは区別して扱うべき、別種の残存リスクとして記録する。

## 追記（2026-07-26 PR レビュー第5弾）: lease 書き込みを best-effort へ差し戻し・owner label 確定ミスマッチの journal 解消・keep_generations の一時超過を明記

push 前最終デルタ検証（adversarial・code-reviewer・Codex CLI）で High 1 件・Medium 2 件が判明した、
push 前最後の修正ラウンド。

### 1. pin lease 書き込みは fail-closed から best-effort（fail-open）へ差し戻し（High）

第4弾追記§1 で `_lease_image_id()` の書き込み失敗を `DockerImageError` 伝搬に変更したが、これは
可用性回帰を生む: build が成功し manifest への登録も完了した**後**に、lease 書き込みだけが
ディスク逼迫や `.sidecars/` の権限異常で失敗し続けると、健全な image が既に存在するにもかかわらず
`ensure_recipe_image()` の呼び出し（キャッシュヒットの再利用パスを含む 3 箇所すべての return
直前）が恒久的に失敗し続ける。これは pin ledger の**読取**側 fail-closed（§3、保護情報なしでは
削除しない）とは非対称な問題であり、書き込み失敗の帰結が全く異なる:

- **読取失敗**（既存 ledger が壊れている/読めない）を fail-open（空扱い）にすると、"保護なし" が
  即座に危険側（削除可能）へ倒れるため fail-closed が正しい。
- **書き込み失敗**を fail-closed にすると、"保護なし" ではなく "ensure 全体の恒久停止" という、
  読取失敗よりはるかに広範囲かつ深刻な障害モードになる。この時点の image は tagged（manifest 登録
  済み、または再利用検証済み）であり、lease はあくまで「この*同一 checkout* が同じタグを再ビルド
  して dangling 化させた場合の保護レイヤー」に過ぎない。lease が書けなくても image 自体は消えない。

このため、`_lease_image_id()` 自体は例外を送出する実装のまま残し（他の将来の呼び出し元が
fail-closed を必要とする可能性に備える）、`ensure_recipe_image()` からの 3 箇所の呼び出しを
`_lease_image_id_best_effort()`（try/except DockerImageError → warning ログ + 処理継続）経由に
差し替えた。読取側の fail-closed（§3）は変更していない。書き込み失敗の残存リスクは
「このセッション中に同一タグが再ビルドされ dangling 化した場合に、その世代が lease で保護され
ない」ことのみであり、これは pin lease が本来想定している防御範囲（同一 checkout 内の同タグ再
ビルドのウィンドウ）の外側まで広がるものではなく、次に lease 書き込みが成功すれば自然に解消する
（自己回復）。呼び出し箇所ごとにインラインコメントで本判断の要旨を明記し、bot レビューでの
再指摘を予防した。

### 2. owner label の確定ミスマッチで journal entry の永久残留を解消（Medium）

`_image_owner_label_matches()` は「削除してよい」（labels 一致、または確認された不存在）と
「削除しない」（不一致・inspect 失敗の両方）の2値しか返していなかった。このため、別 checkout に
tag を奪われた（＝ owner label が確定的に不一致）場合と、inspect が一時的に失敗して判定不能
（indeterminate）な場合が区別できず、いずれも「削除しない」経路へ丸められ、失敗パス
（`_best_effort_remove_pending_tag`）・stale cleanup（`_cleanup_stale_owned_images` の
`_partition_pending` 経由）の両方で journal entry が永久に消し込まれず残留し続けるバグがあった。

対応として、`_image_owner_label_matches()` を `bool | None` の3値に変更した:

- `True`: labels 一致、または確認された不存在（従来どおり削除を試行）。
- `False`（新設）: inspect が**成功**し、well-formed な labels object を返したが、値が
  定義上一致しない（**確定ミスマッチ**）。この tag はもはやこの checkout の所有物ではないと
  確定できるため、image は一切削除しないが、この checkout 自身の journal entry は消し込む
  （もし自分のビルド残骸が別のどこかで dangling 化していれば、label 経由の dangling sweep が
  独立に回収するため安全）。
- `None`: inspect 失敗（daemon 一時障害・タイムアウト）または output の parse 失敗。従来どおり
  image・journal entry のいずれも触らず、次回の再評価に委ねる。

失敗パス（`_best_effort_remove_pending_tag`）は `False` の場合に削除をスキップしつつ journal
pop 処理へフォールスルーするよう変更し、stale cleanup（`_cleanup_stale_owned_images`）は `False`
の tag を `removed_stale_tags`（journal 消し込み対象。ただし `docker image rm` は呼ばないため
`removed_count` は増やさない）へ追加するよう変更した。indeterminate（`None`）の扱いは変更していない
（両パスとも一切触らない）。

### 3. keep_generations は pin lease 保護中は一時的に超過し得る（Medium、ドキュメントのみ）

第4弾追記の fix C（`_prune_image_family` の pin-lease 考慮）により、有効な pin lease を持つ世代は
`keep_generations` の保持数を超過していても prune 対象から除外される。これはコード変更ではなく、
`keep_generations` の契約が「常に保持数以下」ではなく「lease で保護されていない世代のみを保持数まで
絞る」という意味であることの明文化である。超過は最大 `IMAGE_ID_LEASE_TTL_SECONDS`（既定 6h）の
窓に限られ、lease が期限切れになれば次回以降の prune 呼び出しで自然に解消する（自己回復であり、
追加の TTL 管理や強制 prune は導入しない）。`docs/evaluation/docker-runtime.md` EV-16 と対応する
`docker-runtime.checks.yaml` の notes にこの契約を追記した。
