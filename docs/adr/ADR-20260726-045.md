# ADR-20260726-045: 永続イメージライフサイクルの脅威モデル再評価と異常系 stale cleanup の追加

- **ステータス**: proposed
- **日付**: 2026-07-26
- **決定者**: （人間承認待ち）

## コンテキスト

Issue #231 は「meta-harness の反復実行で OrbStack の Docker image / BuildKit cache が肥大化する」
不具合として起票された。主因は `scenario_docker_cli.py` の `_ensure_image()` が `auto_build` 時に
毎回 `docker build --no-cache -t <固定タグ>` を実行し、旧イメージをタグ上書きで dangling 化させ、
かつ BuildKit の build cache を一切 prune していなかったことにある（`docs/design/loop-harness-isolation.md`
§5.1）。

この根本原因は、Issue #250 の設計・実装（PR #306）で先行して解消された。`packages/docker-runtime/lib/docker_runtime_image.py`
の `ensure_recipe_image()` が、recipe-addressed タグ（`{repo}:sha-{digest[:12]}`）・ディスク manifest
＋ `fcntl` ロックによるプロセス間再利用・owner label 限定の世代 prune（既定 keep 3）・専用 buildx
builder・build 成功時の BuildKit cache GC（既定 168h / 10g）を備えた永続イメージライフサイクルへ
scenario/broker image の管理を移行した（`docs/evaluation/meta-harness.md` EV-94〜97）。`--no-cache`
build は廃止され、meta-harness と loop-harness（`packages/loop-harness/lib/loop_docker_image.py`）が
同一の共有モジュールを namespace 注入で利用する構成になっている。

この移行は実装が先行し、ADR としての追認・脅威モデルの再評価が行われていなかった。加えて、
実装後に次の異常系ギャップが残っていることが判明した:

- **シナリオ 2（クラッシュ中断）**: `docker buildx build --load` が成功した直後、manifest への
  書き込み前にプロセスが SIGKILL 等で終了すると、そのタグは manifest に未登録のまま Docker 上に
  残り続ける。次回以降の `ensure_recipe_image()` は manifest に記録がないため再利用も削除も行わず、
  リークしたイメージが蓄積する。
- **シナリオ 3（同一タグへの再ビルド）**: 同一 recipe hash への再ビルドでタグを置き換えた場合、
  置き換えられた旧イメージは dangling（`<none>:<none>`）化するが、`_prune_image_family()` は
  タグ付きイメージだけを走査するため dangling image を回収しない。

本 ADR はこれらを記録し、(1) `--no-cache` から recipe-addressed reuse への移行が意図した保証を
再評価し、(2) 上記 2 シナリオに対する pending journal ベースの stale cleanup 設計を追認し、(3)
意図的にスコープ外とした事項を制限事項として明記する。

## 検討した選択肢

### 脅威モデルの再評価: `--no-cache` が担っていた保証は何だったか

`--no-cache` 方式は「毎回ゼロからビルドする」ことで以下を暗黙に保証していた:

1. **鮮度**: ビルドコンテキストの変更が必ず新しいイメージに反映される（キャッシュ汚染がない）。
2. **単純な所有権**: 固定タグを直接上書きするため、「今 Docker 上にあるそのタグ = 今回ビルドした
   もの」という前提が常に成立する（プロセス間の再利用を考慮しなくてよい）。

recipe-addressed reuse へ移行すると、この 2 点は形を変えて別の保証で代替される必要がある:

1. **鮮度 → recipe hash**: `recipe_hash()` がビルドコンテキストの内容・`--build-arg`・
   `docker_label`・platform/target の全てをハッシュ化し、タグに埋め込む
   （`{repo}:sha-{digest[:12]}`）。内容が変われば別タグになるため、古い内容のイメージを
   「今回のビルドの結果」として誤って再利用することは構造的にない。
2. **所有権 → 検証済み image ID の pin**: `ensure_recipe_image()` は manifest 記録の `image_id` が
   現在の Docker 上の実体と一致することを `docker image inspect` で確認してから返す。さらに
   `scenario_docker_cli.ensure_images()` はこの検証済み ID を `ImageCache.trusted_image_ids` に
   登録し、以降の `image_id()` 参照（container 起動、`image_pin` 照合）はタグの再 inspect を
   行わない。これにより、共有タグに対する並行 retag（他プロセスの同時ビルド等）が発生しても、
   ensure が確保した image と異なる image を誤って起動対象にする TOCTOU を防ぐ。

この対比により、`--no-cache` の 2 つの暗黙保証はいずれも recipe-addressed 方式でも成立している
と判断する。一方で `--no-cache` 方式には存在しなかった新しいリスク（プロセス間で状態を共有する
ことに由来する「manifest と Docker 実体の乖離」）が生じるため、それに対する stale cleanup が
別途必要になる。

### 選択肢 A: pending journal による所有証明 + opportunistic cleanup（採用）

- 概要: manifest とは別ファイル（`<manifest_stem>.pending.json`）に、ビルド開始前にタグを
  「in-flight」として記録する。ビルド成功と manifest 書き込みが完了した時点でエントリを消し込む。
  `ensure_recipe_image()` の**冒頭**（キャッシュヒットで再利用するだけの呼び出しも含む）で、
  この journal をもとに stale なタグ・owner label 付き dangling image を best-effort に回収する。
- メリット:
  - manifest のスキーマを変更しない（journal は sidecar として分離）。
  - 「このプロセスが今ビルドしようとしているタグ」という所有証明を、manifest 書き込み前の
    区間でも持てるため、クラッシュ後も次回呼び出しで確実に検出できる。
  - dangling image の回収は owner label のみで判定でき、pending journal の記録有無に関わらず
    安全に削除できる（tag を持たないため他所有者と衝突しようがない）。
  - 呼び出しのたびに実行されるため、専用の定期ジョブを新設する必要がない。
- デメリット:
  - 呼び出しのたびに `docker image ls` 等を実行するコストが発生するため、TTL
    （`CLEANUP_TTL_SECONDS`、既定 6h）で間引く必要がある。pending journal に記録が残っている
    場合は TTL を無視して必ず実行し、リークの検出を遅らせない。

### 選択肢 B: 定期外部ジョブによる cleanup（不採用）

- 概要: `ensure_recipe_image()` とは独立した cron 相当のプロセスが stale image を定期的に走査・
  削除する。
- デメリット: meta-harness/loop-harness はどちらも「オンデマンドの CLI プロセス」であり、
  常駐プロセスを前提とする設計は ADR-20260712-035 が確立した「常駐させない」方針と矛盾する。
  新しい実行主体・スケジューリング機構を追加するコストも大きい。

### 選択肢 C: manifest 書き込みをビルドより先に行う（不採用）

- 概要: `--load` の前に manifest へ「ビルド中」フラグ付きでエントリを先行登録し、成功後にフラグを
  下ろす。
- デメリット: manifest のスキーマ変更が必要になり、`ManifestEntry` を読む既存ロジック
  （cache-hit 判定、prune 対象抽出）がすべて「ビルド中」状態を意識する必要が生じる。所有証明の
  責務を manifest に持たせると、他 family の再入可能な短時間ロックとの整合も複雑化する。
  pending journal を別ファイルに分離した方が既存ロジックへの影響が小さい。

## 決定

**選択肢 A（pending journal + opportunistic cleanup）を採用する。**

1. `_record_pending_build()` は `_build_image()` 呼び出しの**前**に、per-family build lock を
   保持した状態でタグを pending journal（`digest` / `family` / `repository` / `docker_label` /
   `started_at` を記録）へ書き込む。
2. ビルド成功・manifest 書き込みが完了した直後（同じロック区間内）に `_clear_pending_entry()` で
   journal からエントリを消し込む。
3. ビルド失敗時（`_build_image()` 以降の例外）は `_best_effort_remove_pending_tag()` が journal
   エントリと当該タグを回収してから、元の例外をそのまま re-raise する（cleanup の失敗が build
   失敗のエラーメッセージを上書きしない）。
4. `_cleanup_stale_owned_images_best_effort()` は `ensure_recipe_image()` の**冒頭**（再利用パス
   を含む）で常に呼び出され、(a) pending journal に残ったまま manifest に未登録のタグ、
   (b) owner label 付きの dangling image、を回収する。owner label が一致しない、または pending
   journal に記録のないタグ付きイメージ（他プロジェクトが同じ repository/label を共有した
   ビルド）は削除対象にしない。
5. cleanup 自体は全域 best-effort とし、`docker image rm` の失敗は warning に留めて次回呼び出しに
   持ち越す。cleanup 内の予期しない例外も `ensure_recipe_image()` 全体を失敗させない
   （`_cleanup_stale_owned_images_best_effort` の outer try/except）。
6. cleanup の回収数・BuildKit cache 使用量を INFO ログへ出力し、観測性を確保する
   （既存の hard-fail する build path 側の `_prune_buildkit_cache` の挙動は変更しない）。

## 影響

- `packages/docker-runtime/lib/docker_runtime_image.py` は 699 行から 1050 行に拡張された
  （pending journal の読み書き・stale cleanup・ログ出力）。manifest のオンディスクスキーマは
  変更していない。
- `packages/meta-harness/lib/scenario_docker_cli.py::ensure_images()` は `ensure_recipe_image()`
  が返した検証済み `image_id` を `ImageCache.trusted_image_ids` に登録するようになり、下流の
  `image_id()` 参照が ensure 済みの ID を再利用する（`EnsuredImage` 呼び出しシグネチャは
  後方互換のまま）。
- meta-harness・loop-harness はいずれも `packages/docker-runtime/lib/docker_runtime_image.py` を
  共有しているため、本 cleanup は両方の harness に等しく適用される。Issue #231 本文は
  「loop-harness は Docker build を実行しない」としているが、これは現在不正確である。
  `loop_docker_image.py`（`DOCKER_LABEL = "ai.orchestra.loop-harness"`、専用 builder
  `loop-harness-builder`）は meta-harness と同じ `ensure_recipe_image()` を呼び出しており、
  namespace（label・manifest/lock パス・builder 名）は独立しているが cleanup ロジックは共通基盤
  由来で自動的に適用される。監査結果の詳細は `docs/design/loop-harness-isolation.md` §5.4 に記録する。

### 既知の制限（意図的にスコープ外）

- **BuildKit cache の失敗時蓄積**: build 失敗が連続した場合の BuildKit cache 蓄積は、本 ADR の
  cleanup では扱わない。次回 build 成功時に既存の `_prune_buildkit_cache()`（age-based prune +
  size 上限超過時の無条件 prune フォールバック）が上限を強制するため、失敗が続いても次の成功時に
  自己回復する。失敗時点での即時 prune は追加しない（build 失敗の頻度・原因調査を優先すべきで、
  cleanup コストを毎失敗ごとに払う設計にはしない）。
- **docker context 往復による再 build churn**: manifest は 1 recipe あたり 1 つの `image_id` しか
  保持できないため、`desktop-linux` ⇔ `orbstack` のように daemon（docker context）を切り替える
  たびに、直前の manifest 記録が新しい daemon 上では drift として扱われ再ビルドが走る。本 ADR の
  cleanup はこの再ビルド自体で生じたリーク（旧 daemon 側の孤立イメージ等）を回収する対象では
  ない点に注意（孤立イメージは切替先の daemon には元々存在しない）。churn そのものは既知の制限
  として受容し、daemon 単位で manifest を分割する等の対応は将来のフォローアップとする。
- **recipe-addressed の限界**: `recipe_hash()` が計算する context hash はファイル内容のみを
  対象とし、symlink の有無や file mode（実行ビット等）の変化を考慮しない。依存関係（base image
  以外の外部依存）の完全な pin も本 ADR のスコープには含まない。

## 追記（2026-07-26）: pending journal 判定のレース修正

レビューで、上記「決定」§4 の初期実装に Critical 1 件・High 1 件の指摘が入った。

### 問題

`_cleanup_stale_owned_images()` は manifest lock のみを保持して実行され、`_record_pending_build()`
（build 開始前の記録）から manifest 書き込みまでの区間 —— つまり **別プロセスがまさにその
family を build 中の区間** —— にある pending エントリと、クラッシュ残骸によるエントリを
区別していなかった。`_partition_pending()` は「manifest に未登録 = stale」としか判定しておらず、
journal に記録済みの `started_at` はどこからも参照されていなかった。

このため、ある label を共有する複数 family（例: meta-harness の `scenario` build 中に `broker` の
`ensure_recipe_image()` が呼ばれる、または同一 family への同時呼び出し）が実行されている最中に、
その in-flight タグを stale と誤判定して `docker image rm` してしまう可能性があった。`_tag_latest()`
より前に消えれば偽陽性の build 失敗、後であれば不要な再ビルドを誘発する。

さらに、pending journal に**何らかの**エントリが存在するだけで TTL を無視して毎回 cleanup 一式
（`docker image ls` + `buildx du`）を実行していたため、build が継続している間はホット・リユース
パスの呼び出しすべてが cleanup コストを払うことになっていた（TTL 本来の「間引き」目的が
並行 build 時に機能しない）。

### 対策（多層防御）

1. **family lock による liveness チェック（主判定）**: 削除候補ごとに `entry["family"]` の
   per-family build lock（`_family_lock_path()`）を非ブロッキング（`LOCK_EX | LOCK_NB`）で
   取得試行する（`_family_build_in_progress()`）。取得できなければ「build 中」とみなしスキップ、
   取得できれば即座に解放して削除候補に進める（build はこのロックを区間全体で保持するため、
   非ブロッキング取得成功 = in-flight build なしを意味する）。ロックの probe 自体が manifest
   lock を保持したまま行われるため、非ブロッキングであることが必須（ブロッキングにすると、
   同じ manifest lock を待っている build 側の `_record_pending_build()` とデッドロックし得る）。
2. **`started_at` の猶予期間（副次防御）**: family lock probe が何らかの理由で誤って「解放中」と
   判定した場合に備え、`started_at` から `BUILD_TIMEOUT_SECONDS + PENDING_LIVENESS_GRACE_SECONDS`
   （既定 15分 + 5分）未満のエントリは無条件でスキップする（`_pending_entry_is_recent()`）。
   `started_at` がパース不能な場合も安全側（= in-flight とみなす）に倒す。
3. **stale 候補ゼロ時の TTL 早期リターン**: pending の存在有無ではなく、上記 2 チェックを経た
   **stale 候補が 1 件でもあるか**、または TTL が経過しているかのいずれかでのみ `docker image ls`
   等を実行する。stale 候補ゼロかつ TTL 未経過なら Docker コマンドを一切発行せず即座に return する
   （journal の resolved エントリ消し込みのようなファイルI/Oのみの後処理は行ってよい）。
4. **lock 保持時間の短縮**: 削除候補の確定（journal 読み込み + `docker image ls`）は manifest lock
   保持下で行うが、`docker image rm` のループ自体は lock を解放したあとに実行し、成功した
   エントリの消し込みだけ再度短時間ロックして行う。
5. **journal 由来タグの形式検証**: `docker image rm` に渡す前に、`recipe_tag()` が生成し得る形式
   （`<repository>:sha-<12桁hex>`）と厳密に一致するかを検証する（`_is_removable_tag_reference()`）。
   一致しないエントリは journal から消し込むのみで、Docker コマンドには一切渡さない。

dangling image（owner label 付き・タグなし）の回収ロジック自体（決定§4(b)）は本追記の対象外とする。
本追記ではレースの修正のみを行い、dangling 回収の判定条件（owner label 一致のみで削除可）は
変更していない。dangling 回収のスコープ（checkout/worktree 横断で削除してよいか）についての
最終判断は次の追記（2026-07-26 E2E 追記）で確定した。

## 追記（2026-07-26 E2E）: dangling 回収のスコープ確定、および実機検証で判明した2件のバグ修正

### dangling 回収は owner label 一致であれば checkout/worktree 横断で削除する（意図した動作）

上記「決定」§4(b) の dangling image 回収は、`main_root` や checkout/worktree では一切スコープせず、
`recipe.docker_label` の一致のみを削除条件とする。これは意図的な設計であり、以下の根拠による:

1. **dangling はタグ不在のため、そもそもどの checkout からも再利用不能な純粋なゴミである**。
   `ensure_recipe_image()` のキャッシュヒット判定はタグ（`{repo}:sha-{digest[:12]}`）を起点に
   行われる。dangling image（`<none>:<none>`）は定義上タグを持たないため、削除しても「別の
   checkout が参照していたタグを奪う」ことは構造的に起こらず、他 checkout に再ビルドを誘発しない。
2. **実行中コンテナが参照する image は Docker 自身が rm を拒否する**。仮に何らかの理由で dangling
   image が実行中コンテナの base として参照されていても、`docker image rm` は
   `image is being used by a running container` 相当のエラーで失敗し、本実装は best-effort として
   それを警告に留めて次回に持ち越す（既存の `_remove_image_best_effort` の失敗時挙動）ため、
   誤って稼働中の資産を破壊することはない。
3. **`main_root` 等で checkout 固有にスコープする代替案は不採用**。dangling image はタグを持たず
   `main_root` のようなメタデータとも紐付いていないため、スコープを絞るには pending journal と
   同様の「どの checkout が作ったか」を記録する仕組みを新設する必要があり、タグ自体は
   `manifest_path`/`lock_path` を共有する複数 checkout 間で再利用される設計（Issue #250）と
   衝突する。スコープを誤って狭めると、他 checkout が正当に持つはずの dangling 回収機会を奪い、
   ゴミの蓄積を許すリスクの方が大きいと判断した。

### バグ 1（実機 E2E で確認）: `docker image ls` に `--all` がなく dangling 回収が常に no-op

`_list_label_owned_images()` の `docker image ls --filter label=...` に `--all`/`-a` が付いておらず、
実 Docker では `-a` なしの `docker image ls` は dangling を**デフォルトで除外**するため、
`_dangling_image_ids()` は常に空リストを受け取り、上記の dangling 回収パスが実機で一度も発火しない
ことが OrbStack 上の E2E で確認された。単体テストの `FakeDocker` は `-a` の有無を区別せず常に
`image_ls_output` をそのまま返していたため、この欠落を検出できていなかった。

修正: `_list_label_owned_images()` のコマンドへ `--all` を追加した。`FakeDocker` も実 Docker の
挙動（`--all` がない呼び出しでは dangling エントリを返さない）を模倣するよう更新し、
`test_cleanup_removes_dangling_owner_labelled_image` に実行コマンドへの `--all` 存在チェックを追加
することで、`--all` が再び失われた場合に検出できる回帰にした。

### バグ 2（実機 E2E で確認）: 一度も image 化されなかった pending 記録が journal に永久残留

build プロセスが `--load` に到達する前に死んだ場合（image が daemon に一度も作られない）、
cleanup の `docker image rm <tag>` は「No such image」で失敗し続け、`_remove_image_best_effort()`
はこれを通常の失敗と区別しなかったため、journal エントリが消し込まれず毎回 warning を出し続ける
ことが確認された。

修正: `docker_runtime_cli.reports_missing_resource()` に `kind="image"`（`"no such image:"` 検出）
