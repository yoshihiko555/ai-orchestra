# ADR-20260728-046: 蓄積型ログの root worktree 解決と配置規約

- **ステータス**: accepted
- **日付**: 2026-07-28
- **決定者**: yoshihiko
- **関連**: ADR-20260612-025（fail-logs 新設・記録フェーズ）, ADR-20260630-027（fail-logs 活用フェーズ）, `packages/audit/hooks/event_logger.py`（root worktree 解決の先行実装）

## コンテキスト

本リポジトリおよび導入プロジェクトは git worktree 運用が多く、gitignore された蓄積型ログ
（fail-logs の `failures.jsonl`、skill-evolution の metrics）が worktree 内の `.claude/` に
書かれるため、worktree 削除とともに消失する。ADR-20260612-025・ADR-20260630-027 が設計した
「記録 → 集計 → 再発サマリー注入」の学習ループは、worktree をまたいだ蓄積があって初めて機能する
前提だったが、実際には worktree ごとにログが分断され、この前提が満たされていなかった。

audit パッケージのみ `event_logger.py` の `_resolve_root_worktree()` / `_resolve_log_root()`
（`git rev-parse --path-format=absolute --git-common-dir` を用いる）で root worktree への集約を
既に実装しており、root に 213 セッション分の蓄積を確認した。fail-logs / skill-evolution は
この対応をしておらず、同じリポジトリ内でパッケージ間の挙動が非対称になっている。

加えて、ログ機構の正本ドキュメント `docs/reference/logging.md` は 2026-04-14 を最後に更新が
止まっており、上記の非対称を含む実態からドリフトしている。

## 検討した代替案

### 代替案 1: fail-logs / audit / skill-evolution の 3 系統ログを 1 ファイルへ統合（却下）

ADR-20260612-025 は fail-logs と quality-gates の捕捉重複について目的・スキーマが異なるため
意図的に許容すると裁定しており、系統ごとの分離を前提とした設計が既に確立している。3 系統の統合は
この前提を覆すが、それに見合う利点がない。root 解決の話は蓄積先ディレクトリの問題であり、ログの
意味的統合とは独立した論点のため、統合の動機にならない。

### 代替案 2: config で `logs_dir` に root worktree パスを直接指定可能にする（却下）

利用者が config 経由で任意の絶対パス（project_dir 外）を `logs_dir` として指定できるようにする案。
既存のパストラバーサルガード（`resolve_path_within`、ADR-20260630-027 §8 参照）を弱めることになり、
設定経由での任意パス書き込みリスクを再導入する。root 解決は hook 内部の git コマンドで完結でき、
利用者に新しい設定項目を追加する必要がないため不採用。

### 代替案 3: audit の共通関数載せ替えを本 ADR の実装と同時に実施（却下）

`_resolve_root_worktree()` / `_resolve_log_root()` を `packages/core/hooks/hook_common.py` へ
抽出したあと、audit 本体もそれを使うように置き換える案。挙動は同一になる想定だが、稼働中の監査ログ
（213 セッション蓄積済み）への blast radius を、新規に root 化する fail-logs / skill-evolution の
変更と同一 PR に混ぜるのは検証の切り分けを難しくする。共通関数抽出後の audit 側載せ替えは、
本 ADR のスコープ外・別 Issue の後続リファクタとする。

## 決定

1. **共通関数の抽出**: 蓄積型の gitignore ログ（fail-logs `failures.jsonl` / skill-evolution の
   metrics・pending・locks）は root worktree 解決で書く。audit の実装パターン
   （`_resolve_root_worktree()` / `_resolve_log_root()`）を `packages/core/hooks/hook_common.py`
   へ共通関数として抽出し、fail-logs / skill-evolution はこれを利用する。audit 本体の共通関数への
   載せ替えは挙動同一のリファクタであり、別 Issue の後続作業とする（代替案 3 参照）。
2. **root 解決は hook 内部限定**: root 解決は hook 内部の git コマンド呼び出しのみで行い、
   config 経由で project_dir 外パスを指定させない。既存のパストラバーサルガード
   （`resolve_path_within`）は維持する（代替案 2 参照）。`git rev-parse` 失敗時は従来どおり
   project_dir へフォールバックする（fail-safe。fail-logs が一貫して採る非ブロッキング・
   fail-safe 原則（記録機能の失敗が本体動作を妨げない）と整合する）。
3. **配置規約の制定**: 機械が書く蓄積ログの標準配置規約を `.claude/logs/<pkg>/` と定める。
   これに従い、skill-evolution の metrics / pending / locks を `.claude/skill-evolution/` から
   `.claude/logs/skill-evolution/` へ移設する。移設は fail-safe な one-shot migration とし、
   旧パスに実体があり新パスにない場合のみ移動する。移行処理が失敗しても hook を止めない
   fail-open とする。
4. **lessons は対象外**: skill-evolution の `lessons/*.md` は本 ADR のスコープに含めない。
   git 管理下に置いたまま worktree ローカルとして維持し、コミット → PR マージを生存経路とする
   （gitignore ログではないため、worktree 削除で消失する問題自体が発生しない）。将来 lessons を
   git 管理から外す判断をした場合は、root 化を改めて検討する。
5. **出所追跡の追加**: fail-logs のレコードに `branch` フィールドを追加する。root 集約後は
   複数 worktree/ブランチの失敗が同一ファイルに混在するため、どのブランチ/worktree で発生した
   失敗かを追跡可能にする。

## Amendment（2026-07-29 追記・PR #331 レビュー裁定）

決定3の適用範囲を精緻化する。**root 集約の対象は蓄積型の metrics のみ**とする。
pending / locks は一時的セッション状態であり、worktree 間干渉（他 worktree の実行中 pending
の誤回収）を避けるため project ローカルの `.claude/logs/skill-evolution/` 配下とする。

決定3の原文（「fail-logs `failures.jsonl` / skill-evolution の metrics・pending・locks」を
root 解決対象として列挙した箇所）は実装時のレビューでこの区別が必要と判明したため、本追記で
補正する。原文は書き換えず、本 Amendment を裁定として追記する。
