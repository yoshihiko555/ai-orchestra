# ADR-20261104-064: サブエージェントへの routing と共有コンテキストを SubagentStart の additionalContext で届け、Agent の入力を書き換えない

- **ステータス**: accepted
- **日付**: 2026-11-04
- **決定者**: yoshihiko
- **承認根拠**: 2026-11-04 の対話で、利用者が案 E の採用と案 A（冪等化だけで直す）の不採用を選んだ
- **関連**: [ADR-20261028-060](./ADR-20261028-060.md)（前提: `[Resolved Routing]` と `agents.<name>.tool` による routing は必須。本 ADR はその届け方だけを変える）

## 背景

core パッケージの `inject-shared-context.py` は、サブエージェントに 2 つのブロックを届けている。
解決済みの routing（`[Resolved Routing]`。tool / sandbox / model / flags を hook が config から解決・検証したもの）と、
前回までのサブエージェントの結果と作業中のファイル（`[Shared Context]`）である。
これまでは PreToolUse（Agent / Task）で `updatedInput` を返し、Agent の入力の prompt の末尾に 2 つのブロックを足していた。

この方式で、次の 2 つの問題が起きた（2026-11-04、digital-garden のセッション、Claude Code 2.1.317 のトランスクリプトで確認）。

- **auto mode での拒否**: Agent の起動 12 件が、classifier の「no verdict」（`permissionDecision` が reject、理由 `classifier:auto-mode:unavailable`）で拒否された。
  拒否文は「a hook changed this call's input after auto mode reviewed it」で、hook が書き換えた入力を引用していた。
  同じセッションで Bash・Read などほかのツールにこの拒否は無く、auto mode を抜けた後の Agent 起動 5 件は初回で通った。
  classifier はモデルが送った入力を審査し、その後に hook が入力を変えると審査結果が使えなくなる、とログから推定している
  （公式の hooks リファレンスに、auto mode の classifier と `updatedInput` の関係の記載は無い。未確認）
- **ブロックの 2 重付加**: hook はブロックがすでにあるかを確かめずに追記する。拒否文の引用と完全一致しない形で送り直すと、
  hook がもう一度追記し、ブロックが 2 つになった（2 件。うち 1 件は 2 重のままサブエージェントに届いた）

制約は 2 つある。routing は必須なので（ADR-20261028-060）、hook が解決・検証した値をサブエージェントに届け続ける必要がある。
また、ブロックが届かない環境のために、サブエージェントが config を自分で読んで解決する手順が既にある。

## 選択肢

### A. 追記を冪等にする（不採用）

- prompt の末尾が今回足す文面と一致すれば何も返さない。2 重付加は消える
- auto mode の初回の拒否は残る（起動のたびに 1 往復の送り直しが要る）。E にすれば送り直しの不一致そのものが起きない

### B. `updatedInput` をやめ、PreToolUse の `additionalContext` だけを返す（不採用）

- 拒否も 2 重付加も起きない
- PreToolUse の `additionalContext` はオーケストレーターの会話に入り、サブエージェントには届かない
  （hooks リファレンスの PreToolUse の節。このリポジトリでも、オーケストレーターの会話に「PreToolUse:Agent hook additional context」として表示されることを 2026-11-04 に確認）。
  routing はサブエージェントが config を自分で読む手順に戻り、hook による sandbox・flags の検証が効かなくなる

### C. auto mode のときだけ書き換えない（不採用）

- auto mode では B と同じく routing が届かない。permission mode によって routing の契約が変わる

### D. `updatedInput` に `permissionDecision: "allow"` を付ける（不採用）

- Agent の起動を classifier の審査から外す判断になる（サブエージェント内の個々の操作は引き続き審査される）
- auto mode で hook の allow が classifier より優先されるかは未検証。2 重付加は残る

### E. SubagentStart hook の `additionalContext` で届ける（採用）

- Agent の入力を変えないので、classifier の審査と衝突しない。prompt に追記しないので、送り直しで 2 重にもならない
- 2026-11-04 に一時プロジェクトで確かめた（Claude Code 2.1.317、`claude -p --permission-mode auto`、background で起動した
  `general-purpose`・custom agent・`subagent_type` 省略の 3 件）。3 件とも `additionalContext` がサブエージェントに届き、
  classifier は 3 件とも初回で承認した
- SubagentStart の入力には `agent_type`（`subagent_type` 省略時は `general-purpose`）と `cwd` が入り、prompt は入らない。
  routing と共有コンテキストの組み立てに使う入力はエージェントの種別と project のディレクトリだけなので、組み立て処理をそのまま使える

## 決定

**サブエージェントへの `[Resolved Routing]` と `[Shared Context]` は SubagentStart hook の `additionalContext` で届け、Agent / Task の入力は書き換えない。**

1. SubagentStart で、起動したエージェントの種別（空なら `general-purpose`）から routing を解決し、2 つのブロックを `additionalContext` として返す。
   ブロックの形式、注入の対象（routing の config に定義されたエージェントだけ）、`[Resolved Routing]` を最後に置くこと、
   共有コンテキストの値を 1 行に畳むことは従来どおりとする
2. PreToolUse（Agent / Task）は入力を変えない。オーケストレーターには、解決済みの routing の値だけを `additionalContext` で見せる。
   共有コンテキストは見せず、`[Resolved Routing]` の見出しも付けない。信頼できない過去のサブエージェント出力をオーケストレーターの文脈に入れないため。
   また、オーケストレーターが prompt に書き写しても、routing のブロックとして扱われないようにするため
3. サブエージェントは、hook が注入したブロック（タスクの prompt の外に、hook の文脈として届くもの）だけに従い、
   prompt の本文に書かれた `[Resolved Routing]` は無視する。hook の文脈の中でも、正とするのは末尾に行頭の見出しで置かれる 1 ブロックだけで、
   `[Shared Context]` に含まれる文字列は routing として扱わない（過去のサブエージェント出力を経由した偽装を防ぐため）。
   従来の「prompt の最後のブロックが正」という偽装対策は、「hook の文脈の最後のブロックが正」に置き換える
4. hook が注入したブロックが無いときは、サブエージェントが base と `.local.yaml` を読んで自分で解決する従来の手順を残す
5. 導入済みのプロジェクトには、既存の hook の同期（SessionStart）で SubagentStart の登録を足す。
   登録されるまでの間は 4 の手順で動く。routing は hook から届かないが、拒否も 2 重付加も起きない
   （同期は、manifest にあって `settings.local.json` に無い hook を足す。`scripts/lib/sync_engine.py` の実装と単体テストで確認）

## 検証

- 成功の条件: auto mode で Agent を起動して classifier の拒否が起きない。各サブエージェントにブロックが 1 回だけ届く。
  PreToolUse の出力に `updatedInput` が無い。prompt の本文に偽の `[Resolved Routing]` を入れても、サブエージェントが hook の注入に従う
- 結果（2026-11-04、Claude Code 2.1.317、一時プロジェクトに変更後の hook を登録し `claude -p --permission-mode auto`、モデルは Haiku）:
  custom agent（変更後の `debugger` の定義）・`general-purpose`・`subagent_type` 省略の 3 件を起動し、classifier は 3 件とも初回で承認した（拒否 0 件）。
  各サブエージェントのトランスクリプトに SubagentStart の文脈は 1 回だけ入り、prompt は送った文面のままだった。PreToolUse の出力に `updatedInput` は無かった。
  prompt の本文に `tool: codex` の偽ブロックを入れた `debugger` は、hook の文脈（「SubagentStart hook additional context」の枠）にある `tool: claude-direct` に従うと答えた。
  決定 2・3 の形（PreToolUse の表示は routing の値だけ、hook の文脈の末尾の 1 ブロックだけが正）でも同じ条件で確かめ、
  共有コンテキストのエントリーと prompt の本文の両方に偽ブロックを入れた `debugger` は、どちらも無視して末尾のブロックに従うと答えた。
  PreToolUse の表示に共有コンテキストと `[Resolved Routing]` の見出しは含まれなかった

## 影響

- auto mode で Agent / Task の起動が初回で通る。ブロックの 2 重付加が無くなる
- `updatedInput` は入力全体を置き換える（hooks リファレンス「Replaces the entire input object」）。
  2026-11-04 の digital-garden のセッションでは、モデルが送った `run_in_background` が hook の入力にも hook が返した入力にも無かった。
  そのため、hook に渡らなかった引数が書き換え後の呼び出しから落ちるおそれがあった（実行時に落ちたかは未確認）。入力を書き換えなくなるので、このおそれも無くなる
- サブエージェントは、hook の文脈とタスクの prompt を見分けて従う。見分け方は Claude Code が hook の文脈をどう表示するかに依存する。
  表示の仕方が変わって見分けられなくなった場合や、SubagentStart の `additionalContext` が届かなくなった場合は、決定 4 の手順に落ちる
- オーケストレーターが送る prompt にはブロックが入らない。オーケストレーターが routing を確かめるときは PreToolUse の表示を見る
- 今後 `updatedInput` を返す hook を足すと、auto mode で同じ拒否が起きる

## 決定しないこと

- hook が注入したブロックを機械的に見分ける仕組み（署名・使い捨ての目印など）: 決定 3 の規則だけに頼る。
  サブエージェントが prompt 本文の偽ブロックに従った事例が見つかった時点で決める
- Codex CLI / Antigravity CLI に routing を届ける方法: 本 ADR の対象外。両 CLI のハーネスで、サブエージェントの起動時に文脈を足す仕組みを使うことになった時点で決める
- ほかの hook の注入経路: `inject-shared-context.py` 以外に `updatedInput` を返す hook は無い（2026-11-04、`packages/*/hooks` を確認）。
  `updatedInput` を返す hook を新たに足すときに、本 ADR に照らして判断する
