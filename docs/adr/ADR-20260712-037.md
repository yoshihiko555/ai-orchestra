# ADR-20260712-037: PR レビュー指摘を action-scoped snapshot でプロセス境界を越えて受け渡す

- **ステータス**: accepted
- **日付**: 2026-07-12
- **決定者**: yoshihiko

## コンテキスト

`wait_external_review` の Step 2 では、`collect_review_findings()` が取得した `ReviewFindingsResult` を
分類 Task の前後で利用する。明示的な severity を持つ finding は collect 時点で processed として
記録されるため、分類 Task 完了後の別プロセスで再度 collect すると結果から消える。このため、最初の
collect では High finding が存在していても、phase check に渡す結果から欠落し、誤って合格する可能性が
ある。

分類 Task の前後はプロセス境界をまたぐため、最初の collect 結果を情報欠落なく引き継ぐ正式な契約が
必要である。特に finding の `body_excerpt`、`path`、`line` などは既存 state に保持されておらず、state
だけから元の `ReviewFindingsResult` を完全には再構成できない。

また、この snapshot は phase check の入力となる trust-bearing artifact である。別 action の空 snapshot、
stale lease、symlink や権限変更で差し替えられたファイルを受理すると、指摘欠落による fail-open を再び
許し得る。PR 由来文字列を JSON 化した後に正規表現 redaction すると JSON 構造を壊して処理不能にも
なり得るため、action binding と secure load に加えて JSON-safe な構造化 redaction が必要である。

## 検討した選択肢

### 選択肢 A: prompt だけで同一プロセス内に結果を保持する

- メリット: 永続化処理を追加せず、実装変更を最小限にできる
- デメリット: 分類 Task 前後のプロセス境界を越えられず、実行オーケストレーションに暗黙依存する。
  再開時や別プロセスからの phase check で同じ結果を保証できない

### 選択肢 B: state と GitHub API の再取得結果から再構成する

- メリット: 新しい artifact を追加せず、既存の state と外部データを利用できる
- デメリット: state は `body_excerpt`、`path`、`line` などを保持しないため完全な再構成ができない。
  GitHub API の再取得は外部状態の変化や processed 判定の影響を受け、最初の collect 結果と一致する保証が
  ない

### 選択肢 C: action-scoped artifact に `ReviewFindingsResult` snapshot を保存する（採用）

- メリット: 最初の collect 結果を全フィールド含めて正確に引き継げる。既存 state のスキーマを拡張せず、
  action の生存期間だけに限定した小さな差分で実現できる。lease / pending action / envelope binding と
  hardened load を組み合わせれば stale artifact やファイル差し替えも拒否できる
- デメリット: artifact の保存・復元・構造化 redaction・binding / ファイル境界検証と、不要になった
  artifact のライフサイクル管理が必要になる

## 決定

選択肢 C を採用し、`wait_external_review` Step 2 のプロセス境界では action-scoped artifact に保存した
`ReviewFindingsResult` snapshot を正式な受け渡し契約とする。

- `collect_review_findings()` の完了直後に、結果の全フィールドを snapshot として保存する。
- artifact は action 単位で分離し、ファイル権限を `0600` とする。payload は構造を保ったまま
  `redact_payload()` で機密値をマスクしてから JSON 化する。
- snapshot envelope に `schema_version`、`loop_id`、`action_id` を含める。save / load の両 API は active
  `lease_token` を検証し、state の current phase / `pending_action` が同じ `action_id` の
  `wait_external_review` である場合に限り処理する。
- 分類 Task 完了後は `collect_review_findings()` を再実行せず、保存済み snapshot を復元して phase check
  へ渡す。
- load は `lstat`、非 symlink regular file、mode 0600、1 MiB 上限、`O_NOFOLLOW` + `fstat` を検証する。
  artifact の欠損、不正 JSON、不正スキーマ、binding / lease / action / file 境界違反は fail-closed とし、
  空の finding として処理を継続しない。
- snapshot は分類前に取得した結果の受け渡しだけを責務とし、ループ全体の永続 state の正本にはしない。

## 影響

- 明示 severity finding と分類待ち finding が混在していても、分類後の phase check で最初の collect
  結果が欠落しなくなる。
- `/loop-issue` の指示書は、collect 直後の保存と分類後の復元を必須手順として扱う。
- `pr_review_wait.py` は active lease / phase / pending action に束縛された snapshot 保存・復元 API と、
  envelope、全フィールド、スキーマ、secure file 境界の厳格な検証を提供する。
- 構造化 redaction 後も JSON として復元できること、別 loop / stale action / lease 不一致、および
  symlink・mode 違反・oversize・欠損・破損時にレビュー合格へ倒れないことを回帰テストで保証する。
- 既存 state のスキーマおよび GitHub API からの finding 収集仕様は変更しない。
