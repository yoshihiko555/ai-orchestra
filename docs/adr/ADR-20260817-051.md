# ADR-20260817-051: frontier コスト軸をキャッシュ中立コスト（cache_neutral_cost_usd）へ切替え、5 分 TTL ephemeral cache の偽 dominance 勾配を除去する

- **ステータス**: accepted
- **日付**: 2026-08-17
- **決定者**: yoshihiko
- **関連**: Issue #378、loop 実行 `loop-20260817-132400-75b785`（本 ADR の実測根拠）、
  ADR-20260814-049（C-9 ペア評価・凍結の前提となるコスト計測ノイズの原因特定）、
  ADR-20260814-050（skill target 品質分解能。本 ADR はその後段のコスト分解能を扱う）

## コンテキスト

run の記録コスト `total_cost_usd`（CLI 申告値と broker 推定値の `max()`、
`_account_cost_with_broker_metrics`）は、Anthropic API の prompt cache 実測
（`cache_creation_input_tokens` は input 単価の 1.25 倍、`cache_read_input_tokens` は
input 単価の 0.1 倍で計上される）をそのまま反映する。5 分 TTL の ephemeral cache により、
同一 worktree/シナリオへの評価が「直前 5 分以内に走ったか」で `cache_creation` /
`cache_read` の配分比率が大きく変わり、結果として `total_cost_usd` が最大 ~60% 変動する。

実測（`loop-20260817-132400-75b785`、fix-greet-none-bug、同一 candidate 系列・同一
turns/tool 呼び出し構成の 3 run）:

| run   | cache_creation_input_tokens | cache_read_input_tokens | 記録 total_cost_usd |
| ----- | ---------------------------: | ------------------------: | -------------------: |
| b17a  | 60,011                       | 292,951                   | $0.3471               |
| 1d2c  | 4,652                        | 410,163                   | $0.1864               |
| b9fe  | 3,903                        | 348,971                   | $0.1565               |

b17a（baseline、cache miss 直後）と b9fe（同一構成、cache warm）は turns・tool 呼び出しが
同一であるにもかかわらず、記録コストは b17a が b9fe の **2.2 倍**になる。この差は候補の
質・効率とは無関係な環境アーティファクト（fixture 実行ビット欠落・exit 126 に続く、
2026-08 内で確認された第 2 号の環境アーティファクト）であり、`frontier.cost_axis` に
そのまま使うと dominance 判定に偽の勾配を持ち込む。

## 決定

### 1. 正規化式とキャッシュ中立性の根拠

```
cache_neutral_cost_usd =
    (input_tokens + cache_creation_input_tokens + cache_read_input_tokens) × price_input
  + output_tokens × price_output
```

すべての input 系トークン（新規 input・cache creation・cache read）を **同一の input 単価**
で計上し、cache creation/read 側の割増・割引単価は使わない。これにより、同じ作業量の run が
「直前にキャッシュが温まっていたか」で異なるコストに評価されなくなる。

単価は既存 broker の budget 用上限単価
（`evaluate.isolation.broker.pricing_upper_bound_usd_per_million.input` / `.output`、
既定 3.0 / 15.0 $/M）をそのまま転用する。この単価は本来「予算超過を早期に検知するための
安全側上限」であり絶対値としての正確な市場価格ではないが、**全候補に同一単価を一律適用する
相対比較専用の軸**であるため、絶対値の較正は不要という判断で正当化する。ただし
input:output 比が 1:5 であるため、turns 構成比によっては相対順序に影響し得る点は既知の
制約として記録する（将来、絶対値較正が必要になった場合は raw トークン内訳から再計算できる
よう `cache_creation_input_tokens` / `cache_read_input_tokens` を raw のまま `cost` に
保持する — 決定3 参照）。

### 2. usage ソースの優先順位（judge コスト混入回避）

1. **CLI 結果イベントの `usage`**（`cache_neutral_source: "cli"`）— 通常経路
2. **`modelUsage` フォールバック**（budget latch 時の `_sum_model_usage` 拡張、
   `cache_neutral_source: "model_usage"`）
3. **broker metrics usage**（`isolation.broker.metrics.usage`、
   `cache_neutral_source: "broker_metrics"`）— (1)/(2) が完全に空（4 トークンフィールド
   すべて 0）の場合のみの最終フォールバック

broker metrics は run スコープの broker 経由トラフィック全体（judge 呼び出しを含む）を
集計したものであり、(1)/(2) が使える限りは絶対に優先しない。broker 側を安易に既定にすると、
本 ADR が除去しようとしている測定ノイズの発生源（Issue #354 の judge 一過性リトライ等）を
別ルートから再導入することになるため。

`_account_cost_with_broker_metrics` が `metrics.anomaly` / `metrics.budget_exceeded` を
「信用できない broker 計測」の合図として `total_cost_usd` を fail-closed 側に倒すのと同じ
信頼モデルを流用し、これらのフラグが立っている broker metrics は
cache-neutral フォールバックでも「不在」として扱う（`_untrusted_broker_metrics_usage`）。
budget 会計側と cache-neutral 側で broker metrics への信頼水準が非対称にならないための措置。

broker_metrics フォールバック時、`cost["input_tokens"]` / `cost["output_tokens"]` 自体は
書き換えない（`extract_cost()` が返した値のまま、通常は 0）。書き換えるのは新設の
`cache_creation_input_tokens` / `cache_read_input_tokens` / `cache_neutral_cost_usd` /
`cache_neutral_source` のみ。したがってこの稀なコーナーケース（headless run が `result`
イベント発行前にクラッシュした場合）では、`cost` dict からの再計算（決定1 の「raw から
再計算できる」保険）は不完全であり、真の再計算源は run の `metadata.json`
（`isolation.broker.metrics.usage`）である。

### 3. schema 後方互換

`ledger.event.schema.json` の `$defs.cost` に以下 4 フィールドを **optional** で追加する
（`required` には追加しない）:

- `cache_creation_input_tokens: integer, minimum 0`
- `cache_read_input_tokens: integer, minimum 0`
- `cache_neutral_cost_usd: number, minimum 0`
- `cache_neutral_source: enum ["cli", "model_usage", "broker_metrics"]`

`result.schema.json` は `$defs/cost` を `$ref` で参照しているため追従は不要。
`additionalProperties: false` のため、この 4 フィールドを追加しない限り新形式の `cost` は
拒否される一方、これらを追加した後も **旧形式（7 キーのみ）の `run_completed` ledger
イベントはそのまま検証を通る**（`test_legacy_run_completed_cost_round_trips_and_validates`
で検証）。

### 4. evaluator_hash 世代切替を意図的に許容する

`evaluator.py` / `meta_harness_common.py` は `_EVALUATOR_SOURCE_FILES` に含まれるため、
本変更で `evaluator_hash` は変わる。これは PR #377（skill 昇格 promoter の hash 温存判断）
とは**逆の判断**である: PR #377 は「昇格ロジックの変更で既存の評価を無効化しない」ことを
優先したが、本 ADR は「キャッシュ依存の旧 `total_cost_usd` ベース評価はそもそも本 ADR が
問題視する測定ノイズを含んでおり、どのみち新旧比較に使えない」ため、hash 世代切替による
再評価要求を許容する。運用上の帰結として、config 切替後に旧 ledger を含む frontier
再構築を試みると EV-83 の fail-closed（`MetaHarnessRootError: missing cost field
'cache_neutral_cost_usd'`）で停止する。これは意図された挙動であり、remediation は該当
target の frontier/store の再 bootstrap である（次回 loop 運転前に baseline を
再 bootstrap する必要がある — プロジェクトメモ記載のとおり）。

### 5. C-9 ペア評価（ADR-049）との関係

ADR-20260814-049 で検討・凍結された C-9（ペア評価 + コスト軸緩和）は、own suite が
実 backend を呼ばずコスト軸そのものを持てない routing-config target 特有の問題への対処
として設計されたものであり、本 ADR の正規化とは別レイヤーの課題を扱う。本 ADR は
「記録されたコストの測定方法」を修正するものであり、C-9 が扱う「統計的に有意な差をどう
判定するか」という論点の代替ではない。両者は独立に組み合わせ可能であり、C-9 が
再検討される場合、その入力となるコスト値は本 ADR 適用後の `cache_neutral_cost_usd` を
前提とすべきである（測定ノイズが小さいほど統計検定の必要な効果量が小さくて済むため、
本 ADR は C-9 の必要性そのものを弱める可能性が高いが、それ自体は将来の再評価事項とする）。

### 6. `frontier.cost_axis` 既定値の切替範囲

- 実効設定（`.claude/config/meta-harness/meta-harness.yaml` および配布元
  `packages/meta-harness/config/meta-harness.yaml`。両者は byte-identical であることが
  `test_repository_synced_config_matches_package_default` で強制されるため同時更新する）
  の `frontier.cost_axis` を `total_cost_usd` → `cache_neutral_cost_usd` に変更する。
- Python 側 `meta_harness_common.DEFAULTS["frontier"]["cost_axis"]`（config 読み込み失敗時の
  fallback 既定値）は意図的に `total_cost_usd` のまま維持する。理由: この fallback は
  「config が壊れている/読めない場合でも、あらゆる既存 ledger の `cost` オブジェクトが
  必ず持っているフィールド」を指し続けなければならない。`cache_neutral_cost_usd` は
  本 ADR 以前の ledger イベントには存在しないため、これを fallback 既定にすると config 破損時
  に過去データ全体が fail-closed してしまう。

## 影響

- 変更対象: `packages/meta-harness/lib/evaluator.py`（`extract_cost` / `_sum_model_usage`
  拡張、`_apply_cache_neutral_cost` / `_cache_neutral_pricing` /
  `_untrusted_broker_metrics_usage` 新設、`ZERO_COST` 拡張）、
  `packages/meta-harness/lib/meta_harness_common.py`（`KNOWN_COST_FIELDS` 拡張）、
  `packages/meta-harness/schemas/ledger.event.schema.json`（`$defs.cost` 4 フィールド追加）、
  `.claude/config/meta-harness/meta-harness.yaml` + `packages/meta-harness/config/meta-harness.yaml`
  （`frontier.cost_axis` 切替）、対応テスト、`docs/design/meta-harness-detailed.md` の
  cost/frontier 関連記述
- `evaluator_hash` が変わるため、既存 store の frontier は決定4 のとおり再評価要求で
  fail-closed する（意図された挙動）
- budget 会計（`_account_cost_with_broker_metrics` の `max()` 判定、
  `attempt_budget` フォールバック、budget latch 判定、`loop_state._validated_run_cost`、
  `_pre_iteration_guard`、regression suite の予算チェック）は無改修。これらは実額の
  `total_cost_usd` を引き続き参照し、本 ADR の影響を受けない
- 既知ギャップ（本 ADR のスコープ外、フォローアップ課題として記録）:
  `docs/evaluation/meta-harness.md` の EV-83（「既定は全 target 共通の `total_cost_usd`
  である」の記述）は本 ADR で古くなるが、当該ファイルは本実装のガードレールで編集対象外
  としたため、評価セット突合の gap として別途起票が必要
