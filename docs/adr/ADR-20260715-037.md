# ADR-20260715-037: loop-harness LP-2（Maker/Checker）の実行基盤を Docker 完全隔離へ移行する

- **ステータス**: proposed
- **日付**: 2026-07-15
- **決定者**: yoshihiko

## コンテキスト

Issue #211（loop-harness LP-2: Maker/Checker の Docker 完全隔離）は、PR #210（LP-2 実装）の
外部レビュー（CodeRabbit Critical / security-reviewer）指摘に端を発する。LP-2 の Maker/Checker は
現在 `claude -p` を driver（`loop_driver.py`）と同一ホスト・同一 UID で実行しており、
`docs/design/loop-harness-cli.md` §2.2 の 4 層防御（プロンプト制約／env 認証剥奪／
disallowedTools+hook／push 後整合性検証）で push/資格情報アクセスを緩和している。しかし同ドキュメントは
末尾で「同一 UID で動作する別プロセスからの `.claude/loop/` journal/state ファイルへの改ざんに対する
完全性保証は持たない」ことを明示し、本 Issue（#211）へ対応を申し送っている。

並行して、meta-harness は同種の課題（scenario 実行の資格情報隔離）を ADR-20260712-034 で
Docker コンテナ + ephemeral credential broker 方式に解決済みである。本 ADR は、この既存資産を
loop-harness LP-2 に適用する設計判断を記録する。詳細設計は `docs/design/loop-harness-isolation.md`
に記す。

## 検討した選択肢

### 選択肢A: 現行の 4 層防御を強化し続ける（コンテナ化しない）

- メリット: 実装コストが最小。Docker daemon への依存を増やさない。
- デメリット: 振る舞いベースの検知・剥奪に留まり、`.claude/loop/` journal/state・`.git/config`・
  `hooks/` への直接書き換えに対する**構造的な**保証を得られない。denylist・env 剥奪の
  「追加バイパスが見つかるたびにパッチする」いたちごっこが今後も続く。**不採用**。

### 選択肢B: Docker コンテナによる Maker/Checker の完全プロセス隔離（採用）

- 構成: Maker/Checker 実行ごとに `docker run --rm` でオンデマンド起動・実行後破棄する。
  meta-harness（ADR-20260712-034）の dual-homed sidecar broker・セキュリティプロファイル
  （`--read-only` / `--cap-drop=ALL` / `--security-opt=no-new-privileges` / `--internal` network）を
  そのまま流用する。git commit の成立は「ephemeral GIT_DIR + 共有 objects の alternates 読み取り +
  driver 側 CAS 書き戻し」方式（詳細設計 4 節）で解決する。
- メリット:
  - `.claude/loop/` state/journal・`.git/config`・`hooks/`・他ブランチの ref への書き込み経路が
    コンテナに一切マウントされないことで**物理的に**遮断される（検知ベースから構造的境界へ）。
  - meta-harness で実証済みの containment 性質（cgroup による `setsid()` 離脱子孫の確実な回収、
    `--internal` network による egress 遮断）をそのまま継承でき、再検証コストが小さい。
  - broker 経由の認証代行方式により、コンテナ内に資格情報を一切置かない構成を維持できる。
- デメリット / リスク:
  - Docker daemon への依存が増える（ローカルマシン常駐前提の LP-2 運用とは整合するが、Docker 未導入
    環境では利用できない）。
  - Maker がコンテナ内で自ブランチ以外の ref を参照できない制約が生じる（詳細設計 4.5 節）。
  - loop-harness 専用の Docker イメージ整備・ライフサイクル管理（下記）という新規の運用コストが生じる。

### 選択肢C: OS レベルの軽量隔離（sandbox-exec / user namespace のみ、コンテナなし）

- Issue #211 原文が挙げた代替案の一つ（macOS: sandbox-exec、Linux: user namespace + seccomp）。
- メリット: コンテナランタイムへの依存を避けられる。
- デメリット: macOS/Linux で別実装が必要になり、meta-harness の Docker 資産を再利用できない。
  ネットワーク egress 制限の実装も自前になる。**不採用**（Docker が既に meta-harness で実証済みの
  資産であり、二重に隔離機構を持つ理由がない）。

## 決定

**選択肢B（Docker コンテナによる完全プロセス隔離）を採用する。** 以下 7 点を決定事項として確定する
（詳細設計は `docs/design/loop-harness-isolation.md`）。

1. **コンテナ粒度**: Maker/Checker 実行ごとのオンデマンド起動・実行後破棄とする。常駐コンテナは
   持たない（1 アクション = 1 コンテナ）。
2. **資格情報**: コンテナに git/gh 認証を一切入れない「driver 完結方式」を採る。Maker はコンテナ内で
   `git commit` までを行い、push・PR 作成は現行どおりホスト側 `loop_driver.py` の責務として残す。
   broker は meta-harness と同様 Anthropic API 仲介専用とし、git/gh プロキシへは拡張しない。
3. **ベースイメージ**: loop-harness 専用の Docker イメージを新設する。digest 固定に加え、
   **content-hash によるイメージ再利用**・**prune ポリシー**・**並行ビルドのロック**を必須要件とする
   （Issue #231 の教訓の再発防止。詳細設計 5 節）。
4. **egress 制限**: scenario コンテナ（Maker/Checker）は `--internal` Docker network のみに接続し、
   broker が internal + external の dual-homed sidecar として仲介する（ADR-20260712-034 の踏襲）。
   `--read-only` / `--cap-drop=ALL` / `--security-opt=no-new-privileges` も踏襲する。
5. **スコープ**: LP-2（headless `claude -p`）のみを対象とする。LP-1（セッション内伴走型）は対象外とし、
   既存の Claude Code 権限モデル・多層防御をそのまま維持する。
6. **Checker read-only 同梱**: Checker（機械検証・LLM レビュー実行）は worktree を `:ro` マウントし、
   書き込みを物理的に不可能にする（Issue #196 相当の Checker 誤書き込み対策）。
7. **段階導入**: 既存の層2〜4 深層防御（`design:loop-harness-cli` §2.2）は残し、隔離バックエンドは
   config（`lp2.isolation.backend`）で切替可能にする。既定は非隔離（`none`）を維持し、後方互換を
   壊さない。

## ガバナンス上の補足

本 ADR は実装エージェントが起草した `proposed` であり、`accepted` への遷移は
ADR-20260712-034 の申し送りどおり人間レビューを経て行う。実装（`docs/design/loop-harness-isolation.md`
8 節の段階導入計画）は本 ADR の承認後に着手する。

## 影響

- `docs/design/loop-harness-cli.md` §2.2 の「残余リスク（同一 UID 前提）」欄は、本 ADR 承認後の
  実装完了時点で `docs/design/loop-harness-isolation.md` 9 節の内容へ追従して更新する。
- `.claude/config/loop-harness/loop-harness.yaml` に `lp2.isolation` キー群を追加する（既定は
  `backend: none` を維持し、既存プロジェクトの挙動は変わらない）。
- meta-harness の Docker/broker ロジックの一部（コンテナライフサイクル・セキュリティプロファイル・
  broker セッション管理）を共有モジュールへ抽出する設計目標を持つ（`docs/design/loop-harness-isolation.md`
  6 節・8 節 Phase 0）。Phase 0 では `packages/docker-runtime` を新設し、Docker CLI/image 操作、
  security profile の純粋 builder、namespace 注入型の broker/container/network lifecycle、broker image
  資産を共有層へ置く。Phase 1-a では broker 本体も `DR_BROKER_*` / `DR_PRICE_*` 優先・旧 `MH_*`
  fallback の harness 非依存契約へ移行し、明示された namespace から `server_version`/user-agent を
  導出可能にした。namespace 未指定時は meta-harness の既存文字列を維持する。harness 固有の config
  解決・worktree・git metadata・成果物処理は各 harness に残し、meta-harness の既存モジュールパスは
  互換 wrapper として維持する。
- Issue #231（イメージキャッシュ肥大化）相当の不具合の修正は、共有モジュール抽出を通じて
  meta-harness 側にも波及させることを推奨するが、本 ADR のスコープは loop-harness 側の新設に限る
  （meta-harness 側の追従は別 Issue とする）。
- Issue #196（Checker 誤書き込み）は本 ADR の decision 6（`:ro` マウント）により構造的に解消される。
