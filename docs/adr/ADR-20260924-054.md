# ADR-20260924-054: cocoindex パッケージの配布を終了し、実測で効果が確認できない意味検索は導入しない

- **ステータス**: accepted
- **日付**: 2026-09-24
- **決定者**: yoshihiko
- **関連**: ADR-20260302-006 / ADR-20260307-007 / ADR-20260421-017 / ADR-20260423-018（いずれも
  cocoindex の運用方式に関する決定。本 ADR で supersede する）、Issue #240（並列ループのハング。
  cocoindex の SQLite 競合が原因と判断してクローズ）、Issue #344（cocoindex の proxy_manager の
  python3 ハードコード。本 ADR により対象消滅）

## コンテキスト

cocoindex パッケージは、意味検索 MCP サーバー cocoindex-code を Claude Code / Codex CLI /
Antigravity CLI に自動プロビジョニングし、mcp-proxy による共有化と `orchex proxy` での管理を
提供していた（2026-02-24 導入）。これまでの ADR はすべて「どう動かすか」（SQLite 競合・ポート・
proxy の起動と停止）を扱っており、**意味検索がエージェントの探索に役立つかは一度も検証されて
いなかった**。

2026-09-24 に利用実績と有効性を確認した。

1. **利用実績**: 直近 30 日のセッション記録では、cocoindex-code が接続されていた約 1,200
   セッションで search の呼び出しは 0 回だった（同じセッションで Grep/Glob は 600 回以上）。
   MCP ツールは deferred tool として名前しか提示されず、使い所を示す指示も無かったため、
   「使われなかった」ことは有効性の否定にはならない。
2. **有効性の実測（A/B）**: upstream が推奨する方式（`ccc` CLI + Skill、cocoindex-code
   0.2.41、社内 OpenAI 互換ゲートウェイの埋め込みモデル）で learno（約 1,100 ファイル）に索引を
   作り、「どこに実装されているか」を問う質問を Read/Grep/Glob のみ（A）と A + `ccc search`（B）
   で `claude -p` に解かせた。

   | ラウンド | モデル           | 質問                                                 | 実行数 | 完全正解 A / B | コスト B/A                                         |
   | -------- | ---------------- | ---------------------------------------------------- | ------ | -------------- | -------------------------------------------------- |
   | 1        | claude-opus-5-5  | 8 問 × 2 回                                          | 32     | 16/16 / 16/16  | 約 +9%（git 経由の近道で答えた 1 問を除く）        |
   | 2        | claude-haiku-4-5 | 12 問（うち 4 問は質問語と識別子がずれる問題）× 2 回 | 48     | 23/24 / 24/24  | +33%（B の Bash 制限による無駄ターンを含む上限値） |
   - 正解率はどちらのモデルでも差が出なかった。語彙がずれる問題も Grep のみで 8/8 正解した。
   - B でも `ccc search` の後に毎回 Grep で裏取りしており、探索の置き換えにはならなかった。
     検索結果（10 断片）が以降の文脈に残るため、入力トークンとコストは B が多い。
   - `ccc search` の結果上位 10 件に正解ファイルが含まれた割合は約 3 割（絞り込み無しでは
     docs とテストが上位を占める）。モデルが使いこなせないのではなく、検索器として弱い。

3. **運用コスト**: 並列セッションでの SQLite 競合（#240 のハング）、proxy の管理、sandbox 内から
   daemon のソケットに届かない問題、プロジェクトの Bash 拒否ルール（`*password*` 等）が検索
   クエリも弾く問題など、導入に伴う負担が継続的に発生する。

## 検討した選択肢

### 選択肢 A: パッケージを残し、Skill + `ccc` CLI 方式へ作り直す

- メリット: upstream の推奨方式に追従でき、将来の大規模リポジトリで効く可能性を残せる
- デメリット: 実測で効果が確認できていない機能のために、作り直しと運用負担を負う

### 選択肢 B: パッケージを残したまま凍結する

- メリット: 変更が最小
- デメリット: 使われない配布物・`orchex proxy`・関連テストとドキュメントの保守が続く。
  導入先に残った hook が動き続ける

### 選択肢 C: パッケージの配布を終了し、導入先から自動で外す

- メリット: 保守対象と導入先の不要なプロセス起動がなくなる
- デメリット: 既存の導入先に移行手順が必要（`orchex proxy` の削除は CLI の後方非互換）

## 決定

**選択肢 C** を採用する。

- `packages/cocoindex/`、`facets` の `cocoindex-usage`、`docs/evaluation/cocoindex.md`、
  `orchex proxy stop/status` サブコマンドと関連テスト・ドキュメントを削除する。
- 導入先の移行は SessionStart 同期で行う。`scripts/sync-orchestra.py` の `REMOVED_PACKAGES` に
  `cocoindex` を登録し、`installed_packages` と `file_hashes` から自動除去する。登録済みの hook は
  同じ同期の `sync_hooks` が未導入パッケージの hook として外し、同期済みの config は
  `remove_stale_files` が消す。
- 各 CLI の MCP 設定（`.mcp.json` / `.codex/config.toml` / `.gemini/settings.json`）の
  `cocoindex-code` エントリには触れない（`orchex uninstall` と同じ方針）。利用者が手で削除する。

コード探索は、エージェントの Grep/Glob/Read による探索（agentic search）を前提とする。意味検索を
再検討する場合は、本 ADR の実測と同じ A/B 手順で効果を確認してから導入する。数万ファイル規模の
リポジトリや、探索を小型モデルに任せる構成は未検証であり、再検討の候補として残る。

## 影響

- **後方非互換**: `orchex proxy` サブコマンドが無くなる。`orchex uninstall cocoindex` は
  パッケージ実体が無いためエラーになる（同期による自動除去で代替する）。
- **移行時の注意**: hook は設定ファイルの変更を都度読み直すため、同期後のプロンプトから cocoindex
  の hook は発火しない。ただし、ai-orchestra を更新した時点で起動中のセッションは、再起動（または
  次の SessionStart 同期）まで存在しない hook スクリプトを起動しうる。cocoindex を導入している
  プロジェクトは、更新後にセッションを一度再起動する。
- 本 ADR により ADR-20260302-006 / ADR-20260307-007 / ADR-20260421-017 / ADR-20260423-018 は
  superseded となる。Issue #344 は対象消滅でクローズする。
