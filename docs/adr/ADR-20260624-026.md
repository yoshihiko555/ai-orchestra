# ADR-20260624-026: CODD 整合性レイヤーの新設（思想借用・独立パッケージ・essential 化）

- **ステータス**: accepted
- **日付**: 2026-06-24
- **決定者**: yoshihiko
- **関連**: `design:codd-coherence-layer`（`docs/design/codd-coherence-layer.md`）, core パッケージ, facets, ADR-20260322-011

## コンテキスト

AI Orchestra を導入したプロジェクトでは、`/design` などのスキルが要件・設計・ADR・実装計画など
複数のドキュメントを生成する。しかし現状、これらの間には ID 採番（FT-xxx / API-xxx 等）はあるものの、
依存関係の宣言や整合性検証の仕組みがなく、変更時にドキュメント間がドリフトしても検知できない。

[CODD（Coherence-Driven Development）](https://zenn.dev/shio_shoppaize/articles/shogun-codd-coherence)
は、ドキュメントのフロントマターに依存関係を宣言し、依存グラフを構築して整合性を検証する方法論
（参考実装: [yohey-w/codd-dev](https://github.com/yohey-w/codd-dev)）。

要件は2段階:

1. AI Orchestra 自身のドキュメント整合性を保つ。
2. **最重要**: AI Orchestra を導入した各プロジェクトが生成するドキュメントを、配布物として
   CODD 管理下に置く。

AI Orchestra は packages / facets / hooks を導入先へ配る既存の配布レールを持つため、整合性機構を
その上に載せれば新しい配布機構なしに全導入先へ展開できる。

## 検討した選択肢

### 選択肢 A: codd-dev を導入・連携する

- メリット: scan/impact/validate と Claude スキル群が既製で揃う
- デメリット: 外部 OSS 依存の追加、AI Orchestra の package/facet モデルとの二重管理・重複
- デメリット: 既存の context build/sync 資産と統合しづらい

### 選択肢 B: 思想のみ借りて独立パッケージとして独自実装する

- メリット: package/facet/hook の既存流儀に統一でき、配布レールにそのまま載る
- メリット: ON/OFF・依存・テストを AI Orchestra の規約で管理できる
- メリット: 既存の ID 採番（FT/API/SC）を node_id に流用できる
- デメリット: scan/validate を自前実装する初期コスト

### 選択肢 C: 既存パッケージ（core/audit 等）に相乗りで機能追加する

- メリット: 新規パッケージ不要
- デメリット: 有効/無効の切り替えと責務分離が曖昧になる

## 決定

**選択肢 B** を採用する。あわせて以下を決定する。

- **D1**: codd-dev のコードは使わず、思想のみ借りて独自実装する。
- **D2**: 整合性レイヤーは独立パッケージ `packages/codd/` として実装する。
- **D3**: 依存宣言の正本はドキュメント内フロントマター（`codd:` ブロック）。外部 `doc_links.yaml` は作らない。
- **D4**: Phase 1 は `scan` / `validate` まで。impact 分析・hook 配線・CI・コード⇔ドキュメントは別Issue。
- **D5**: 整合性管理の最重要対象は「導入先プロジェクトが生成するドキュメント」。配布前提で設計する。
- **D6**: codd を essential プリセットに追加し常時有効とする（未導入プロジェクトへの frontmatter 漏れを
  facet 条件付きオーバーレイなしで解決）。
- **D7**: 1ファイル=1ノード。`node_id = <kind>:<file-slug>`。集約ファイル内 FT-xxx 等の細粒度ノード化は別Issue。
- **D8**: 依存グラフの保存形式は JSONL（`.claude/codd/graph.jsonl`）。規模拡大時に SQLite を検討。

理由:

1. **既存配布レールとの整合**: manifest.json + presets.json essential で、新しい配布機構なしに全導入先へ届く。
2. **二重管理の回避**: 依存宣言をフロントマター1箇所に集約し、`doc_links.yaml` の二重管理を避ける。
3. **段階導入**: 重い impact 分析・hook 強制・CI を Phase 2 以降に隔離し、Phase 1 で価値（整合性の見える化）を先出しする。
4. **essential 化の必然性**: ドキュメント生成スキル（core/quality-gates 所有）に frontmatter 生成を足すと
   未導入プロジェクトにもメタが出るため、条件付きオーバーレイ機構を新設するより essential 常時有効が単純。

## 影響

- 新パッケージ `packages/codd/`（manifest / lib / scripts / config / tests）を追加する。
- `presets.json` の essential に `codd` を追加し、全導入先で常時有効になる。
- ドキュメント生成スキル（`design` / `design-tracker` / `task-state`）の facet ソースを改修し、
  CODD フロントマターを生成させる。
- `/codd-scan` `/codd-validate` スキルと `codd-frontmatter-policy` ルールを配布する。
- 既存ドキュメント（docs/・.claude/rules/・templates/context/）へ段階的にフロントマターを付与する。
- Phase 2/3 の impact 分析・hook 配線・CI・コード⇔ドキュメント・サブノード粒度は別Issue で扱う。
- 詳細設計は `docs/design/codd-coherence-layer.md`、実装計画は `.claude/Plans.md` を SSOT とする。
