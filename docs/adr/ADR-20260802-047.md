# ADR-20260802-047: agent-routing e2e テストを実効 config 追従の 2 階層構成にする

- **ステータス**: accepted
- **日付**: 2026-08-02
- **決定者**: yoshihiko
- **関連**: Issue #341、Issue #261（Phase A bootstrap）、PR #252 / PR #257、
  ADR-20260717-042（proposer への routing config patch 段階解放）、
  `docs/design/meta-harness-proposer-routing-unlock.md`（F1 の live gap を本 ADR が解消）

## コンテキスト

meta-harness の routing-config target は `config_patch.allowlist`（`agents.*.tool` /
`antigravity.model`）で proposer に config 変更提案を許可している（ADR-20260717-042、Phase A）。
一方、適応度関数の critical check `agent-routing-regression-suite-passes`
（`python3 -m pytest -q packages/agent-routing/tests`）が実行する e2e テスト
（`test_agent_router_e2e.py`）は現行 config 値（debugger=codex / architect=claude-direct /
researcher=antigravity）を固定 assert している。

評価 worktree では候補 patch が `cli-tools.local.yaml` として materialize されるため、
allowlist で合法な提案のほぼ全域がこのテスト pin と衝突し、内容の良し悪しに関わらず原理的に
全不採択となる（実測: 候補 cand-20260721-113744-debugger-9fdb が verify-routing-config で
決定論的に fail、noop baseline は pass）。探索空間（allowlist）と適応度関数（e2e テスト pin）が
矛盾しており、routing-config target のメタハーネス運用が構造的に成立しない。

## 検討した選択肢

### 選択肢 A: e2e テストを実効 config 追従の 2 階層構成へ書き換える

- メリット: 合法な config patch が「変更の実力どおりに」verify-routing-config を通過できるようになり、
  Phase A の loop 運転が成立する。meta-harness 側（シナリオ定義・critical check コマンド）は
  変更不要。
- デメリット: テスト自体の構成が複雑化する（固定値のみを assert する単純なテストから、
  config 解決 + 期待値マーカーマップを持つ 2 階層構成への移行が必要）。

### 選択肢 B: シナリオ側の回帰コマンドから config 値依存テストを除外する

- メリット: ハーネス側（シナリオ定義）だけで完結し、agent-routing パッケージ自体の変更が不要。
- デメリット: 「テストが通る構成か」というゲートの検証の意味が弱まる。critical check が
  config 依存の振る舞いを検証しなくなり、routing-config target の適応度関数としての実効性が
  下がるため棄却。

### 選択肢 C: テストが pin するキーを allowlist から除外する

- メリット: 探索空間と適応度関数の矛盾自体は解消する。
- デメリット: routing-config target の探索空間がほぼ消滅し、proposer 解放
  （ADR-20260717-042 / PR #257）の意義が失われるため棄却。

## 決定

**選択肢 A を採用する。** e2e テストを「実効 config（base + local.yaml マージ後）を読み、
resolved tool 値に応じた期待出力を assert する」形へ書き換える。テストは「hook が config どおりに
動くこと」を検証し、「config の値そのもの」は検証しない。構成は 2 階層とする。

1. **Tier 1（fixture ベース）**: 一時 config を注入し、各 tool 値
   （codex / antigravity / claude-direct / auto）とエッジケース（`enabled: false` フォールバック、
   model allowlist WARN、`local.yaml` 部分 deep-merge、旧 `gemini` 読み替え等）の振る舞い契約を
   完全固定でピン留めする。live config に依存しない。
2. **Tier 2（live-config 契約）**: 実 config を production helper
   （`route_config.load_config`〈内部で `load_cli_tools_config` へ委譲〉/ `get_agent_tool`）で
   解決し、テスト内に独立して手書きした期待値マーカーマップで分岐検証する。tautology 回避のため
   `build_cli_suggestion`（テスト対象)を期待値生成に使わない。なお Tier 2 は期待値の分岐に
   `get_agent_tool` 自身を使うため、同関数のロジック回帰は Tier 2 では検出できない。その担保は
   Tier 1 の fixture テスト（tool 値ごとの完全固定検証）が受け持つ。

`tool: auto` の「CLI 提案なし」は現状仕様として維持する（EV-08 と整合）。行動ベーススイート
（`route-debugger-behavior.yaml`、C-8）の「実効 tool 値に応じて期待を変える」設計思想と本決定は
整合する。

## 影響

- 合法な config patch が「変更の実力どおりに」verify-routing-config を通過できるようになり、
  Phase A の loop 運転が成立する。
- meta-harness 側（シナリオ定義・critical check コマンド）は変更不要。
- `packages/agent-routing/tests/test_agent_router_e2e.py` は Tier 1 / Tier 2 の 2 階層構成へ
  書き換える。Tier 2 の期待値マーカーマップはテスト対象の実装から独立して手書きし、
  実装変更時の追従漏れを `docs/evaluation/agent-routing.md` の突合で検知する。
- 選択肢 B（ハーネス側除外）・選択肢 C（allowlist 縮小）は不採用。将来 Phase B で
  `codex.model` を解放する際も、本 ADR の Tier 1 / Tier 2 構成を前提に契約テストを拡張する。
