# ADR-20260814-048: 品質軸の飽和は own suite の行動ベースシナリオ + gate/graded critical 分離で解消する（支配ルールは変更しない）

- **ステータス**: accepted
- **注記（2026-08-14）**: 本 ADR の一部決定（gate/graded 分離・行動ベースシナリオ・較正
  スパイク・勝者の呪い対処）は ADR-20260814-049 により撤回された。存続するのは
  convergence 判定修正・loop_state 集約の verdict 基準化・数値衛生ガード（1e-6）。詳細は
  ADR-20260814-049 決定 3・5〜7 を参照
- **日付**: 2026-08-14
- **決定者**: yoshihiko
- **関連**: Issue #364、Issue #254（target 拡大、スコープ外）、
  ADR-20260717-042（proposer への routing config patch 段階解放）、
  ADR-20260802-047（e2e テストの実効 config 追従化）、
  `docs/design/meta-harness-proposer-routing-unlock.md`（F1 / §7 Phase B）、
  loop レポート `reports/loop-loop-20260809-222032-4ffd29.md`（F1 の決定的実証）

## コンテキスト

routing-config target の own suite（4 シナリオ）は critical check が全て二値の機械チェックで
あり、合法な config patch は `quality_score = critical_pass_rate * 70 + max(0, 30 - penalty * 5)`
が 100 に収束する（論点 F1「品質軸がほぼ定数」）。2026-08-09 の loop 初完走
（`loop-20260809-222032-4ffd29`、9 反復・$19.22）で以下が実証された:

- loop の progress は quality 改善のみを数える（コスト改善・frontier への候補追加は
  progress にならない）。candidate 成立 3 回で quality 改善（+0.5pt 超）がなければ
  divergence 停止するため、品質飽和下では**実質 candidate 3 回で必ず止まる**
- コスト削減候補（7ccc、-2.2%）は frontier に並存できても、quality 厳密優越ルール
  （C-2、Phase A 凍結決定）の下で baseline を世代交代させられない
- 結果、現行 suite のままでは loop を何回回しても「毎回 divergence 停止・たまに
  コスト削減候補」以上の成果が出ない

さらに、対策設計の Codex レビュー（2026-08-14）とコード裏取りで、単純な「複合 critical で
部分点を作る」案には**実装機構レベルの欠陥**があることが確定した:

- `_determine_verdict`（`evaluator.py`）は critical が 1 つでも fail なら verdict=fail を
  返し、fail run を持つ候補は frontier 資格を失う。つまり部分点（例: 3/4 通過で
  quality 82.5）は記録されても**候補ごと frontier から脱落**し、品質分解能は frontier に
  一切現れない
- convergence 判定（`loop_cli.py: _iteration_converged`）は各候補を「その候補自身を含んだ
  後の best」と比較するため、best を更新した候補は常に距離 0 となり、**連続で大きく品質
  改善している最中でも converged 停止が成立し得る**。#364 の完了条件「divergence 以外の
  停止」がこの欠陥由来の空虚な converged で満たされるリスクがある
- quality_mean は non-holdout シナリオ平均のため、graded な検証項目の**実効刻み幅は
  `70 / (graded 項目数 × non-holdout シナリオ数)`**（graded-only 分母、決定 2 参照）。
  シナリオ 3 本・graded 4 項目なら約 5.8pt であり、convergence band（3pt）との余裕は
  薄い。項目数を増やすほど刻みは band を割り込む

Issue #364 の完了条件は「更新後の suite/ルールで loop を再運転し、divergence 以外の停止
または品質差のある frontier が形成されること」。

## 検討した選択肢

### 選択肢 A: own suite に行動ベースの品質分解能シナリオを追加する（suite 拡充を主軸とする）

解決先 backend が実タスクを解き、出来を段階評価で測る行動ベースシナリオを追加し、
quality を config の関数にする。

- メリット: F1 の根本解消。設計 doc が予見した C-8 系譜（行動ベーススイート拡充）の実行で
  あり、凍結決定（C-2 維持）と無衝突。impact suite（issue-fix 型）で部分点の分散と
  コスト実績 $0.6〜1.0/本が既に実証済み
- デメリット: backend 実行由来の確率的揺らぎ（フレーク）を品質軸に輸入する。評価コスト増
  （1 evaluate あたり +$1〜2 程度）。また上記の verdict 機構の欠陥により、
  **シナリオ YAML 追加だけでは成立せず**、gate/graded 分離の evaluator 改修が必要

#### A の部分点実現方式（サブ選択肢）

- **(A-1) gate/graded critical 分離**: critical を「gate critical」（実行成立性・回帰
  非破壊。fail なら従来どおり verdict=fail）と「graded critical」（出来栄えの段階評価。
  quality にのみ寄与し verdict に影響しない）に分離する。シナリオ YAML に新フィールドを
  追加し、evaluator の verdict / quality 算出を限定改修する。分離宣言シナリオの
  quality 70 点項は **graded critical の pass rate のみを分母として計算**する
  （graded-only 分母。frontier 適格候補は定義上 gate 全通過のため、gate を分母に含めても
  定数項となり刻み幅を希釈するだけになる）
- (A-2) non-critical `checks`（rubric_judge）を quality に組み込む: judge のノイズ
  （#354 で対処したクラス）が採点に直結し、自己採点系の reward hacking 面も広がるため棄却
- (A-3) frontier 資格の緩和（verdict=fail の候補も frontier 比較対象にする）: 「壊れた
  候補を弾く」ゲート意味論自体が壊れるため棄却

### 選択肢 B: 支配ルールの変更（品質同点時にコスト有意差で世代交代を認める）

- メリット: frontier の quality 100 同点並存を解消できる
- デメリット: C-2（コスト単独勝ち禁止）は Phase A の凍結決定であり、設計 doc §7 は緩和の
  前提として C-9（ペア評価）の導入を明記している。さらに品質飽和下の「quality 同点」は
  無意味なシグナル（全員 100）であり、その状態でコスト差の世代交代を認めることは C-2 が
  塞いだ「最安 backend 全切替が構造的に勝つ」攻撃面の再開放そのもの。また loop の progress
  は quality のみを数えるため、支配ルールだけ変えても divergence 停止は解消せず、
  **#364 の完了条件を単独では満たせない**。棄却

### 選択肢 C: A + B の同時導入

- B の前提（C-9）が未実装のまま支配ルールに触れることになり、reward hacking ガードの
  検証負担が A 単独の数倍になる。A で品質軸に実分散が出た後であれば「同点」が情報を持ち、
  コスト有意差の閾値も実測データで較正できるため、B を今混ぜる利益がない。棄却

### 付随論点: dominance への epsilon（分散考慮）導入

品質軸に実分散が入ると、厳密浮動小数比較の dominance は微小ノイズで frontier が揺れうる。
ただし統計的 epsilon の適正値は実分散データなしには較正できない（較正 4 段
〈PR #360/#361〉の教訓「上限ガードは実測で較正する」と同型）ため先送りとする。
一方、**数値衛生ガード**（品質の厳密優越判定に微小マージン 1e-6 を要求し、浮動小数誤差に
よる誤った支配判定だけを防ぐ）は統計的 epsilon とは別物の保守的変更であり、今回導入する。

## 決定

**選択肢 A（A-1 方式）を採用する。** 具体的には:

1. `scenarios/routing-config/` に **`agents.debugger.tool` 感応の多段デバッグタスク**を
   train 1 本 + holdout 1 本追加する。graded critical は 3〜4 項目とし、**実効刻み幅
   `70 / (graded 項目数 × non-holdout シナリオ数)` が convergence band（3pt）と loop の
   quality epsilon（0.5pt）を十分上回る**よう設計する（設計 doc に計算式と制約を明記）
2. **gate/graded critical 分離を evaluator に導入する（A-1）**: gate critical の fail は
   従来どおり verdict=fail（frontier 資格喪失）、graded critical の fail は quality にのみ
   反映する。分離宣言シナリオの quality 70 点項は graded critical の pass rate のみを
   分母として計算する（graded-only 分母）。未宣言の既存シナリオは全 critical が gate 兼
   quality 分母のまま（従来算出と同一）となる後方互換の opt-in スキーマとする
3. **支配ルール（C-2）・promote 基準は変更しない**。選択肢 B は C-9（ペア評価）とセットで
   別 Issue として、A の実測分散データを得てから設計する
4. **統計的 epsilon は実装しない**（観測項目「ノイズ起因の frontier 変動」で実測データを
   収集してから判断）。ただし**数値衛生ガード（1e-6）は品質優越判定に導入する**
5. **convergence 判定の欠陥を修正する**: 比較基準を「その候補を含む前の best」に改め、
   改善が続いている間は converged が成立しないようにする（停止条件の意味論修正。
   #364 完了条件の判定信頼性に直結するため本スコープに含める）。あわせて `critical_pass`
   の集約基準も gate/graded 分離後の verdict 基準（gate critical 全達成）に追従させ、
   graded critical の部分点候補が収束判定から恒久的に除外されないようにする
6. 実装前に**較正スパイク**を行う: baseline（claude-direct）と tool を振った合成候補
   2〜3 個で手動 evaluate し、config 間の quality_mean 差（≥ 実効 1 刻み）と同一 config 内
   分散（< 実効 1 刻み）を実測確認する。加えて graded 項目ごとの pass 頻度・項目間相関・
   天井/床効果、train/holdout の順位整合、「バグを解かずに期待アーティファクトだけ生成
   する」adversarial control による oracle leakage 検証を測定項目に含める。満たさない
   場合はシナリオを再設計する
7. **train repeat=1 の勝者の呪い**（まぐれ高得点が偽 divergence を誘発するリスク）への
   対処（best 更新候補の train re-eval 等）は、スパイクで同一 config 内分散を実測して
   から要否を判断する（今回は実装しない）
8. graded critical の設計原則: **独立したエンドステート挙動のみを採点**し、ルート宣言・
   ログ・自己申告・期待ファイル形式そのものに報酬を与えない。holdout は train の
   リネームではなく本質的に異なるバグを用いる（proxy-gaming / oracle leakage 対策）
9. 現 baseline（7ccc 昇格由来の debugger=claude-direct）が品質軸の導入で世代交代される
   可能性を**許容する**。品質×コストのトレードオフの可視化こそが本改善の目的であり、
   promote は従来どおり human ゲートで判断する
10. `antigravity.model` 系の分解能シナリオは今回追加しない（スパイク結果を見て増設を判断）

## 影響

- suite_hash に加えて **evaluator_hash も変わる**（gate/graded 分離・convergence 修正・
  数値衛生ガード）ため baseline の再 bootstrap が必要（12c6 の holdout 未クリーン問題は
  この時点で自然消滅する）
- 評価コストは 1 evaluate あたり +$1〜2 程度増加する（行動シナリオ実測 $0.6〜1.0/本）。
  新シナリオの上限は較正済みの `max_turns: 16` / `max_budget_usd: 15.0` を出発点とする
- 変更対象: `lib/evaluator.py`（verdict / quality 算出の gate/graded 対応）、
  `lib/meta_harness_common.py`（`_dominates` の数値衛生ガード）、
  `lib/loop_cli.py`（convergence 比較基準）、`lib/loop_state.py`（`non_holdout_summary` の
  `critical_pass` 集約を `critical_pass_rate == 1.0` から gate/verdict 基準へ変更。
  graded 部分点を持つ適格候補が収束判定から除外されないようにする）、シナリオ YAML
  スキーマ（graded 指定の opt-in フィールド）、対応するテストと
  `docs/evaluation/meta-harness.md` の突合
- loop 再運転の期待される出口は「品質改善の観測による継続」または「（修正後の判定に
  よる）converged 停止」。いずれも #364 完了条件を満たす
- 選択肢 B（支配ルール変更）と統計的 epsilon、勝者の呪い対処は不採用ではなく**先送り**。
  いずれもスパイク / 再運転の実測データを前提条件として再検討する
- `docs/design/meta-harness-proposer-routing-unlock.md`（F1 / §7）と
  `docs/design/meta-harness-detailed.md`（quality/verdict・suite 設計節）を本 ADR に
  追従して更新する
