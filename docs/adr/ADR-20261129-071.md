# ADR-20261129-071: 隔離実行用の buildx builder は、ホスト上で誰も使っていなければビルドの後に止める

- ステータス: 採用（accepted）
- 決定日: 2026-11-29
- 関連: [ADR-20260726-045](./ADR-20260726-045.md)（前提。loop-harness と meta-harness のイメージを、docker-runtime の共通処理が専用の buildx builder でビルドする）

## 背景

loop-harness と meta-harness は、隔離実行用のイメージを専用の buildx builder（driver は `docker-container`）でビルドする。
開発者の既定の builder の cache を prune しないために、専用の builder を分けている（`docs/design/loop-harness-isolation.md` の 5.2 節）。
builder を使うのはビルドのときだけだが、作った builder を止める処理がない。
2026-11-29 に手元（macOS + OrbStack）を `docker ps` で見ると、2 つの builder コンテナが 5 日間起動したままだった。

builder 名は Docker daemon 全体で 1 つで、既定名は全プロジェクトで同じになる。
一方、ビルドを直列にするロックは checkout ごとのファイルにある。
そのため、あるプロジェクトのビルドの後に builder を止めると、同じ builder で別のプロジェクトが進めているビルドを失敗させうる。

2026-11-29 に手元（macOS + OrbStack、buildx v0.37.2）で次を確かめた。

- 止めた builder へ `docker buildx build` を流すと、builder は自動で起動し、ビルドは成功する
- BuildKit cache は builder の named volume に残り、止めても消えない
- 止めた builder への `docker buildx du` と `docker buildx prune` は、builder を起動せず終了コード 1 で失敗する
- builder の再起動ポリシーは `unless-stopped` で、手で止めた builder は daemon を再起動しても止まったままになる。常駐の原因は、止める処理がないことにある

## 選択肢

### A. 止めない。止める手順だけを案内する（不採用）

- 他のビルドを止める心配はないが、利用者が毎回止める必要があり、常駐は解消しない。

### B. ビルドの後に無条件で止める（不採用）

- 別のプロジェクトが同じ builder でビルドしている最中に止めうる。

### C. 再起動ポリシーを `no` にする（不採用）

- daemon の再起動後に起動しなくなるだけで、daemon が動いている間の常駐は残る。上の実測のとおり、原因は再起動ポリシーではない。

### D. 専用の builder をやめ、既定の builder でビルドする（不採用）

- 開発者の既定の builder の cache を prune しないために専用の builder を分けた前提（ADR-20260726-045）を崩す。

### E. ホスト全体で共有するロックで使用中かを調べ、誰も使っていなければ止める（採用）

- 使い終わった builder は常駐しない。別のプロジェクトのビルド中は止めない。止めても cache は残り、次のビルドで自動で起動する。

## 決定

**隔離実行用の buildx builder は、ビルドで使い終わったときに、同じ builder を使っているプロセスがホスト上に他になければ止める。**

1. 使用中かどうかは、builder 名ごとにホスト全体で共有するロックで判定する。ロックはユーザー単位で 1 か所に置き、どの checkout・worktree からも同じ場所を指すようにする（具体的な場所は docker-runtime の評価セット EV-38 に書く）。
2. builder を使うプロセスは、builder の準備から、ビルドの後の cache の prune が終わるまで共有ロックを持つ。prune は止めた builder では失敗するため、prune が終わるまでは止めない。
3. 抜けるときは、排他ロックを待たずに取りにいき、取れた場合だけ builder を止める。取れなければ、最後に抜けるプロセスが止める。
4. ビルドが失敗した後も、同じ条件で止める。止める処理の失敗は、ビルドの結果も元の例外も変えない。
5. builder を使わない経路（ビルド済みイメージの再利用など）では止めない。
6. ロックを開けない・取れない環境では、ビルドを失敗させず、ロックなしでビルドし、builder は止めない。
7. このロックは builder を止めるかどうかの判断だけに使う。image・pending journal・pin lease の cleanup は、これまでどおり checkout 単位で行う。

## 検証

- docker-runtime の評価セット EV-38 と EV-39 を単体テストで確かめた。対象は、止める順序（prune の後）、失敗時の停止、他のプロセスがロックを持つ間は止めないこと、再利用の経路で止めないこと、停止に失敗してもビルドは成功すること、ロックを開けない環境でのビルドである。
- 2026-11-29 に手元（macOS + OrbStack、buildx v0.37.2）で meta-harness の Docker 統合テストを実行した。builder が作られてビルドに使われ、テストの後に止まった。2 回目の実行でも、起動・ビルド・停止の順に動いた。

## 影響

- 使い終わった builder コンテナは常駐しない。BuildKit cache は残る。
- ビルドのたびに builder の起動を待つ。起動にかかる時間は計測していない（未確認）。
- orchex が初めてホスト全体で共有する実行時の状態になる。builder 名ごとに空のロックファイルがユーザーのディレクトリに残る。
- ロックなしで進めたビルドは、ロックを取れる別のプロセスからは見えない。そのため、そのプロセスのビルドが終わったときに止められうる。止められたビルドは失敗し、次の呼び出しで作り直される。
- ロックで調停できるのは、同じユーザー・同じ HOME で動くプロセス同士だけである。別ユーザーや HOME を変えたプロセスが同じ builder でビルドしている最中には、止めうる。
- ビルドの外で出していた BuildKit cache の使用量の警告は、builder が止まっている間は出ない。cache の上限の制御は、ビルドの後の prune が builder の起動中に行う。
- このロックを持たない旧版の orchex と新版が同じ builder 名を使う場合（`.local.yaml` で builder 名を固定したときなど）、新版は旧版のビルド中に builder を止めうる。

## 決定しないこと

- builder を止めない設定を設けるか: ビルドのたびの起動待ちが問題になったと利用者から報告があった時点で決める。
- ロックファイルの掃除: builder 名ごとに空のファイルが 1 つ残るだけなので行わない。builder 名の種類が増えて問題になった時点で決める。
- daemon 全体で共有する cleanup の調停: 扱わない（`docs/evaluation/docker-runtime.md` の Non-Goals）。
