# ADR-20260706-031: ループエンジニアリング基盤（loop-harness）の導入とコア共有型制御モデルの採用

- **ステータス**: accepted
- **日付**: 2026-07-06
- **決定者**: yoshihiko

## コンテキスト

2026 年 6 月、「ループエンジニアリング（loop engineering）」という概念が定着した。Peter Steinberger は
「エージェントに投げるプロンプトではなく、エージェントを駆動するループを設計すべきだ」と述べ、
Anthropic の Boris Cherny は「自分の仕事はループを書くことだ」と表現した。Addy Osmani はこれを
Trigger（起動条件）→ Maker（生成）→ Checker（検証）→ 停止判定という反復構造として体系化している。

AI Orchestra は harness engineering の部品（hooks / rules / agent-routing / quality-gates）は既に
揃っているが、これらを束ねて「Trigger → Maker → Checker → 停止判定」の反復ループ本体として動かす
基盤が存在しない。既存資産にもループ的要素は点在する（`/review` の Phase 5-7 はプロンプト駆動の
`while` ループで停止判定が決定論的でない、`skill-evolution` の `evaluate_stop()` はスキル改善固有
メトリクス前提でテスト合否のような離散的な Checker 結果に使えない、fail-logs は記録に留まり次の
反復を駆動しない）。ファーストユースケースは Issue 消化ループ（Issue 1 件 → worktree 隔離で実装 →
検証 → 修正反復 → 合格で PR 作成 → PR 上の外部レビュー対応 → 新規指摘解消で完了）とする。

詳細な背景・課題（P-1〜P-5）・スコープは `docs/requirements/loop-harness.md` を、制御モデル比較の
詳細は `docs/design/loop-harness.md` の 1 節を参照。

## 検討した選択肢

制御モデル（誰が・どこでループを駆動するか）について 3 案を検討した。

### 選択肢 A: プロンプト駆動拡張

`/review` の Phase 5-7 のように、LLM 自身が指示書に従って `while` ループを回す方式。

- メリット: 実装コスト最小。既存パターンの延長で導入できる
- デメリット: 停止判定・反復回数が決定論的に保証されない。Maker/Checker の分離が指示書頼みで
  自己評価バイアス（Nodding Loop）への構造的防御が弱い

### 選択肢 B: 完全独立実行

セッション内伴走（LP-1）も持たず、常に `claude -p` を子プロセスとして起動する headless worker
（LP-2 型）に実行モデルを一本化する。

- メリット: 実行モデルが単純（1 種類のみ）
- デメリット: セッション内伴走（対話しながらの反復観察・介入）ができない。agent-routing / audit /
  codex-suggestion-compliance 等のセッション内 hook 基盤を経由できず、これらを LP-2 側に再実装する
  必要が生じ、既存資産の再利用方針に反する

### 選択肢 C: コア共有型（採用）

状態機械・ガード評価・失敗シグネチャ正規化を `loop_common.py` に集約する。LP-1（セッション内伴走型）
はオーケストレーターが `loop_step` CLI を two-phase プロトコル（`propose` / `complete`）で都度呼び出し
次アクションを決定論的に受け取るハイブリッド制御とし、実際のアクション実行（Task 起動）はオーケスト
レーターが担う。LP-2（ローカル常駐自律型）は同じコアを使う完全独立ドライバ（`loop_scheduler` +
`loop_driver`）とし、trigger discovery からループ完了まで `claude -p` を用いて自律的に駆動する。

- メリット: コアの二重実装を避けつつ、LP-1 はセッション内資産（agent-routing / audit / tmux hooks）
  を活かせる。LP-2 は認証共有・常駐・cron/launchd 起動という制約に合わせて独立して動ける。ガード
  評価・失敗シグネチャ正規化・state/journal スキーマが 1 箇所に閉じるため、LP-1/LP-2 で挙動が
  乖離しない
- デメリット: 実行モデルが 2 種類になり、`loop_common.py` のインターフェースを両モデルに耐える形で
  設計する必要がある

## 決定

選択肢 C（コア共有型: LP-1 セッション内ハイブリッド + LP-2 ローカル常駐完全独立ドライバ + `loop_common.py`
コア共有）を採用する。

1. 汎用ループ基盤 `packages/loop-harness` を新設する。ループ定義は `phases[]` を第一級とする宣言的
   YAML とし、コア改修なしで新しいループを追加できる構成にする。
2. 制御モデルは案C とする。P-2（決定論的停止の欠如）・P-4（Nodding Loop 対策の欠如）は状態機械と
   ガード評価を Python 側に正本として持つことで解消する（LLM の自己申告のみに依存しない）。案A は
   停止判定が決定論的でないため却下し、案B はセッション内 hook 基盤の二重実装を招くため却下する。
3. ループ状態は root worktree 側 `.claude/loop/` の専用 state/journal を正本とする。audit へは
   `loop_start` / `loop_iteration` / `loop_stop` イベントを `EVENT_TYPES` に additive 追加して相乗り
   させる。core `log_common` の未配線 `events.jsonl` 系統は使わない（既存 2 系統併存を悪化させない）。
4. Checker は機械検証（`failure_detector.analyze()` を直接利用したテスト実行 + lint 判定）を必須とし、
   これに LLM レビュー（`code-reviewer` ベースライン + `skill-review-policy` 準拠の追加選定、最大 2 名）
   を組み合わせた二層とする。自動合格基準は選定された全レビュアーの **Critical=0 かつ High=0** とする。
   ループは無人反復であり、人間による「High の理由付き受容」判断を挟めないため、通常のレビュー運用
   より合格基準を厳格化する。この基準は LP-1（伴走型）にも意図的に一律適用し、LP-1/LP-2 で挙動を
   揃える。
5. ループは PR 作成後の外部レビュー対応まで担う。当面は Codex の GitHub 連携自動レビューのみを対象と
   し、発信元 allowlist 照合により受け入れる指摘元を限定する。人間の関与はマージ判断（および停止後の
   Draft PR 対応）に集約する。PR の auto-merge は付けない。
6. Issue #139（`skill-evolution` オフライン層）は本決定のスコープ外とする。目的が異なる（スキル定義
   の最適化 vs 開発タスクの消化）ため統合しないが、将来 loop-harness 上への載せ替え候補として本 ADR
   に記録する。

## 影響

- 既存の `issue-fix` / `pr-create` スキルは変更せず、そのまま資産として再利用する。Issue 消化ループは
  新スキル `/loop-issue` として追加する。
- audit の `EVENT_TYPES` に `loop_start` / `loop_iteration` / `loop_stop` の 3 イベントを additive に
  追加する（既存イベントへの後方互換は維持）。
- 評価セット `docs/evaluation/loop-harness.md` は実装時（詳細設計後）に新設する。
- セキュリティ設計（push 前ガード、redaction の全チャネル適用、state ファイルの権限分離）は
  `docs/design/loop-harness.md` を正本として参照する。
- `loop_common.py` のインターフェース変更は LP-1 / LP-2 双方に影響するため、変更時は両モデルでの
  回帰確認を必須とする。
