# ADR-20260720-041: 予算 latch を frontier 回帰判定で評価不能として中立化する

- **ステータス**: accepted
- **日付**: 2026-07-20
- **決定者**: yoshihiko（2026-07-20 承認）

## コンテキスト

Issue #261 の routing-config Phase A bootstrap では、no-op baseline の own suite と 7 つの
cross-skill regression suite のうち 5 suite が完走した一方、`skill:issue-create` と
`skill:issue-fix` は broker の保守的な worst-case 前課金で error になった。実費は $0.6 未満でも、
会話履歴を含む request body が turn ごとに成長するため、scenario 予算を $3→$6→$9→$15 と
引き上げるたびに後半 turn で同じ 429 を再現した。

従来の `evaluation_completed.verdict` は regression の error を全て候補の欠陥として扱うため、
何も変更しない no-op baseline も frontier に載らない。根本解決は Issue #278 の Token Count API
による正確な入力計測だが、Phase A の探索を安全に継続するには「候補が壊した」と「予算制約で
測れなかった」を区別する必要がある。

## 検討した選択肢

### 選択肢 A: budget latch だけを合成 verdict で中立化する（方針 1a）

- メリット: 非予算の regression fail/error は hard gate のまま維持し、評価不能だけを探索上の
  中立要素として扱える。promotion は suite 別 error を独立検証するため安全性を維持できる。
- デメリット: frontier 上では未検証 suite を持つ候補が親になり得るため、警告の永続化と promotion
  拒否を継続する必要がある。

### 選択肢 B: frontier を own suite だけで判定する（方針 1b）

- メリット: regression 実行基盤の状態にかかわらず探索を継続できる。
- デメリット: 候補が実際に壊した非予算 regression も探索の親にでき、cross-skill hard gate を導入した
  ADR-20260715-038 の設計意図を失う。

### 選択肢 C: 予算引き上げまたは Token Count API 導入まで frontier を停止する

- メリット: 評価不能を frontier 判定へ持ち込まない。
- デメリット: 予算引き上げは body 成長に追随して再 latch することが実測済みで、Token Count API は
  endpoint・request・失敗モードを追加する Phase B の変更になる。

## 決定

**選択肢 A（方針 1a）を採用する。**

1. broker は token/cost upper bound による前課金拒否だけを `budget_rejected_count` として metrics に
   記録する。入力不正・model allowlist・通常の HTTP 拒否はこの理由コードに含めない。
2. evaluator は `budget_rejected_count > 0`、broker の budget latch と整合する metrics reason、run verdict が
   `error`、かつ失敗した critical check・cleanup/metadata/oracle/schema 等の独立した hard error がない場合だけ、run result に
   `budget_latched: true` を記録する。新フィールドは optional とし、既存 result/metadata を受理する。
3. regression suite に fail run がなく、error run が 1 件以上あり、その全件が `budget_latched: true`
   の場合だけ latch-only suite とする。1 件でも非 latch error または fail があれば従来どおり hard gate
   とする。
4. latch-only suite は合成 verdict の error/critical 集計から除外し、
   `evaluation_completed.budget_latched_suites` に明示する。`regression_results[].verdict` は `error`、
   `critical_pass` は false のまま保持する。own と残りの regression が pass なら合成 verdict は pass とし、
   既存 frontier eligibility を通す。
5. promotion 判定と quality strict dominance（C-2）は変更しない。promotion は suite 別
   `regression_results` と run event を独立検証するため、latch-only suite を含む候補を引き続き拒否する。
6. Token Count API による根本的な前課金精緻化は Issue #278（Phase B）で継続する。

## 影響

- no-op baseline のように候補起因でない latch-only regression を持つ評価は frontier の探索親になれる。
- latch suite は台帳から隠れず、run result と evaluation summary の両方で監査できる。
- 非予算 error、fail、独立した hard error、latch と非 latch error の混在は従来どおり frontier を拒否する。
- latch suite を含む候補は holdout promotion gate を通らず、本番反映には利用できない。
- Issue #261 PR9 review fix で promotion の独立検証を強化し、holdout/train いずれの evaluation batch でも
  `budget_latched_suites` が非空なら明示拒否して、zero-holdout suite の train 側 latch が aggregate verdict
  だけの確認を通過する隙間を塞ぐ。
- 旧 result/event は新フィールドを欠いていても schema-valid であり、理由コードを持たない旧 error は
  fail-closed に hard error として扱われる。
