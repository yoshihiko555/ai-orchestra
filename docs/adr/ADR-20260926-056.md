# ADR-20260926-056: 開発プロセスを「対話 → 発注書 → 4 実行エンジン」に組み直し、Plans.md を発注書として拡張する

- **ステータス**: accepted
- **日付**: 2026-09-26
- **決定者**: yoshihiko
- **関連**: プロンプト監査（2026-09-25）の F14（`preflight` の EnterPlanMode 禁止の重複）、
  Notion タスク「設計〜リリースの開発プロセス（スキル群）を最新のワークフローに合わせて見直す」、
  ADR-20260520-022（main 一本化。`stage` ブランチの残存言及を本 ADR の quick-win で消す）、
  調査メモ `.claude/docs/research/ai-dev-process-2026.md`（仕様駆動フレームワークと自律ループの
  比較。出典の確度ラベル付き）

## コンテキスト

2026-09-25 のプロンプト監査で F14（`facets/instructions/preflight.md` の 7 / 36 / 153 行目に同じ
禁止指示が 3 回ある）を指摘したが、文言を直す前に preflight を含む開発フローのスキル群が今の
使い方に合っているかを確認した。

**実際に動いている開発フローは 4 本**で、旧フロー（`/preflight` → `/startproject` / `/issue-fix`）は
どれにも登場しない。

| フロー | 前半（計画）                                      | 後半（実行）                                                             | 状態の置き場                                    |
| ------ | ------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------- |
| A      | grill-me 等の対話 → Plans.md に受け入れ条件（AC） | Claude Code の `/goal` が AC を満たすまで回す                            | Plans.md                                        |
| B      | 対話 → Plans.md → `/handoff` で引き継ぎファイル   | Codex CLI が直接実装（レート制限時の退避を含む）                         | Plans.md（Codex も AGENTS.md の指示で更新する） |
| C      | `/issue-create` で AC 付き Issue                  | `/loop-issue`（LP-1 の Maker / Checker 反復）→ PR → `/review-respond`    | loop_step の state.json と Issue コメント       |
| D      | 対話 → 指示書を手書きして TAKT に貼り付け         | TAKT（nrslib/takt）が別クローンで plan → implement → review → fix を回す | `.takt/tasks/<id>/`                             |

使用実績（claude-mem のプロンプト履歴）: `/preflight` は 7/23〜8/14 に 9 回で以後なし、
`/startproject` は 7 月以降なし、`/design` は 8/14 に他プロジェクトで使用（learno / baton の
`docs/` は 8〜9 月に更新）、`/pr-create` は 8〜9 月に継続使用、`/review` は 8 月まで多数。`/loop-issue` と
`/review-respond` はプロンプト履歴には出ないが、PR とセッション記録（#429 / #443 / #464 等）から 9 月も
継続使用と判断した。

棚卸しで見つかった問題:

1. 対話（grill-me）の結論を Plans.md に起こす正式な導線が preflight の Phase 4 しかなく、preflight を
   使わなくなった今は会話に残るだけになっている。`/task-state add-phase` を直接呼ぶと AC を聞き直す
2. Plans.md は「Phase + AC + タスク行」だけで、目的・前提・対象外・制約を書く場所がない。
   TAKT 向け指示書（learno の `order.md`）はこれらを毎回手書きしており、AC の記法も Issue や
   Plans.md の `verify` / `judge` と揃っていない
3. レビュアー選定ロジックを `/issue-fix` Phase 4・`/loop-issue` Checker・`/review` の 3 スキルが個別に持つ
   （`/loop-issue` は `route_config.py` と harness コードに結合しており、本 ADR では触らない）。
   `/issue-fix` は PR 作成手順も `/pr-create` から転記して自前で持つ
4. 「既存 docs を読んで矛盾を確認する」が preflight / design Phase 0 / startproject Phase 2 に散在し、
   「タスク分解 → Plans.md」も preflight と startproject で二重
5. 4 フロー（+ セッション内で小さく直す `/issue-fix`）の使い分け基準がどこにも書かれていない
6. `codex-system` の knowledge 5 件（agent-prompts / code-review-task / delegation-patterns /
   refactoring-task / troubleshooting）は instruction 本文からも Codex レビュー経路
   （`codex_review.py` / `review.md`）からも参照されていない。agent-prompts の役名は実エージェント名と
   一致しない
7. 古い記述: `/tdd` Phase 0 の「Typical Routing: codex」表と Codex 前提の強制文、`design.md` の
   「Antigravity 等」（`/pr-create` `/issue-fix` の stage / staging 言及は base branch resolver の候補と整合して
   おり、他プロジェクトの多段ブランチ運用向けなので残す）

外部調査（上記調査メモ）で確認した点:

- 仕様駆動フレームワーク（Spec Kit / Kiro / OpenSpec / superpowers / Plan Mode）は共通して
  「対話で合意した直後に 1 回だけファイルへ書き出し、以後はファイルを正本にする」境界を持ち、
  タスク行に対象ファイルと検証手順を持たせる
- Plans.md は gitignore 対象の worktree ローカルなので、別クローンで動く TAKT や別 worktree の
  loop-issue からは見えない。4 エンジン共通の正本にはできない
- Spec Kit の 4 ファイル構成や OpenSpec の差分仕様は、既存の Plans.md + `.claude/rules/` + CLAUDE.md
  と役割が重なり、ソロ開発ではファイルが増えるだけなので採用しない
- 報酬ハッキングは本プロジェクトの meta-harness で実例（候補 b10a）があり、独立レビュアーと
  テスト差分検知は継続する
- TAKT は `takt add #N` で Issue を取り込み、キューに積む前に AI との会話で要件を確認する
  （README の CLI 一覧）。Issue を発注書にしても TAKT 側の対話は失われない

## 検討した選択肢

### 選択肢 A: F14 の重複だけを消す

preflight の本文中の再掲を削り、他は触らない。preflight 自体が 6 週間使われておらず、直しても
使われない可能性が高い。

### 選択肢 B: 発注書の正本を 1 か所に決める

B-1（コミット済み仕様ファイルを正本にし、Issue を生成）は、タスクごとにファイルが git に溜まる。
発注書は完了したら捨ててよい短命な文書で、履歴で追う価値がない。
B-2（Issue を正本にし、Plans.md を生成）は、複数フェーズの進捗をローカルで持つ Plans.md の
役割と衝突し、中断後の再開点が分からなくなる。
どちらも「発注書」と「進捗状態」を同じ物として扱っているのが問題。

### 選択肢 C: 発注書と状態を分け、Plans.md を発注書として拡張する

- 発注書（何をするか + AC）は使い捨てで git に残さず、対話の結論から 1 回だけ書き出す。
  置き場は実行エンジンごとに 1 か所（Plans.md か Issue 本文）
- 状態（どこまで進んだか）は実行エンジンが自分で持つ。再開はエンジンの手段で行う
- Plans.md に発注書の節（目的・前提・対象外・制約・未決）を足し、タスク行に対象と確認方法を書く。
  同じ内容モデルを Issue 本文へ写せば loop-issue と TAKT の発注書になる
- 書き出しを担うスキルを 1 つ新設し、旧フローのスキルは廃止・縮小する

## 決定

**選択肢 C** を採用する。

### 1. プロセス

前半は 4 エンジン共通、後半はエンジンごと。

1. **決める**: grill-me 等の対話で要件と計画を詰める。正式な設計書（codd 付き `docs/`）が要るときだけ
   `/design` を使う
2. **発注する**: `/order`（仮名。実装時に確定）が対話の結論を発注書の内容モデルに固めて 1 回だけ提示し、
   選んだエンジンの発注書として 1 か所に書く。AC は対話で確定した内容を転記し、聞き直さない
3. **作る**: 実行エンジンが発注書を読んで実装し、状態を自分の置き場に書く
4. **出す**: `/pr-create` → `/review-respond`。`/goal` はループ完了後にユーザーが `/release-readiness` で
   AC 全チェック・テスト・レビューを確認する（`disable-model-invocation` のため手動）

| 実行エンジン             | 発注書                                    | 状態                    | 再開                     | 向いている場面                                        |
| ------------------------ | ----------------------------------------- | ----------------------- | ------------------------ | ----------------------------------------------------- |
| `/goal`                  | Plans.md                                  | Plans.md の `cc:` と AC | SessionStart hook の注入 | セッション内で完結し AC が機械検証できる              |
| Codex 直接（`/handoff`） | Plans.md から生成した引き継ぎファイル     | Plans.md                | `codex -c`               | Codex に実装を任せる、レート制限時の退避              |
| `/loop-issue`            | Issue 本文                                | loop_step の state.json | `--attach` / `--resume`  | 無人で Maker / Checker を反復させる                   |
| TAKT                     | Issue 本文（`takt add #N`）またはタスク文 | `.takt/tasks/<id>/`     | `takt -c`                | 別クローンで並列に回す、実装プロバイダを Codex にする |
| `/issue-fix`（補助）     | Issue 本文                                | 会話と git のみ         | なし                     | Issue 起点でセッション内に小さく直す                  |

エンジンをまたぐときは発注書を変換して片方だけ残す。Plans.md の Project を Issue に出したら、その
Project は「#N へ引き渡し」として Plans.archive.md に移す。逆方向も同様に変換し、二重に状態を持たない。

### 2. Plans.md v2

Project 直下に発注書の節を足し、タスク行を具体化する。階層は Project → Phase → Task の 3 段で、
AC は Phase の属性。Decisions / Notes はファイル末尾に 1 つずつ（現行どおり）。

```markdown
## Project: {名前}

#### Goal

#### Context ← 参照する設計書 / Issue / ADR、確定している事実

#### Out of Scope

#### Constraints

#### Open Questions ← 決まったら Decisions へ移して消す

### Phase 1: {名前} `cc:TODO`

#### Acceptance Criteria

- [ ] {条件} — verify: `{コマンド}`
- [ ] {条件} — judge: {判定基準}

#### Tasks

- `cc:TODO` {何をするか} — 対象: `{ファイル}` / 確認: {方法}
```

- 「確認」は「その行を `cc:done` にしてよい根拠」（絞ったテスト / 静的チェック / grep で消えたことを
  見る / 手動観察）。省略可（`確認: なし`）。Phase の AC verify はフェーズ全体の合格判定で、Task の
  確認は実装者がその場で回す自己チェック
- v2 は既存パーサでもそのまま動く（Project 直下の節は無視され、タスク分類と WIP / TODO の注入は
  正しく出た。2026-09-26 に `load-task-state.py` で検証済み）が、「たまたま動く」ではなく正式に扱う。
  `load-task-state.py` は 5 節を認識して Goal（1 行）と Open Questions の件数を SessionStart の注入に
  加え、節内の行をタスク分類から明示的に除外する
- `templates/project/Plans.md`（`orchex init` の雛形）、`/task-state init` / `add-phase`
  （合意済み AC を受け取る引数を追加）、`/handoff`（Goal / Context / Constraints を引き継ぎファイルに
  含める）、ルール `task-memory-usage.md` の書式節を v2 に合わせる。Plans.md を読む他の hook
  （`precompact-dump.py` / `turn-end-summary.py` / `codex_run.py` 等）は v2 で壊れないことをテストで
  確認する

### 3. 発注書の内容モデルと `/order`

Plans.md v2 の Project 節 + Phase の AC + Tasks を共通の内容モデルとし、Issue 本文へは
Goal → 概要、Context / Constraints → 前提、Tasks → 作業内容、AC → 受け入れ条件、Out of Scope → 備考
として写す（`/issue-create` の現行テンプレと対応）。TAKT 向けの別形式は作らず、Issue を `takt add #N`
で渡す。`/issue-create` には「AC 確定済み」の経路を設け、対話で確定した AC を聞き直さない。

### 4. スキルの処置

| スキル                                                                                           | 処置                                                | 理由                                                                                                               |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `preflight`                                                                                      | 廃止                                                | 対話 + `/order` に置換。F14 は廃止で決着                                                                           |
| `startproject`                                                                                   | 廃止                                                | Phase 1〜5 は `/design` + `/order`、Phase 6〜7 は各実行エンジンと重複                                              |
| `issue-fix`                                                                                      | 縮小存続                                            | Phase 4 のレビューを `/review` へ、PR 作成を `/pr-create` へ委譲。meta-harness の `skill:issue-fix` 対象なので残す |
| `design`                                                                                         | 存続                                                | 他プロジェクトで現役。評価セットあり                                                                               |
| `tdd` `pr-create`                                                                                | 存続（軽微修正）                                    | ルーティング表と `--base stage` 例を直す                                                                           |
| `review` `release-readiness` `loop-issue` `review-respond` `handoff` `issue-create` `task-state` | 存続                                                | `loop-issue` の Checker は評価セットと harness コードに結合しているため触らない                                    |
| `codex-system` の knowledge 5 件                                                                 | 廃止                                                | どこからも参照されていない                                                                                         |
| 新設                                                                                             | `/order`、使い分けルール（`.claude/rules/` に配布） | 上記 1〜3                                                                                                          |

### 5. 進め方

1. 評価セットを先に更新して人間レビューを通す（`docs/evaluation/core.md` に Plans.md v2 の観点、
   `docs/evaluation/skills/design-flow.md` の EV-14〜23 を preflight / startproject 廃止に合わせて改訂）
2. 決定に依存しない quick-win を同じ PR に含める（tdd のルーティング表と強制文、design.md の Antigravity 言及。
   startproject の Agent Routing 表は PR #468 で hook 方式に書き換え済み）
3. Plans.md v2（パーサ・雛形・task-state・handoff・ルール・テスト）
4. `/order` と使い分けルール、`/issue-create` の AC 確定済み経路
5. スキルの廃止と縮小、README のスキル表、CHANGELOG
6. facet build の orphan cleanup と配布先 sync の stale 削除で、廃止スキルが消えることを確認する

## 影響

- **後方非互換**: `/preflight` `/startproject` が無くなる。配布先では facet build の orphan cleanup と
  SessionStart 同期の stale 削除で自動的に消える。`/task-state add-phase` の AC ヒアリングは
  「合意済み AC を渡す」経路が加わるだけで、既存の呼び方は変わらない
- **Plans.md**: v2 は追加のみで、既存の Plans.md はそのまま読める。既存 Project に節を足す必要はない
- **追従が必要な箇所**: meta-harness の task-state シナリオ 2 件（「`/preflight` から来た AC 合意済みの
  呼び出し」の文言）、`check-codex-after-plan.py` の「Before /startproject」文言、README のスキル表、
  `orchestra-usage.md` のワークフロー例、design-flow.md の EV-14〜23
- **触らないもの**: `/loop-issue` の Checker とレビュアー選定、`/review` の選定ロジック、
  loop-harness の状態管理
- **残す判断**: TAKT が作った PR に `/review-respond` を当てるかは運用で決める（bot レビューが付く
  場合のみ有効）。`/issue-fix` をセッション内の小修正用に残すかは meta-harness の対象変更と合わせて
  再検討する
