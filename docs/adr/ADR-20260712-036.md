# ADR-20260712-036: Maker 選定を実装可能ロールへ限定し初回結果を state に固定する

- **ステータス**: accepted
- **日付**: 2026-07-12
- **決定者**: yoshihiko

## コンテキスト

`/loop-issue` は Issue title と labels を `detect_agent()` に渡して Maker を選ぶが、同 API は定義順の
先着一致である。タイトルに「要件」「計画」「手順書」等が含まれると編集不能ロールが選ばれ、無人反復が
実装を進めないまま停止条件まで消費する。また各反復で再検出すると、ラベルや設定の変更で Maker が揺れる。

## 検討した選択肢

### 選択肢 A: routing 入力を title + labels に限定するだけ

- メリット: 既存 API を変更しない。
- デメリット: title 自体の偶発一致と反復間の選定揺れを防げない。

### 選択肢 B: negative denylist で非実装ロールを除外する

- メリット: 既知の誤選定を小さな設定差分で防げる。
- デメリット: 新規ロール追加時に既定許可となり、安全境界が拡大する。

### 選択肢 C: positive allowlist と state 永続化を組み合わせる

- メリット: 選定可能範囲を明示でき、初回選定後の反復・フェーズ間の一貫性も保証できる。
- デメリット: 実装可能ロール追加時に allowlist 更新が必要になる。

## 決定

選択肢 C を `issue-loop` の `auto` Maker に限定して採用する。`detect_agent(prompt, allowed_agents=None)`
を後方互換な opt-in API とし、`/loop-issue` だけが `maker.allowed_agents` を渡す。非許可候補は一致しても
飛ばし、次候補または allowlist 内の `maker.fallback_agent` を選ぶ。初回 `run_maker` 完了結果の agent は core が検証して
`state.maker_agent` に一度だけ保存し、以後の反復と `pr_review_response` では再検出せず再利用する。
`issue-loop` の完了結果では `maker.agent` を必須とし、保存後に異なる agent が返された場合も
journal/state 更新前に拒否する。

## 影響

- `allowed_agents=None` の既存呼び出し元は従来の定義順先着一致を維持する。
- 旧 state は `maker_agent=None` として読み込める。
- completed journal からの reconcile も通常 complete と同じ検証・永続化経路を通る。ただし変更前に
  書かれた未選定 state の `maker` キーなし結果だけは受理し、次回 Maker 完了時に選定する。
- 新規 `complete` では `maker.agent` の欠落・空値・型不正・保存済み値との不一致を fail-closed で拒否する。
- custom loop には allowlist 検証・state 固定を適用せず、フェーズごとの `maker.agent` を維持する。
- バグ修正を実装可能な `debugger` は allowlist に含め、`bug` / `error` 等の専門ルーティングを維持する。
- 実装可能ロールを追加・削除するときは `maker.allowed_agents` と評価テストを同時更新する。
