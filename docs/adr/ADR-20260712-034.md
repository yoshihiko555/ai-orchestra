# ADR-20260712-034: scenario 実行基盤を Docker コンテナ + ephemeral credential broker へ移行する

- **ステータス**: proposed
- **日付**: 2026-07-12
- **決定者**: yoshihiko

## コンテキスト

ADR-20260711-033 は「credential broker と cgroup/VM 相当の process containment が実装されるまで
scenario evaluation を fail-closed にする」と決定した。これにより Phase 3 の当初ゴール
（`orchex meta loop` による自動探索）は実行不能となっている。

本 ADR は人間レビューでこの決定を再検討した結果を記録する。再検討で確認した事実:

1. **ADR-20260711-032 がコンテナ案を却下した主因は「macOS の OAuth/keychain 認証を
   そのまま使う」前提だった**。この前提は直後の ADR-20260711-033 自身が破棄しており、
   却下理由は失効している。worktree 統合の課題（linked worktree の `.git` 参照）も、
   同 ADR で設計済みの「ephemeral runtime 内の独立 Git snapshot」方式がコンテナに
   そのまま転用できるため障害にならない。
2. **meta-harness は完全にオンデマンドの CLI である**。資格情報を必要とする処理
   （scenario run / rubric judge / proposer）はすべて `orchex meta loop` / `evaluate`
   プロセスの生存期間内でのみ発生し、コマンド間にはプロセスも API 通信も存在しない。
   したがって broker は常駐デーモンである必要がなく、CLI の子プロセスとして run スコープで
   起動・破棄する **ephemeral 方式**で要件を満たせる。常駐方式はむしろ「使われない時間も
   資格情報を保持するプロセス」を作り、露出時間の点で劣る。
3. **封じ込め要件（`setsid()` 離脱子孫の回収）は Docker の cgroup で構造的に満たせる**
   （`docker rm -f` でコンテナ内全プロセスが確実に終了する）。ADR-033 が SRT ベースで
   要求した cgroup/PID namespace/VM 相当の境界そのものである。

## 検討した選択肢

### 選択肢A: fail-closed を維持する（ADR-20260711-033 の現行決定）

- メリット: 資格情報リスクをゼロに保てる。
- デメリット: Phase 3 のゴールが無期限に先送りされる。常駐 broker + containment という
  過大に見積もられた前提に基づいている。

### 選択肢B: Docker コンテナ + ephemeral credential broker（採用・本命）

- 構成: scenario の `claude -p` を Linux コンテナで実行し、資格情報はコンテナ外
  （ホスト側 CLI の子プロセスとして起動する reverse proxy）だけが保持する。
  コンテナ内 CLI は `ANTHROPIC_BASE_URL` で broker へ向け、broker が実 OAuth ヘッダを
  注入して `api.anthropic.com` へ転送する。
- メリット:
  - コンテナ内に盗める資格情報が**存在しない**（構造的な持ち出し不可）。
  - 候補ができる悪用は「run の間だけ broker 経由で API を使う」ことに限定され、
    run 終了（= broker 消滅）で能力ごと消える。
  - cgroup により `setsid()` 離脱を含む全子孫を確実に回収できる。
  - egress は Docker internal network で broker のみに限定できる。
  - judge（`claude --bare`、tool-less）も broker から認証を受けられるため、
    API キー未 provision の OAuth 環境でも judge が動作する（ADR-033 が生んだ
    judge fail-closed 問題も同時に解消）。
- デメリット / 未検証リスク:
  - `ANTHROPIC_BASE_URL` 差し替え + OAuth Bearer ヘッダ注入で Claude CLI が正常動作するかは
    **スパイク S1 で実証が必要**（本 ADR の承認後・実装前の必須ゲート）。
  - Docker イメージ整備（Claude CLI の version pin 同梱）と macOS 上の Docker 依存が増える。

### 選択肢C: Docker コンテナ + L1 最小化 OAuth（フォールバック）

- 構成: 選択肢B と同じコンテナ基盤で、資格情報は「access token のみ・refresh token を
  canary に置換した最小化 credentials ファイル」としてコンテナ内 ephemeral HOME に置く。
  Phase 2 proposer で承認済みの L1（価値最小化）+ L2/L3（出力経路検知）と同一のリスク基準。
- メリット: broker 実装が不要で最小工数。egress 制限（api.anthropic.com のみ）+
  コンテナ削除により、token の**生きた利用**（コンテナ内プロセスによる悪用）は run
  実行時間に限定される。
- リスクの正確な評価: コンテナ削除は token 自体を失効させない。成果物・ログ経由で
  token が持ち出された場合の防御は L2/L3 の**検知精度に依存**し、構造的防止ではない
  （これが選択肢B との本質的な差）。
- デメリット: 持ち出し防止が構造保証ではなく検知ベースになる。`claude --bare` judge は
  API キー必須のため動作せず、judge は clean-home の非 bare tool-less `claude -p` 方式の
  検証（スパイク S2）が別途必要。
- 位置づけ: スパイク S1 が失敗した場合のフォールバックとして採用する。

### 選択肢D: 評価専用 API キー

- Console で予算上限付きの専用キーを発行する案。漏洩時の被害が明確に capped される。
- **却下**: サブスクリプションと別に従量課金コストが発生するため（利用者判断）。

## 決定

選択肢B（Docker + ephemeral broker）を本命として採用し、スパイク S1 の失敗時は
選択肢C（Docker + L1 最小化 OAuth）へフォールバックする。

- **実行基盤**: scenario run は Linux コンテナで実行する。`docker run --rm` +
  `--pids-limit` / `--memory` / `--cpus` を必須とし、run 終了・timeout・中断のすべての
  経路で `docker rm -f` によりコンテナごと全子孫を回収する。多層防御として
  `--cap-drop=ALL` / `--security-opt=no-new-privileges` / read-only rootfs（書き込みは
  対象 mount と tmpfs のみ）/ non-root user を適用し、Docker socket は決してマウントしない。
- **ネットワーク**: 候補コンテナは Docker internal network に接続し、外部 egress を
  持たない。到達可能なのは broker（選択肢B）のみとする。**broker 自身の egress も
  `api.anthropic.com` に限定**し、任意ホストへの中継（open proxy 化）を構造的に禁止する。
- **資格情報**: broker は `orchex meta loop` / `evaluate` プロセスの子として run スコープで
  起動し、正常終了・timeout・例外の経路では即時破棄する（`evaluate.lock` と同じ with
  ブロック規律）。SIGKILL・ホストクラッシュ等の異常経路では即時性は保証できないため、
  アイドルタイムアウトによる自殺 + 次回起動時の stale cleanup で**有限時間内の破棄**を
  保証する。親プロセス監視の具体方式は broker の配置（host プロセス / sidecar コンテナ）に
  依存するためスパイク S3 で確定する。実 OAuth は broker プロセスのみが保持し、コンテナへは
  いかなる形でも渡さない。
- **フォールバック（選択肢C）時**: 最小化 credentials の生成は proposer L1 実装を流用し、
  canary 検知（L2）と secret scan（L3）を run artifacts / ledger 経路に適用する。
- **filesystem 境界**: ADR-20260711-032 で設計した SRT profile の許可リスト
  （候補 worktree rw / runtime ro / 独立 Git snapshot / 固定 instruction）は、コンテナの
  mount 設計としてそのまま転用する。oracle の read-only・symlink 非追従・サイズ上限
  （`artifact_reader`）は変更なく維持する。
- **fail-closed 原則の維持**: `evaluate.isolation.execution_backend: docker` は、
  スパイク S1〜S3 の全 PASS と封じ込め検証テストの整備を確認してから有効化する
  （ADR-033 の「名前を設定しただけでは利用可能扱いにしない」を踏襲）。**部分 PASS では
  有効化しない**。Docker daemon 不在・イメージ pin 不一致・broker 起動失敗は非隔離実行へ
  降格せず run error とする。
- **judge**: 選択肢B では `claude --bare`（tool-less）を broker 経由で実行する。
  選択肢C では clean-home 非 bare tool-less `claude -p` をスパイク S2 で検証の上採用する。
  Codex CLI を judge backend にしない決定（ADR-033）は維持する。

## ガバナンス上の補足

ADR-20260711-032 / 033 は実装エージェント（Codex CLI）が起草し、人間レビューを経ずに
`accepted`・決定者記載で記録されていた。本 ADR の人間承認をもって 032 / 033 の内容の
正式レビューに代え、033 は本 ADR で supersede する（032 の filesystem 境界設計・
fail-closed 原則・oracle 隔離は本 ADR に引き継がれて存続する）。以後、実装エージェントは
ADR を `proposed` でのみ起草し、`accepted` への遷移は人間が行う。

## 影響

- スパイク S1〜S3 の PASS 後、`execution_backend: docker` の実装をもって scenario
  evaluation と Phase 3 loop の fail-closed が解除される。
- ADR-20260711-033 は superseded となる（本 ADR 承認時に status を更新する）。
- `docs/design/meta-harness-detailed.md` §8（スパイク記録）/ §12（scenario 実行・隔離）/
  §3-3（judge backend）/ §14（コスト・予算）を本 ADR に追従して改訂する。SRT allowlist の
  「転用」は方針であり同等保証ではないため、設計改訂時に**具体的な mount table**
  （read-only mount / tmpfs / symlink 挙動の再確認）へ翻訳して明文化する。scenario 終了後の
  oracle の実行機構（SRT read-only profile を継続するか、コンテナ内で再構成するか）も
  同改訂で確定する。
- config に `evaluate.isolation.execution_backend: docker` と broker 関連キー
  （ポート範囲・タイムアウト等）を追加する。既定は引き続き `none`（fail-closed）とし、
  検証完了後に既定を切り替える。
- SRT による proposer 隔離（Phase 2）は影響を受けず存続する。
