# ADR-20260703-029: 評価セット（docs/evaluation/）の導入

- **ステータス**: accepted
- **日付**: 2026-07-03
- **決定者**: yoshihiko

## コンテキスト

ai-orchestra のテストコードは大部分が AI によって書かれており、コード量が多く人手レビューが追いついていない。
テストの妥当性をテスト自体に依存させると「実装の都合を追認しただけのテスト」を検出できない。
各パッケージについて「正しい状態とは何か」を自然言語で先に定義し、既存・将来のテストをその定義と突合して
判断できる基準が必要になった（Notion タスク「ai-orchestra の評価セットを作成する」起点）。

## 検討した選択肢

### 選択肢 A: docs/evaluation/ に評価セットを新設（パッケージごと 1 ファイル）

- メリット: 人が読む判断基準として一元管理できる。テンプレート（`_template.md`）と共通観点（README.md）で統一できる。CODD の kind 語彙を拡張せずに導入できる
- デメリット: 実装・テストと乖離しうる（陳腐化リスク）。運用ルールで補完が必要

### 選択肢 B: CODD 管理下（codd: frontmatter 付き）で依存グラフに組み込む

- メリット: validate / impact による整合性検証の対象になる
- デメリット: codd の kind 語彙（requirement/design/adr/plan/rule/instruction）に評価セット用の kind がなく、スキーマ拡張が先に必要。導入コストが高い

### 選択肢 C: 既存テストのカバレッジ計測（coverage 数値）のみで品質担保

- メリット: 自動化しやすい
- デメリット: 「テストが仕様に沿っているか」は計測できず、実装追認テストを排除できない（本タスクの動機を満たさない）

## 決定

選択肢 A を採用する。構成は以下の通り。

1. **評価セット本体**: `docs/evaluation/<pkg>.md` × 全 14 パッケージ。責務定義 / 入出力・副作用 / 評価観点（`EV-NN`、正常・異常・境界 × must/should、仕様根拠付き）/ 類型別観点（hook 型・CLI ツール型・スキル型）/ テストレビュー判断基準
2. **ギャップの扱い**: テストとの突合結果（ギャップ）は評価セットに恒久記録せず、パッケージ単位の GitHub Issue（チェックリスト形式）で追跡する。突合マトリクスはレビュー時の一時成果物とする
3. **運用ルール**: `.claude/rules/evaluation-set-policy.md`（facet: `evaluation-set-policy`）で「テスト改修時は該当評価セットと突合し、must 観点のギャップゼロで完了する」ことを完了条件化する
4. **自動化**: テスト変更時に突合を促す hook 化は Issue #123 で追跡する（本決定のスコープ外）

CODD 統合（選択肢 B）は評価セット運用が安定した後の将来課題として残す。

## 影響

- テストコードの追加・変更は、該当パッケージの評価セットとの突合が完了条件になる（`evaluation-set-policy` ルール）
- パッケージの仕様変更時は評価セットを先に更新し、人間レビュー後に「最終レビュー日」を更新する運用になる
- 新規パッケージ追加時は評価セットの同時作成が必要になる
- AI 生成テストのレビューは `docs/evaluation/README.md` の共通 6 基準 + 各パッケージ固有基準で行う
- 突合で見つかった既存ギャップ・仕様疑義はパッケージ別 Issue として登録され、後続対応の入力になる
