# ADR-20261028-060: 必須 routing と任意の CLI 相談助言を分離し、提案条件・通知範囲を絞る

- **ステータス**: accepted
- **日付**: 2026-10-28
- **決定者**: yoshihiko
- **承認根拠**: ユーザーが A 案と追加レビュー対応を承認
- **関連**: ADR-20260223-003（実装委譲と相談 hook のデッドロック）、ADR-20260926-056（config-driven routing とスキル固有の実装委譲）

## コンテキスト

hook の出力は advisory なのに、compliance ルールは編集・Web 調査の保留と追加相談を必須としていた。
`core` / `config` / 通常の class・文字数や一般的な検索語でも発火し、相談済みの作業やサブエージェント内で同じ助言を繰り返す。
この過剰な相談を減らしても、明示的な実行先やスキル固有の実装委譲を省略できるようにはしない。

## 検討した選択肢

### 選択肢 A: 必須 routing を維持し、助言を任意化・限定する

- メリット: 実行契約を維持したまま、不要な保留・再相談・重複通知を減らせる
- デメリット: 意味的な相談済み・助言の有用性はオーケストレーターが判断する必要がある

### 選択肢 B: 広い発火条件と相談必須の compliance を維持する

- メリット: 相談機会を広く確保できる
- デメリット: 軽微・適用外の操作にも保留や追加相談を要求し、委譲先でも相談が再帰する

## 決定

ユーザー承認に基づき **選択肢 A** を採用する。

1. **必須と任意を分離する**。`[Resolved Routing]` / `agents.<name>.tool` とスキル固有の委譲義務は必須のまま。
   `[Codex Suggestion]` / `[Antigravity Suggestion]` は任意助言とし、操作の保留・追加相談・採否の毎回の説明を義務付けない。
   相談済み・軽微・適用外なら続行できる。変更の累積数だけによる一律の委譲義務は助言ルールから外すが、
   `review-respond` 等の実装委譲は維持する。相談時は既存の config 解決と sandbox 安全条件に従う。
2. **Codex の編集前提案を設計・契約に限定する**。`DESIGN.md` / `ARCHITECTURE.md` の basename、
   `design/`・`architecture/`・`schema/`・`schemas/`・`interfaces/`・`contracts/` 等の明確な設計パス、
   `interface` / `abstract class` / `Protocol` / `ABC` / `@abstractmethod` 等の契約宣言の変更を対象とする。
   ただし TS/JS の `interface` は通常パスではコードシグナルとせず、設計パス内の変更としてのみ対象とする。`Props` という名前だけでは除外しない。
   `core` / `config` / `model`・通常の class・文字数・`src/` だけでは発火しない。
   Edit の old/new で宣言が同じならコードシグナルを抑制する。設計パス以外のソース（`.py` / `.pyi` / `.ts` / `.tsx` / `.js` / `.jsx` / `.java`）への Write は、ディスク上の旧本文と新本文の宣言を比較する（新規ファイルの旧本文は空）。
   旧本文が読取不能・大き過ぎ・非通常ファイル・非 UTF-8 の場合は任意通知を抑制し、exit 0 とする。設計パスは旧本文比較と独立に判定する。プロジェクト外の除外は維持する。
   同じ契約ヘッダ内のメソッド変更や同じ `@abstractmethod` の個数増加等の既知の未検出境界は、[評価セット](../evaluation/codex-suggestions.md)に明記し、今回は検出範囲を拡大しない。
3. **Antigravity は調査意図で提案する**。WebSearch の `query` / WebFetch の `prompt` に比較・選定・移行等の意図がある場合に限定する。
   明確な選択比較（`vs` / `vs.` / `versus` / `違い` / `どっち` / `which is better`）も対象とする。文字列等の演算比較や単純な migration エラー検索は除外するが、明確な選択比較が同居すればそちらを優先する。
   URL・長さ・documentation / library / guide / example / best practice 等の一般語だけでは発火しない。
4. **共通 helper で通知を抑制する**。トップレベルの `agent_id` が非空の文字列（`str`）の場合だけ、サブエージェント／インプロセス teammate 内と判定して提案を抑制する。
   `agent_type` は `--agent` で起動したメインにも付くため、単独では抑制しない（出典: [Claude Code 公式仕様 — Common input fields](https://code.claude.com/docs/en/hooks#common-input-fields)）。
   `tool_input.subagent_type` は呼出先なので判定に使わない。`session_id` があれば project / worktree 別に、
   同一 session・同一ファイル（Codex）または正規化した同一質問（Antigravity）に 1 度だけ通知する。
5. **状態は最小限にする**。両 hook の config・対象範囲・marker に使う project / worktree は、環境変数 `CLAUDE_PROJECT_DIR` が非空ならそのルートを使い、未設定または空の場合だけ hook 入力の `cwd` で解決する。
   その `.claude/state/suggestions/` に session / 対象を hash 化した空 marker のみを置く。
   質問本文・URL・生の識別情報は保存しない。状態書き込み失敗は無出力・exit 0、`session_id` 欠落時は state を作らず呼び出しごとの助言とする。
   marker の自動削除は今回追加しないため、終了後も session ディレクトリが残る。cleanup は将来課題とする。
   **通知済みは相談済みではない**。意味的な相談済み判定はオーケストレーターの責務とし、hook は transcript を解析しない。
6. **after-plan は変更しない**。`check-codex-after-plan.py` の発火条件と既存の advisory を維持し、今回の編集前・Web 調査前の通知抑制を適用しない。

## 影響

- compliance の強制相談と広い発火条件を変更するが、CLI 無効化・`.local.yaml` 上書き・sandbox 安全条件は維持する。
- 導入済み環境は更新後の facet build で新しいルールを反映する。必須 routing を無視してよいという移行ではない。
- hook 評価は明確なシグナル・通知の分離・空 marker・状態書き込み失敗を確認し、オーケストレーターの任意判断とは分ける。
- 次回監査では researcher の指定 CLI 試行率と、メインの任意提案の採用率を分離する。サブエージェント内の通知は `agent_id` で抑制され、researcher の `agy` 実行は `researcher.md` の指示が担うため、hook 通知数を researcher の遵守率の代用にしない。
- 旧 ADR 全体は置き換えない。ADR-003 の相談 hook に関する例外・累積数の扱いは本 ADR の境界に読み替え、
  明示 CLI 実行とスキル固有の委譲に関する決定は維持する。CODD 上は全体置換ではないため `references` とする。
