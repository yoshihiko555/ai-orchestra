# ADR-20261103-063: 失敗から教訓候補を自動で蓄積し、昇格候補の提示までを自動化する（ADR-057 の部分 supersede）

- **ステータス**: accepted（2026-11-03。実装は PR #537〜#540 と、`/lessons`・`/review-respond` の連携・memory-layers の改訂の PR）
- **日付**: 2026-11-03
- **決定者**: yoshihiko
- **承認根拠**: 2026-11-03 の対話で、失敗の定義（4 種の合図）、教訓候補の置き場（ローカル・root 集約）、教訓化の方式（セッション終了時の LLM を主、`/review-respond` を補）、昇格の自動化の範囲（提示まで）、昇格先（AGENTS.md の記述欄・プロジェクト独自の `.claude/rules`・ガード）、既定で無効の教訓化、モデル（sonnet）、非対話セッションの除外、伏せ字の実装（audit の強化版）を利用者が選択
- **関連**: ADR-20260927-057（§対象外の「fail-logs を昇格の入口にすること」「昇格・棚卸しの自動化」と、§決定 4 の「まず auto-memory に書く」「昇格の書き込み先は記述欄だけ」を部分 supersede。記憶の層の分担という決定自体は有効のまま）、ADR-20260612-025（fail-logs 新設）、ADR-20260630-027（再発失敗サマリーの注入）、`docs/requirements/fail-logs.md`、`docs/design/fail-logs.md`

## コンテキスト

fail-logs は失敗を記録し、再発をセッション開始時に注入するところまでしかない。2026-11-03 時点の実データでは、蓄積 433 件はすべてテスト・lint の出力パターン検知で、ツール呼び出しの失敗は記録経路に届いていなかった（hook を `PostToolUse` にしか登録しておらず、失敗は `PostToolUseFailure` に届くため）。

一方、auto-memory に残っている教訓 27 件の出どころは、ユーザーの訂正 8・その場のツールエラー 7・エラーの出ない副作用や後から判明した誤り 8・CI とレビュー 3・実験 1 で、fail-logs から生まれたものは 0 件だった。教訓は「失敗 → 原因 → 回避策」の組から生まれ、失敗の回数だけからは生まれない。

ADR-20260927-057 は、全 CLI に必要な知見を「まず auto-memory に書き、依頼されたときの手動の棚卸しで AGENTS.md の記述欄へ昇格する」と決め、fail-logs を昇格の入口にすることと、昇格・棚卸しの自動化を対象外にしていた。この結果、教訓は人が「ルールにして」と頼んだときだけ残り、auto-memory は Codex / Antigravity に届かないままになっている。

## 検討した選択肢

### 何を貯めるか

- **A: 失敗イベントとは別に「教訓候補」（事象・原因・回避策・根拠・再発回数・重大度・対象範囲・状態）を貯める（採用）**
- B: 失敗イベントの再発回数をそのまま昇格の基準にする: TDD の red など、回数が多くても教訓のない失敗が上位を占める

### いつ・誰が教訓にするか

- **A: セッション終了時に裏で LLM が、セッションの記録と失敗イベントから作る（主）（採用）**: 人の訂正やエラーの出ないずれは、セッションの記録にしか現れない
- **B: `/review-respond` で採用した指摘を、実行中のセッションが候補にする（補）（採用）**
- C: 失敗の直後に hook がエージェントに記録を促す: エージェントが従うかに左右される
- D: 週次のバッチ: 直した経緯が失われる

### 教訓化の LLM の呼び出し方

- **A: `claude -p --restricted --tools "" --strict-mcp-config --no-session-persistence --settings '{"disableAllHooks": true}'`（採用）**: OAuth のまま動き、道具・hook・MCP を持たない。2026-11-03 に動作を確認した
- B: `claude -p --bare`: OAuth を読まず API キーが必須のため、サブスクリプションの利用者が使えない
- C: `cli-tools.yaml` の routing で Codex / Antigravity を使う: どちらもシェルを持つため、信頼できない入力（セッションの記録）を読ませる用途に合わない

### 教訓候補の置き場

- **A: `.claude/logs/fail-logs/lessons.jsonl` に、出来事を追記するだけの台帳として置く（採用）**: root worktree に集約され、gitignore と所有者限定の権限が既にある。追記だけなので同時更新で壊れない
- B: auto-memory: Claude Code 専用で、配布する hook から書けない（ADR-057 決定 5）
- C: git 管理のファイル: 未承認の候補でコミットが増える

### 昇格をどこまで自動にするか

- **A: 基準を超えた候補の提示までを自動にし、承認と書き込みは人が行う（採用）**
- B: 昇格の PR の作成まで自動: 承認前の差分が溜まる
- C: 蓄積だけを自動にし、棚卸しは依頼されたときだけ: 繰り返し現れる教訓に気づく契機がない

### 昇格先

- **A: AGENTS.md の記述欄・プロジェクト独自の `.claude/rules`・ガード（Issue を作るまで）（採用）**: Claude Code 固有の教訓（sandbox の制約など）は `.claude/rules` が適所。ルールより機械で止める方が効く教訓はガードにする
- B: AGENTS.md の記述欄だけ（ADR-057 決定 4 のまま）: Claude Code 固有の教訓まで全 CLI に配ることになる
- C: skill-evolution の lessons も含める: スキル単位の仕組みで、今回の横断的な教訓とは単位が合わない

## 決定

1. fail-logs を「失敗を貯め、そこから昇格させる」パッケージと位置づけ、失敗イベントとは別に教訓候補を `.claude/logs/fail-logs/lessons.jsonl` に貯める。教訓候補は memory-layers ルールの新しい層として扱う
2. ツール呼び出しの失敗（`PostToolUseFailure`）と auto mode の拒否（`PermissionDenied`）も失敗イベントとして記録する
3. 教訓化は、セッション終了時に hook が裏の処理を起動し、裏の処理が LLM を使わない前段判定で合図を確かめてから、§選択肢 A の方法で LLM を呼んで行う。既定で無効とし、設定で有効にした環境でだけ動く。既定のモデルは sonnet。非対話のセッションは既定で対象外
4. `/review-respond` で採用した指摘のうち一般化できるものと、作業中にエージェントが得た落とし穴・回避策は、同じ置き場に候補として追加する（auto-memory には書かない）。利用者の好みと長期の事実は、引き続き auto-memory に書く
5. 基準（異なるセッション・PR での再発回数、または重大度「重大」）を超えた候補を、セッション開始時に提示する。重大度「重大」で再発回数 1 の候補は、文面を出さずに件数と ID だけを示す（LLM が作った文を、再発の裏付けも人の確認もなしに文脈へ入れないため）。昇格の承認と書き込みは、人が昇格スキル（`/lessons`）で行う
6. 昇格先は AGENTS.md の記述欄・プロジェクト独自の `.claude/rules`・ガード（Issue の作成まで）とする。AGENTS.md の管理ブロックと orchex が配布する rule には書き込まない。昇格先に書く文面は、書き込む直前に伏せ字を再びかけ、要約せずに承認画面に示す。公開リポジトリ・Issue へ書くときは明示的に確認する
7. LLM に渡す内容・候補の置き場の内容・新しく記録する失敗イベントは、audit の強化版マスキングで伏せてから切り詰める。読み込めなければ LLM に渡さない

### 受け入れるリスク

- 管理者設定（managed settings）の hook は、教訓化セッションの中でも止められない
- `distill.enabled` はプロジェクトの `fail-logs.local.yaml` でも有効にできる。悪意のあるリポジトリが費用を発生させる余地は、1 日の上限と 1 回の費用の上限で抑える
- セッションの記録（transcript）の形式は公開仕様ではない。解析できないときは LLM を呼ばずに終了し、合成した記録のテストで形式の変化を検知する
- 既存の `PostToolUse` 経路の伏せ字は、互換性のため簡易版のまま残す（強化版への載せ替えは別途行う）
- 昇格・却下・Issue の作成などの人の承認は `/lessons` の AskUserQuestion で行い、状態を変える専用の入口（`lessons_admin.py`）を実行するときの Bash の許可の確認を二重の歯止めにする。auto mode ではこの確認が人に届かないことがあり、利用者がこれを許可リストに入れた場合も歯止めにならない（README と `/lessons` で案内する）。書き込みは worktree の差分・PR・Issue として残るため、事後に検出できる
- `lessons_cli.py` の主体（`--actor`）と、レビュー経路の PR の根拠は自己申告である。注入されたエージェントが偽の根拠で提示の基準に届かせる余地がある。影響は無害化された見出しが提示されることに限られ、昇格には人の承認が要る
- サンドボックスで root に書けない環境では、候補の追加だけを作業中の worktree に退避し、hook が取り込む。退避からは状態の変更を受け付けず、退避が持ち込んだ根拠は再発回数に数えない

## 対象外

- Codex 直接実行・TAKT の失敗の収集
- 人の承認なしの昇格
- auto-memory の自動書き換え（ADR-057 決定 5 は有効のまま）
- skill-evolution の lessons への昇格
- 異常終了したセッションの回収、候補の置き場の肥大化への対処

## 影響

- memory-layers ルール（`facets/instructions/memory-layers.md`）を改訂する。ADR-057 に部分 supersede の注記を足す
- fail-logs に hook 2 本（教訓化の起動、提示）と裏の処理・CLI・昇格スキルが加わる。既定の設定では LLM を呼ばないため、既存の配布先が同期しただけで費用は発生しない
- 評価セット `docs/evaluation/fail-logs.md` と `docs/evaluation/skills/review-respond.md` を実装より先に改訂し、昇格スキルの評価セットを新設する
- 教訓化を有効にした環境では、セッション終了ごとに最大 1 回の LLM 呼び出しが裏で発生する（1 日の上限あり）
