# ADR-20260814-049: routing-config は検証専用 target と位置づけ、適応度関数の分解能は skill target の loop 運転で実証する（ADR-048 の部分 supersede）

- **ステータス**: accepted
- **日付**: 2026-08-14
- **決定者**: yoshihiko
- **関連**: Issue #364、Issue #254（skill 系 target 拡大）、ADR-20260814-048（部分 supersede 対象）、
  `docs/design/meta-harness-proposer-routing-unlock.md`（§4-3 / §5 C-9 / §7 Phase B）、
  Phase A ledger バックテストと Codex 設計レビュー 2 巡（2026-08-14 実施、本文に要点を記録）
- **codd 注記**: codd グラフ上は ADR-20260814-048 への依存を `references` とする（codd の
  `supersedes` は全体置換の意味論のため。実際の撤回範囲は本文決定 5〜7 参照）

## コンテキスト

### 第 1 の発見: own suite は品質軸を持てない（§4-3 停止条件の発動）

ADR-048 は「行動ベースシナリオ + gate/graded critical 分離で quality を config の関数に
する」ことを決定したが、実装形式の調査（スパイク着手前・支出 $0）で以下が確定した:

- routing-config own suite のシナリオは**実 backend（codex/agy）を一切呼ばない**。
  実行者は常に同一の Claude（`allowed_tools: [Read, Write]`、Bash なし）で、materialized
  config から tool を解決し「解決値ごとの決定論的タスク」を実行、oracle が
  `get_agent_tool()` で期待値を**独立再計算して厳密一致**を要求する（§4-3 の実装そのもの)
- この実行モデルで config 依存の品質差を作る経路は (i) シナリオへの作為的な難易度差の
  埋め込み（設計者の選好のハードコード。loop は我々の意見を「発見」するだけになる）か
  (ii) 環境アーティファクト（コンテナ内で codex は常に不可用 → 「全て claude-direct が
  正解」というコンテナ環境の真実の学習）しかなく、いずれも不正な信号である
- §4-3 の事前登録された停止条件「意味のある品質信号に実 codex/agy 実行が不可欠と判明
  した場合は、network/backend 設計変更が必要なため実装を停止する」に該当する

### 第 2 の発見: own suite はコスト軸も持てない（Codex レビュー Blocker + バックテスト）

品質軸の代替として「routing-config をコスト軸 target とし、C-9 ペア評価 + C-2 緩和で
コスト有意差の世代交代を認める」中間案を設計・レビューしたところ、Codex 設計レビューが
**構成妥当性の Blocker** を指摘し、コード事実と Phase A ledger バックテストで裏付けられた:

- own suite の cost が測るのは「シナリオを駆動する Claude 自身の実行コスト」であり、
  解決値ごとの分岐タスクの長さという**シナリオ設計上の artifact**。routed backend は
  呼ばれないため、本番ルーティングのコスト（どの backend にいくら払うか）は一切
  反映されない。`codex.model` を将来解放しても own suite にモデル単価差は現れない
- Phase A ledger バックテスト（963 行、routing-config run 188 件、支出 $0）: own suite
  コストの変動係数 CV ≒ 1.3%、現実的サンプル数でのペア検出限界 2×SE ≒ 2.1〜2.8%。
  **Phase A 全候補（baf0/96e5/7ccc/e3b8）の baseline とのコスト差は ±2% 未満のノイズ域**
  で、仮に C-9 があっても世代交代は 1 件も発生しなかった（= C-2 の凍結判断は正しく
  機能していた）
- **記録訂正**: 「7ccc は最安 -2.2%」という従来記録は ledger 実測と矛盾する（own suite
  +1.0% / holdout +2.2% とむしろ割高。frontier の cost_mean は直近 1 サイクルの点推定で
  複数サイクル平均と ~1% 乖離する）。7ccc の昇格は「品質同点 frontier からの human 選択」
  として正当だが、コスト削減の実証ではなかった

### 帰結: routing-config は最適化 target ではない

現行実行モデルの routing-config own suite は**品質・コスト両軸とも本番の真実を反映する
最適化信号を持たない**。この target の正当な役割は「config patch の妥当性ゲート
（materialization・layering・回帰非破壊・解決規則の検証 — #341 修正で機能している）+
human 判断による promote」である。一方、**#364 の目的「適応度関数が品質改善を発見し
続けられる状態」は skill target では既に正直に成立し得る**: issue-fix suite は実タスク
実行で quality 65〜100 の実分散を持ち（PR #360/#361 較正後の実測。fail run 含む。適格
run 間の分散の由来確認は決定 4 の前提条件参照）、loop は target
汎用（`_validate_target` は suite が読める任意の target を受理）、proposer の facet
overlay 経路は claude-harness target で実機 smoke 済み（2026-07-11）。

## 検討した選択肢

- A′: C-9 ペア評価 + C-2 コスト軸緩和を続行 — Codex レビューの統計設計指摘
  （AB/BA カウンターバランス、n=3 の検定力不足、収束条件との競合、ペア比較の
  Pareto 非推移性等）に対処する重い設計をしても、**Blocker（構成妥当性）により
  routing-config に最適化対象が存在しない**ため、ペイオフが空。棄却
- B: 実 backend 実行のためのインフラ拡張 — egress 拡大 + サードパーティ CLI の
  資格情報ブローカリングの再設計。routing-config の両軸を本物にする唯一の道だが
  規模が大きく、#254 側で実需要が生まれた時に合流させるのが妥当。先送り
- C: 選好テーブル oracle — 循環的で proposer が自明に gaming 可能。棄却
- **D（採用）: 正直化 + skill target での実証** — routing-config を検証専用 target と
  明文化し、分解能の実証は quality が本当に変動する skill target の loop 運転で行う

## 決定

1. **routing-config を「検証専用 target」と位置づける**: own suite は config patch の
   妥当性ゲートとしてのみ機能する。**C-2（quality 厳密優越 = コスト単独勝ちの禁止、1e-6
   数値衛生ガード付き）は維持**し、コスト単独の自動世代交代は発生しない。ただし品質差に
   よる dominance は機構上残る。routing-config の own suite における適格候補間の品質差は
   自己申告 penalty 等、本番ルーティングと無関係な信号のみから生じるため、**品質差
   dominance による世代交代が観測された場合は改善ではなく異常（信号汚染）として扱い、
   human レビューで原因を確認する**。promote は従来どおり human ゲートの判断（品質同点
   frontier からの選択を含む）で行う
2. **C-9 ペア評価と C-2 緩和は実装しない**。ただし将来の再開に備え、設計 doc に
   以下を付録として記録する: (a) 同一バッチ再評価型ペア評価の設計骨子、(b) Codex
   レビューが要求した成立要件（AB/BA カウンターバランス、スイート合計単位のペア観測、
   逐次多重比較の誤り制御、ペアレコードの鮮度スコープ拡張、incumbent 固定方式による
   非推移性回避）、(c) バックテスト較正値（own suite CV ≒1.3%・2×SE ≒2.1%・相対床
   1.5〜2.0%）、(d) **再開条件 = 実 backend 実行（選択肢 B）または本番テレメトリにより
   本番の真実を反映するコスト信号が成立すること**
3. **ADR-048 の生存決定の実装は継続する**（全 target 共通の loop 正しさのため）:
   convergence 判定修正（候補を含む前の best と比較）+ `loop_state.non_holdout_summary`
   の `critical_pass` 集約を verdict 基準へ + dominance の数値衛生ガード（1e-6）
4. **#364 の完了条件は skill target の loop 再運転で満たす**: 第一候補
   `skill:issue-fix`（train + holdout 整備済み・quality 65〜100 の実分散実証済み）で
   noop baseline を bootstrap し、loop を再運転（総枠 $40）。Issue 原文の完了条件
   「divergence 以外の停止または品質差のある frontier の形成」をこの target で実証する。
   ただし停止理由が `converged` の場合は、品質改善の実体（best の更新または品質差の
   ある frontier）を伴うときのみ完了根拠とする（品質同点候補の連続による空虚な
   converged は完了根拠にしない。決定 6 と同じ論理）。
   skill target の loop・propose（facet overlay 候補）は初運転のため、運用上の未知数が
   出た場合は較正・数行修正は直接 PR、設計判断を伴うものは Issue 化する（既存方針）。
   - **loop 再運転の前提条件（品質分散の由来確認）**: 「quality 65〜100 の実分散」は
     fail run を含む値であり、適格（verdict=pass）run 間の品質差が現行 suite では
     自己申告 penalty（ambiguities/discretion_fills/retries）のみから生じることが
     指摘されている（自己採点系 reward hacking〈脅威 A5〉の面があり、loop が
     「自己申告をゼロへ寄せる候補」を改善と誤認するリスク）。よって loop 再運転前に
     ledger 分析（$0）で適格 run 間の品質分散の由来を確認し、独立 oracle 由来の分散が
     確認できない場合は、suite の品質項に独立 oracle 由来の段階評価を導入する設計
     （gate/graded 分離の skill target 適用の新規設計を含む。決定 5 で予告した
     「必要性が再浮上した場合」に該当）を先行させる。この設計が必要になった場合は
     別 ADR とする
   - **loop 再運転の前提条件（noop baseline の holdout 必須化）**: `skill:issue-fix` の
     noop baseline bootstrap は train 評価に加えて **holdout 評価（`repeat_frontier` 回）を
     同一 evaluation として完了させることを loop 開始前条件とする**。baseline の holdout
     quality が無いと `_retire_if_overfit` が常に False を返し、過学習ガードが無効化される
   - **総枠 $40 の性質**: loop の `budget_usd` は iteration 開始前の予測チェックであり、
     事前強制の hard cap ではない。初回 iteration は予算が残っていれば無条件開始され、
     issue-fix 系は train 最大 $15 + frontier 入り後 holdout 3 repeat で単一 iteration が
     $60 級に達し得る。$40 は予測目安として扱い、運転時は `budget_usd: 40` を設定した上で
     ledger の累積コストを人間が監視し、超過が見えた時点で中断（`--resume` 可能）する
     運用とする。事前強制（残額の attempt 上限への伝播）は必要になれば Phase 3 実装の
     検討事項
5. **ADR-048 の以下の撤回を維持する**: gate/graded critical 分離の実装（EV-103 撤回。
   skill target の suite 設計で必要性が再浮上したら新規に設計）、行動ベース品質分解能
   シナリオの routing-config への追加、較正スパイク（バックテストで代替済み）、
   勝者の呪い対処の検討
6. routing-config の loop 運転は今後行わない（最適化信号がなく、**意味のある改善を
   実証できない**ため運転コストが無駄になる）。停止の仕方も divergence とは限らない:
   既定値では品質 100 同点の適格候補が 2 回続くと divergence 判定（3 回）を待たずに
   `converged` が成立し得る。この**空虚な converged は #364 完了条件「divergence 以外の
   停止」を見かけ上満たすが、改善の実証ではないため完了根拠にしない**。loop の対象は
   skill 系 / claude-harness target とする
7. 副次発見の記録（別 Issue 起票候補、本 ADR スコープ外）: `frontier_updated` の
   `dominated` リストは「Pareto 支配」と「ineligible（fail/error）」を混在させており、
   Phase A の frontier 出入りの大半は holdout フレーク由来の ineligible 化だった

## 影響

- 実装スコープは決定 3 の生存分のみに縮小: `lib/loop_cli.py`（convergence 比較基準）、
  `lib/loop_state.py`（`critical_pass` 集約の verdict 基準化）、
  `lib/meta_harness_common.py`（`_dominates` の 1e-6 ガード）、対応テスト、
  `docs/evaluation/meta-harness.md` の突合
- evaluator_hash が変わるため、loop 運転前に対象 target（skill:issue-fix）の noop
  baseline bootstrap が必要。routing-config の既存 frontier（6bd8/12c6）は stale の
  まま維持でよい（検証専用 target のため世代交代の実運用がない。12c6 の holdout
  未クリーン問題は追わない）
- 評価セット: EV-103 撤回、EV-104 は graded 節を除き維持（convergence 比較基準 +
  verdict 基準集約）、EV-105 維持（1e-6 ガード）、「routing-config = 検証専用 target」の
  位置づけを EV 前提に反映
- 設計 doc: `meta-harness-proposer-routing-unlock.md` §7 に本 ADR の帰結（routing-config
  の位置づけ変更・C-9 の凍結と再開条件）を追記。`meta-harness-detailed.md` §4-3 に
  検証専用化を、§3-2/§13-2 の ADR-048 由来記述から gate/graded の routing-config 適用を
  撤回。C-9 付録（決定 2）は proposer-routing-unlock 側に記録
- `codex.model` の解放（§7 Phase B の残項目）は、routing-config が検証専用 target と
  なったことで「own suite で差が出るか」ではなく「妥当性ゲート + human 判断で安全に
  扱えるか」の問題に還元される。扱いは別 Issue
- ADR-048 は本 ADR により部分 supersede される（生存部分は決定 3 に列挙）
