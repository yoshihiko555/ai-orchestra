# ADR-20260927-057: 記憶の層の分担を memory-layers ルールで定め、全 CLI に必要な知見は手動の棚卸しで AGENTS.md に昇格する

- **ステータス**: accepted
- **日付**: 2026-09-27
- **決定者**: yoshihiko
- **関連**: ADR-20260313-009（セッション間記憶は claude-mem に委任。本 ADR が補完し、supersede しない）、ADR-20260926-056（Plans.md を発注書と状態の置き場にする）、`.claude/rules/memory-layers.md`、`.claude/rules/task-memory-usage.md`、`.claude/rules/context-sharing.md`

## コンテキスト

作業中に得た状態・決定・気づきを残す場所が 7 つある: `.claude/context/`（context-sharing）、
`.claude/Plans.md`（task-memory）、fail-logs、`docs/adr/`、`AGENTS.md` / rules、Claude Code の
auto-memory、claude-mem。

ADR-20260313-009 は「セッション間の記憶は claude-mem に委任し、`history/` は設けない」と決めたが、
auto-memory の役割と、各層に何を書くかは決めていなかった。その結果、次の問題が起きていた。

- auto-memory に進行状態（「PR マージ待ち」「次回 loop 前に再 bootstrap 要」等）が入っていた。
  auto-memory は同じクローンの全 worktree で共有される（worktree からもリポジトリ root のスラッグの
  メモリが使われる）ため、ある worktree の状態が別の worktree で古い情報として読まれる。Plans.md は
  worktree ごとに独立しており、状態の置き場所として役割が重なっていた
- auto-memory は Claude Code 本体とサブエージェントに、claude-mem は Claude Code 本体に注入されるが、
  どちらも Codex / Antigravity には届かない。Codex / Antigravity にも必要な知見（コマンドの落とし穴、
  リポジトリの規約）がメモリにだけあると、それらには届かない
- `AGENTS.md` や rules にすでに書かれた内容がメモリにも重複していた。`MEMORY.md` の索引は 1 行の要約の
  はずが、最長 4,486 文字の行を持ち、毎セッションの注入量を押し上げていた

## 検討した選択肢

### 置き場所

- **A: core の新しい rule として配布する（採用）**: Plans.md・`AGENTS.md` という orchex の概念と結びつくため、
  配布先にも同じ分担を届ける
- B: ai-orchestra の `AGENTS.md` 記述欄にだけ書く: 配布先に届かない
- C: ユーザー個人の全体指示（dotfiles）に書く: orchex の概念から切り離され、配布先の他ユーザーに届かない

### auto-memory の project 型

- **A: 長期の事実だけを許す（採用）**: ブランチをまたいで通用する事実・外部の制約は auto-memory が適所。
  進行状態は Plans.md / Issue に書く
- B: project 型を使わない: ブランチをまたぐ長期の事実の置き場所がなくなる
- C: 規定しない: 現状の混入が続く

### 全 CLI に必要な知見の扱い

- A: 書く時点で振り分け、メモリに書かず `AGENTS.md` への追記を提案する
- **B: まずメモリに書き、手動の棚卸しで `AGENTS.md` へ昇格する（採用）**: 知見が汎用かどうかは書いた時点では
  判断しにくい。棚卸しでまとめて判断する
- C: A と B の併用

### 棚卸しのタイミング

- **A: 手動（ユーザーが依頼したとき）（採用）**
- B: Plans.md の Project をアーカイブする前 / C: `/release-readiness`: どちらも必ず通るフローではないため、
  組み込んでも取りこぼしが出る

## 決定

1. core パッケージに `memory-layers` ルールを追加し、記憶の層の一覧と「何をどこに書くか」の書き分けを定める。
   `context-sharing` の「セッション間記憶」節と `task-memory-usage` からこのルールを参照する
2. 進行状態は実行エンジンの状態の置き場所（`/goal`・Codex 直接は Plans.md、`/loop-issue`・TAKT は Issue と
   エンジンの状態、`/issue-fix` は会話と git）に書き、auto-memory には書かない。auto-memory の project 型は、ブランチ・worktree を
   またいで長期的に有効な事実だけにする
3. タスクの範囲の決定と気づきは、`/goal`・Codex 直接では Plans.md の `## Decisions` / `## Notes`、Plans.md を
   持たないエンジンでは Issue のコメントか PR 本文に書く。タスクが終わっても参照する設計判断は ADR に残す
   （Plans.md の Decisions は全 Project の完了時にアーカイブされるため）
4. Codex / Antigravity にも必要な知見は、まず auto-memory に書き、ユーザーが依頼したときの手動の棚卸しで
   `AGENTS.md` の記述欄へ移す。メモリの該当記述は、その変更が統合ブランチにマージされてから消す（マージ前に
   消すと、他の worktree からも Codex / Antigravity からも見えない期間ができる）。昇格の書き込み先は記述欄だけとし、
   `AGENTS.md` の管理ブロックと orchex が同期する rule は直接編集しない（`AGENTS.md` は 3 CLI が起動時に
   自動で読むが、`.claude/rules/` は Codex / Antigravity が自動では読まない）
5. 配布する hook でメモリを自動で書き換えない。auto-memory と claude-mem は orchex の管理外であり、ルールが
   決めるのは「何をどこに書くか」だけとする

ADR-20260313-009 の「セッション間記憶は claude-mem に委任する」は有効のまま。本 ADR は委任先を含む各層の
書き分けを補う。

## 対象外

- fail-logs を昇格の入口にすること。fail-logs は失敗の繰り返しを検出するが、そこから得た教訓の行き先は
  別タスク（Notion「失敗やレビュー指摘を自動抽出して、何度も指摘されている内容はルール化する」）で扱う
- 昇格・棚卸しの自動化
- claude-mem の注入設定（`~/.claude-mem/settings.json`、ユーザー設定）の見直し
- 自律実行（loop-harness / TAKT / meta-harness）とメモリの隔離

## 影響

- Claude Code は、進行状態を auto-memory に書かなくなる。別の worktree で古い状態を読む事故が減る
- 全 CLI に必要な知見は、棚卸しを経て `AGENTS.md` に集まり、Codex / Antigravity にも届く。棚卸しまでの間は
  Claude Code にしか届かない（手動を選んだ代償）
- 配布先では、`orchex` の同期（SessionStart の facet build を含む）で `.claude/rules/memory-layers.md` が
  追加され、既存の `task-memory-usage` / `context-sharing` にも「進行状態を auto-memory に書かない」などの
  規範と参照が加わる。hook・コマンド・設定キーの挙動は変わらない。プロジェクト単位で無効にする設定はない
  （他の core rule と同じ）
