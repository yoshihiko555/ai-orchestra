# ADR-20260817-052: claude-harness suite を測定軸ベースで拡充し、ハーネス全体の自己改善を実測可能にする

- **ステータス**: accepted
- **日付**: 2026-08-17
- **決定者**: yoshihiko
- **関連**: ADR-20260814-050（gate/graded 分離の原設計。本 ADR はこれを claude-harness target
  に適用する第一弾）、ADR-20260814-049（skill target での品質分解能実証）、
  ADR-20260817-051（cache_neutral_cost_usd。コスト軸の測定ノイズ除去は独立レイヤー）、
  Issue #267（oracle-tamper-detection。suite_hash/evaluator_hash 世代切替の運用と関連）

## コンテキスト

meta-harness の原構想は「ハーネス全体（CLAUDE.md/rules の指示書品質そのもの）の自己改善」で
あり、`claude-harness` target はその実測手段として位置づけられている。しかし現状の
`scenarios/claude-harness/` は `create-version-file` / `summarize-readme` の 2 本のみで、
いずれも ADR-20260814-050 以前の旧形式（graded なし・holdout なし）だった。ADR-050 で
`skill:*` target 向けに実装した gate/graded 分離機構はシナリオ側の宣言だけで有効になる
target 非依存の実装だが、claude-harness にはまだ適用されていなかった。この状態には
2 つの欠陥がある:

1. **品質分解能がない**: 2 本とも critical のみで判定するため、pass/fail の二値しか
   得られず、候補間の「出来栄えの差」を測れない。
2. **原構想の測定対象が形式化されていない**: 「ハーネス全体の品質」が何を指すのか
   （どんな観点を、どんな難度で測るのか）がシナリオとして具体化されていなかった。

## 決定

### 1. 測定軸を 4 つに整理し、優先順位を付ける

ハーネス全体の品質を測る観点を、以下の 4 軸に分解する:

| 軸  | 名称           | 何を測るか                                                         | 本 ADR での扱い |
| --- | -------------- | -------------------------------------------------------------------- | ---------------- |
| ①  | 指示遵守       | CLAUDE.md/rules（例: coding-principles）を、prompt に明示されなくても守れるか | **第一弾** |
| ②  | コンテキスト効率 | 同じ成果物をどれだけ低コストで達成できるか                           | シナリオ化しない（後述） |
| ③  | ワークフロー完遂 | facet 編集 → facet build → 生成物反映という複数段の手順を最後まで実行できるか | 仕様のみ記載、実装は第二弾 |
| ④  | 誤誘導耐性     | ドキュメント化されていない/紛らわしい設定・状況で誤った近道（過度な一般化）に陥らないか | **第一弾** |

優先順位は ①④ → ③ → ② の順とする。理由:

- **①④ を最優先する理由**: どちらも「prompt にない前提知識を rules から正しく汲み取れるか」
  という同じ性質の観点（①は規約の遵守、④は環境の正しい解釈）であり、既存 claude-harness
  2 本と同型の軽量シナリオ（単一ファイル実装・短い判定コマンド）で実装でき、実装コストが
  最小。gate/graded 変換の実証にも最適。
- **③ を次点とする理由**: facet build を伴うワークフローは実行コストが高い（後述 §3）。
  ①④ で gate/graded 機構と headroom 設計の型を確立してから着手する方が手戻りが少ない。
- **② をシナリオ化しない理由**: コンテキスト効率は「同じ成果物をどれだけ低コストで
  達成したか」であり、これは `frontier.cost_axis`（ADR-20260817-051 の
  `cache_neutral_cost_usd`）が既に全シナリオ横断で測定している軸である。専用シナリオを
  追加する必要はなく、既存シナリオの cost 実測値がそのまま②の代理指標になる。

### 2. 第一弾スコープ: ①④ を train + holdout で各 1 組、既存 2 本を gate/graded 転換

- **①指示遵守**: `implement-slug-util`（train）/ `implement-retry-helper-holdout`（holdout）。
  素朴な実装タスク（URL slug 変換 / ユーザー名検証）を与え、`coding-principles.md`
  の存在や個別規約（型ヒント必須・命名規則・単一責任・Early Return）を prompt では
  一切教えない。graded で「機能の正しさ」「型ヒント完備」「命名規約・docstring・
  関数長」（train）/「ネスト深度 2 以下」（holdout）を機械検証する。
- **④誤誘導耐性**: `resolve-effective-config`（train）/
  `resolve-nested-override-holdout`（holdout）。`config-loading.md` が定義する
  base/local 2 段マージルールの存在を教えずに、矛盾する設定ペアの実効値と根拠を
  answer JSON に書かせる。holdout はキーごとの部分上書き（1 キーだけ local が上書きし、
  もう 1 キーは base 継続）を問い、「local がある = 全部 local が勝つ」という過度な
  一般化に陥っていないかを検証する。
- **既存 2 本の転換**: `create-version-file` / `summarize-readme` を ADR-050 の分類原則
  （gate=実行成立性、graded=出来栄え）に沿って最小限だけ変更する。挙動の意味は変えない
  （§5「headroom 較正」参照）。

### 3. ③ワークフロー完遂の仕様（実装は第二弾）

③は次の形で実装する想定を記録するに留め、本 ADR のスコープには含めない:

- **タスク**: facet（`facets/policies/*.md` 等）を編集させ、`orchestra-manager.py context
  build` 相当の再生成コマンドを実行させ、生成物（`templates/project/CLAUDE.md` 等）に
  変更が反映されていることを確認させる、複数ステップのワークフロー。
- **oracle 方式**: 「oracle 内で同じ facet build を再実行し、候補が生成した成果物との
  diff がゼロであること」を検証する（"rebuild-diff-zero" 方式）。候補の成果物を信用
  せず、oracle 側で独立に正解を再計算する PR #266 流儀を踏襲する。
- **後回しにする理由**: facet build はリポジトリ全体を横断する処理で実行コストが
  ①④ の単一ファイルシナリオより高く、evaluate 予算・実行時間への影響が大きい。①④ で
  gate/graded・headroom 較正の型を確立してから、コストを見積もった上で着手する。

### 4. headroom 較正方針: 2 段階

- **第一弾（本 ADR）**: 既存 claude-harness シナリオ（`max_turns: 10`,
  `max_budget_usd: 3.0`）を踏襲した保守的な初期値を使う（新規 4 本は軽量な単一ファイル
  実装/JSON 出力タスクのため `max_turns: 16` に余裕を持たせつつ `max_budget_usd: 3.0`
  は据え置く）。graded 各項目は「モデルがしばしば落とす」水準を狙う設計にする
  （§5 参照）が、実測前の設計時点の狙いに過ぎない。
- **第二弾（マージ後）**: `skill:issue-fix` 等で確立した較正フロー（PR #356〜#361）と
  同様に、bootstrap 実測（baseline 候補で train+holdout を数回実行）を経て
  `max_turns`/`max_budget_usd`/`max_total_tokens`/`max_output_tokens` を実測値に基づき
  調整する。この 2 段階運用は既存シナリオ群と同じ慣行であり、新規性はない。

### 5. headroom 設計の狙い（graded 項目ごとの想定 fail 率）

- **① graded**: 「機能の正しさ」は baseline でもほぼ確実に pass する想定（正しく実装
  できなければ実行成立性自体が疑わしいため）。差が出るのは「型ヒント」「命名規約・
  docstring・関数長」（train）/「ネスト深度」（holdout）で、prompt に規約が書かれて
  いない以上、rules を実際に踏まえて実装したかどうかで割れる設計。
- **④ graded**: 「実効値」「根拠ファイル」の 2 項目とも、config-loading ルールを
  正しく認識していないと外れる設計。holdout の非上書きキー項目は特に、「local
  ファイルが存在する = そのファイルの値が全キーに優先する」という過度な一般化の罠を
  仕込んでおり、①④ の中で最も headroom が大きいと想定している。
- **既存 2 本の転換で headroom を薄めない**: `summarize-readme` の graded は「200 words
  以内」という prompt 自身の制約を機械検証する（`wc -w`）。20 バイト以上という
  ほぼ必ず pass するチェックは `checks`（非 graded）側に残置し、graded 側には
  混入させない。ただし `wc -w` は日本語要約のような語区切りが疎な出力に対しては
  ほぼ無力（スペース数が少なく語数がカウントされにくい）である既知の制約があり、
  この転換の headroom は主に新規 4 本が担う。`readme-untouched`（リポジトリ非破壊）
  も同様に `checks` に残す。gate=実行成立性・graded=出来栄えという ADR-050 の分類
  原則には厳密には一致しない性質（ガードレール寄り）のため、最小転換の方針として
  現状維持する。

### 6. suite_hash / evaluator_hash の世代切替は Issue #267 の対応と同世代にまとめる

本 ADR のシナリオ追加自体で claude-harness の `suite_hash` は変わる（新規ファイルが
`discover_scenario_paths` の対象に入るため）。加えて、regression 予算再較正
（§7 参照）は `evaluator_hash` も変える（EV-57: `regression.*` の変更は evaluator hash
に影響する）。Issue #267（oracle-tamper-detection の残スコープ）が別途 `evaluator_hash`
を切り替える計画があるため、claude-harness の baseline 再 bootstrap は両者がまとまった
タイミングで 1 回だけ行う運用とする（世代切替のたびに再 bootstrap するコストを避ける）。

## 影響

- 変更対象: `packages/meta-harness/scenarios/claude-harness/*.yaml`（新規 4 本 + 既存
  2 本の gate/graded 転換）、`packages/meta-harness/scenarios/fixtures/assert-python-
  type-hints.py` / `assert-python-conventions.py` / `assert-effective-config.py`（新規）、
  対応テスト（`test_skill_scenarios.py` 相当の新規 fixture 単体テスト）、
  `packages/meta-harness/config/meta-harness.yaml` +
  `.claude/config/meta-harness/meta-harness.yaml`（`regression.max_budget_usd`
  186.0 → 210.0、既存 skill/routing-config 分の較正コメント台帳に追記する形で継続）
- **regression 側への波及**: claude-harness は routing-config candidate の
  cross-skill regression suite の impact target の 1 つ（EV-75）であるため、本 ADR で
  claude-harness の own run 数が 2 → 6（train 4 + holdout 2）に増える。これに伴い:
  - regression の必要予算が train/holdout 通算で +24.0（新規 4 本、各
    `max_budget_usd` 3.0 × train は `repeat_default`(1)、holdout は
    `repeat_frontier`(3)）増加する。実効設定は本 ADR で 186.0 → 210.0 に更新済み
    （`test_default_budget_covers_all_registered_routing_config_regression_suites`
    で検証）。
  - claude-harness の holdout phase が初めて非空になったことで、promote 前提条件
    （`_evaluation_covers_current_holdouts`）が claude-harness の実 holdout
    カバレッジ（2 シナリオ × `repeat_frontier` 回の attempt）を要求するようになる。
    従来は claude-harness の holdout 0 件により vacuously 検証済み扱いだった箇所が、
    本 ADR 以降は実コストを伴う検証に変わる（テスト対応は
    `test_promote_cli.py::_append_full_holdout_coverage` 参照）。
- **既知ギャップ（本 PR スコープ外、フォローアップ課題として記録）**:
  - `packages/meta-harness/lib/meta_harness_common.py` の
    `DEFAULTS["regression"]["max_budget_usd"]`（186.0）は、本来は実効 YAML 値と
    歴史的に同期されてきた config-load-failure 用フォールバックだが、
    `packages/meta-harness/lib/**` が本 PR のガードレール（Issue #267 の並行作業との
    衝突回避）で編集対象外のため、186.0 のまま追従できていない。config 読み込みが
    完全に失敗した場合のみ影響する fail-closed パスであり実害は限定的だが、
    別 PR での追従が必要。
  - `evaluator.py`（3914 行付近）の
    `# A suite can legitimately have no scenarios in one phase (claude-harness has
    train-only scenarios today).` というコメントは、本 ADR で claude-harness が
    holdout シナリオを持つようになったため文言として古くなった。挙動自体に影響は
    ない（該当コードパスは「対象 suite のそのフェーズのシナリオが 0 件なら
    vacuously pass」という一般ロジックで、claude-harness に特化した分岐ではない）が、
    `lib/**` 凍結のためコメント更新は本 PR のスコープ外。
  - `docs/evaluation/meta-harness.md`: EV-107〜EV-110（graded 意味論、ADR-20260814-050）
    は target 非依存の記述であり、claude-harness への適用は既存文言でカバーされる。
    新規に追加すべき EV は本 ADR の実装からは特定されなかった（評価セット突合は本 PR
    のコミットメッセージ / PR 説明で報告する）。
