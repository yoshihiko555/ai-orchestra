# ADR-20261029-062: エージェント提案に任意の Jev 判定を入れ、キーワード判定は依頼の文に限定して残す

- **ステータス**: accepted
- **日付**: 2026-10-29
- **決定者**: yoshihiko
- **承認根拠**: 対話で、記録だけの期間を設けないこと・v3 に固定すること・区切り値 0.5・キーワード判定を残すことを利用者が選択。評価の数値は 2026-10-29 のルーティング監査と Jev の試し呼びによる
- **関連**: ADR-20261028-060（必須 routing と任意の CLI 相談助言の分離）

## コンテキスト

`agent-router.py`（UserPromptSubmit）は、入力にトリガー語が含まれるとエージェントを提案する。提案には `agent-routing-policy` ルールで MUST で従うため、誤った提案はそのまま不要な委譲になる。

2026-10-29 に監査ログ 270 件（試し呼びに使った分を除く）をラベル付けして評価した。

- キーワード判定（main）: 委譲不要の 263 件のうち 48 件に提案した。委譲すべき 7 件は 1 件も拾えなかった。誤提案の多くは、報告・過去の作業の説明・否定・引用の中のトリガー語に反応していた
- キーワード判定に依頼形ゲート（依頼の形をした節だけで照合する）を入れると、誤提案は 4/263 になった
- Jev（TypeSafe の判定モデル。設定 r3-flat-B-v3、会話の文脈なし、区切り値 0.5）: ラベル付き 59 件で提案 9 件中 8 件が妥当、委譲不要への誤提案は 0。試し呼びの 32 件では誤提案 1/25
- Jev の呼び出しは `POST https://api.typesafe.ai/v1/systemone`（Bearer）。p50 0.17s、入力 p50 約 2.9k トークン、1 件あたり約 $0.0001

## 検討した選択肢

### 選択肢 A: 記録だけの期間を設け、提案はキーワード判定のまま Jev の判定をログに残す

- メリット: 本番の入力で Jev を評価してから切り替えられる
- デメリット: その間も誤提案の多いキーワード判定に従い続ける。比べる相手は今のキーワード判定で、評価でそれより悪くなる兆候は無かった

### 選択肢 B: Jev を agent-router に組み込み、既定は依頼形ゲート付きのキーワード判定にする

- メリット: Jev を有効にした環境ではすぐ誤提案が減る。Jev が使えない環境・使わない環境でも、ゲートで誤提案が減る
- デメリット: Jev を有効にすると入力ごとに遅れ（p50 約 0.2s、最悪 0.5s）と外部送信が生じる

### 選択肢 C: キーワード判定を Jev で置き換える（キーワード判定を削除する）

- メリット: 判定の経路が 1 つになる
- デメリット: API キーの無い環境・ネットワークの無い環境・タイムアウト時に提案ができなくなる。外部送信を望まない利用者の既定にできない

## 決定

**選択肢 B** を採用する。

1. **記録だけの期間は設けない**。Jev は `router.engine: jev` を `cli-tools.local.yaml` に書き、API キーがあるときだけ提案に使う。比べる相手は今のキーワード判定で、評価ではそれより悪くなる可能性は低い。判定は毎回監査ログ（`routing_suggestion`）に残し、運用しながら見直す
2. **送信内容は r3-flat-B-v3 に固定する**（指示文・判定基準 31 択・モデル `jev-1.14.0`。sha256 先頭 16 桁 `5ae693c78f47091d` を `request_hash` として記録する）。v4a は「自分で処理して」という依頼（P0）に提案してしまい、v4b は評価に使った 59 件に合わせすぎていた。会話の文脈を付けると誤提案が増えたため、送るのは人の入力 1 件だけにする。内容を変えるときは CONFIG_ID も変える
   - 利用者は `router.jev.model` でモデルを上書きできる（`jev-1.14.0` の提供が終わったときに、コードを変えずに移れるようにするため）。上書きすると評価済みの組み合わせから外れるが、記録の `config_id` は `r3-flat-B-v3` のまま変えない。モデルの違いは記録の `model` と `request_hash` で見分ける
3. **区切り値は 0.5**。`probabilities.none` が 0.5 を超えるか `choice` が `none` なら提案しない。提案には MUST で従うため、見逃しを増やしてでも誤提案を減らすことを優先する。このとき、キーワード判定には戻らない
4. **キーワード判定は削除せず、依頼形ゲートだけを入れる**。既定の判定であり、Jev が使えないとき（キーが無い・タイムアウト・HTTP エラー・接続失敗・不正な応答・マスキング関数が無い）の代わりでもある。トリガー語の削除や特別扱いの一覧は入れない（Codex が出した全面的な改修案は試し呼びのデータに合わせすぎていた）。ゲートは `detect_agent` の外で節に分けて渡す（loop-harness が Issue のタイトルとラベルを渡しているため）
5. **送信は安全側に倒す**。送る前に貼り付けタグの除去 → `mask_secrets` → URL・メール・ホームパスの置換 → 1200 文字で切る。マスキング関数を読み込めなければ送らない。ハーネスの通知とスラッシュコマンドは送らない。API キーは環境変数 `TYPESAFE_API_KEY`、`~/.config/typesafe/api-key` の順で探し、出力・ログ・例外文に出さない
6. **待ち時間は壁時計で 500ms まで**（`router.jev.timeout_ms`）。超えたらキーワード判定にする。hook は止めず exit 0 で終わる
7. **選ばれたエージェントが `.claude/agents` に無ければ提案しない**（次の候補に繰り下げない）

## 見直しの目安

2 週間ほど運用した後、Jev が提案した分だけを Claude と Codex がラベル付けし、意見が割れた分だけを利用者が判断する。次の 3 つを目安にする。

- 提案の 90% 以上が妥当
- 委譲不要への誤提案が 100 件あたり 2 件以下
- 同じ入力で、キーワード判定（毎回記録する `keyword` 項目）より正しい提案が多い

数えるのは `request_hash` が `5ae693c78f47091d`（評価済みの組み合わせ）の記録だけにする。`router.jev.model` を上書きした期間の記録は `config_id` が同じでも別に扱う。記録した確率を使って区切り値も見直す。目安を満たさなければ、既定のキーワード判定に戻す（`router.engine: keyword`）。

## 影響

- 既定（`router.engine: keyword`）でも、キーワード判定は依頼の形をした節にしか反応しなくなる。報告・過去形・否定・引用だけの入力には提案が出ない。audit の期待ルート予測（`expected_route`）も同じ節で行うため、導入前後の監査を比べるときは注意する
- engine=jev にすると、入力ごとにマスキング済みの本文（最大 1200 文字）が TypeSafe に送られる。費用は 1 件あたり約 $0.0001、遅れは p50 約 0.2s・最悪 0.5s
- 監査ログに新しいイベント型 `routing_suggestion` が増える
- 自動の区切り値調整・ダッシュボードへの表示・hook の非同期化・スキルのルーティングは対象外
