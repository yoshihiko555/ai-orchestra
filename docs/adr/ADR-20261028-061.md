# ADR-20261028-061: agency-agents のエージェントを commit 固定の vendor で取り込み、upstream.yaml で付け外しする

- **ステータス**: accepted
- **日付**: 2026-10-28
- **決定者**: yoshihiko
- **承認根拠**: 対話で取り込み方式・上書き範囲・ツール権限・更新時の確認範囲・`essential` への追加・取り込むエージェントを利用者が選択。code / adversarial / security レビューの指摘を反映
- **関連**: なし

## コンテキスト

`specialized-mcp-builder` と `support-executive-summary-generator` は、OSS の agency-agents（MIT）から手でコピーして `agent-routing` に置いていた。
手でコピーしているため upstream の修正に追従できず（`specialized-mcp-builder` は 2 commit 遅れていた）、frontmatter に `tools` が無いので全ツールと `Agent`（サブエージェントの起動）まで持っていた。
`name` も upstream の表示名（`MCP Builder`）のままで、`cli-tools.yaml` のキー（`specialized-mcp-builder`）と一致していなかった。
agency-agents は頻繁に更新されており、今後も有用なエージェントを足したり外したりしたい。

## 検討した選択肢

### 選択肢 A: commit を固定して vendor し、生成物をコミットする

- メリット: 配布先で外部から取得しない。upstream の変更は PR の差分としてレビューできる
- デメリット: 追従には ai-orchestra 側で更新コマンドを実行する必要がある

### 選択肢 B: 配布時（orchex install / sync）に毎回 upstream を取得する

- メリット: 常に最新になる
- デメリット: 配布先にネットワークが必要になり、レビューを経ない外部の変更がそのまま実行権限付きで入る

### 選択肢 C: git submodule で持ち、ビルド時に変換する

- メリット: 版は固定される
- デメリット: submodule の運用負担が増える

## 決定

**選択肢 A** を採用し、新しいパッケージ `packages/agency-agents` に置く。

1. **正本は `upstream.yaml`**。取り込むエージェント（upstream 内のパス）と固定する commit（40 桁の SHA）を書く。`agents/*.md`・`manifest.json` の `agents`・`LICENSE-agency-agents` は `scripts/vendor-agency-agents.py` が生成し、手で編集しない
2. **upstream はローカルの clone から `git show <sha>:<path>` で読む**。clone の作業ツリーやブランチには依存しない
3. **上書きは frontmatter だけ**。本文にはパッチを当てない（不具合は upstream に報告するか、取り込みをやめる）。`name` はファイル名の slug に書き換える。upstream の frontmatter から生成物に通すのは `description` / `color` / `emoji` / `vibe` だけにする（`hooks` / `mcpServers` / `permissionMode` は `tools` の制限と別の経路でコマンド実行や権限の迂回ができるため、upstream に持ち込ませない）。`upstream.yaml` で上書きできるキーも `description` / `model` / 表示用キーに限る
4. **ツール権限は既定で readonly（Read, Glob, Grep）**。必要なものだけ `profile: writer` / `implementer` か `tools: [...]` で広げる。`Agent` はどの profile にも含めない。エージェントごとに本文を読んでツールを決める負担を減らしつつ、書き忘れても安全側に倒すため
5. **更新時はリスクのある変更だけ人が必ず読む**。`update` は次の変更に印を付けて差分全文を出し、印がある限り `--yes` なしでは書き換えない: `Bash` / `Edit` / `Write` / `Agent` を持つエージェントの変更、description の変更、未対応の frontmatter キーの追加、危険なパターン（空白・行継続・日本語の揺れを正規化して照合）、不可視文字・HTML コメントの追加、安全に関する記述の削除。言い換えを完全には防げないため、パターン検出は補助で、安全性は主にツールの制限で担保する（全文を常に読む案も検討したが、利用者の判断で印による絞り込みを採った）
   - 新しい commit で生成に成功するまで何も書かない。進め先は現在の commit の子孫に限り、`--source` の origin が `repo` と同じリポジトリであることを確かめる（巻き戻し・fork の commit を取り込まない）
6. **ルーティング設定（`cli-tools.yaml`）が無い取り込みエージェントは警告にとどめる**
7. **`essential` プリセットに含める**。既存の 2 エージェントを `essential` の新規導入で失わないため
8. **MIT の告知を生成物に入れる**。印のコメントに repo・commit・ライセンス名・著作権表示を書き、upstream の LICENSE を同梱する
9. **初回は 5 エージェントを追加する**: `engineering-privacy-engineer` / `engineering-identity-access-engineer` / `engineering-payments-billing-engineer` / `engineering-database-reliability-engineer`（readonly）と `engineering-minimal-change-engineer`（implementer）。既存エージェントと役割が重ならず、本文に危険な記述が無いことを確かめた

## 影響

- **BREAKING**: 既存プロジェクトの `orchestra.json` には新しいパッケージが自動では入らない。`agent-routing` だけを入れているプロジェクトでは、次の sync で 2 エージェントが消える。`orchex install agency-agents --project <path>` で戻す
- **BREAKING**: 2 エージェントの `name`（`subagent_type`）が `MCP Builder` / `Executive Summary Generator` から `specialized-mcp-builder` / `support-executive-summary-generator` に変わる
- `support-executive-summary-generator` は読み取り専用になり、ファイルを書けなくなる
- `specialized-mcp-builder` と `engineering-minimal-change-engineer` は Bash を持つ。第三者の本文のまま配布先で動くので、この 2 つの更新は毎回人が差分を読む（印が必ず付く）
- パッケージをまたいでエージェントを移すと、移動前のパッケージの `file_hashes` 台帳に古い記録が残る（参照はされない）。このリポジトリの `.claude/orchestra.json` からは外した
