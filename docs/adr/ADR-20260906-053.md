# ADR-20260906-053: LP-2 Docker Checker の実行環境と観測性を実運用値に合わせる

- **ステータス**: accepted
- **日付**: 2026-09-06
- **決定者**: yoshihiko
- **関連**: ADR-20260712-035（Docker + ephemeral credential broker 移行の原設計。scenario
  コンテナの tmpfs 運用を本 ADR で部分的に緩める。§「影響」参照）、ADR-20260715-039（LP-2
  Maker/Checker の実行基盤を Docker 完全隔離へ移行する決定。本 ADR はその実運用フィードバック
  による調整）、`design:loop-harness-isolation`（本 ADR の決定を反映する設計書）

## コンテキスト

loop-harness LP-2（Docker 隔離バックエンド）を実プロジェクト ai-orchestra の Issue #347 に対して
2026-09-06 に無人実行したところ、Maker は Docker 内で完走したが Checker が構造的に失敗した。
GitHub Issue #405 / #409 / #410（yoshihiko555/ai-orchestra）としてそれぞれ記録されている。

1. **#409 — 機械検証（pytest 等）が git/tmp/worktree 前提を満たせない**:
   `loop_git_ephemeral.build_maker_git_mount_spec` / Checker 版が返す `GIT_DIR`/`GIT_WORK_TREE` を
   `loop_docker_action._start()` がコンテナ全体（`docker run -e`）に載せているため、Checker の
   機械検証で `git init` を使うテストが全滅する（実測 656 failed / 429 errors）。加えて `/tmp`
   tmpfs が noexec のため CLI バイナリを生成・実行するテスト 47 件が落ち、worktree ro マウント
   のためソースツリーを書き換える e2e テスト 5 件（`tests/conftest.py` の `orchestra_dir` fixture
   が `REPO_ROOT` を返し `os.utime`/書込する）が落ちる。
2. **#405 — broker 既定値が実測の 1 桁小さい**: `packages/loop-harness/lib/loop_docker_config.py`
   の既定値（budget_usd 3.0 / max_requests 64 / max_total_tokens 500000 /
   max_upstream_bytes 50MB）が実 Maker（実測: 31 リクエスト・$6.68・cache_read 込みの
   total_tokens が 2M を 23 リクエストで超過）に対して過小であり、429 で全拒否されても
   driver 側に痕跡が残らない（`refresh_metrics()` は本番から呼ばれず、claude の stderr も
   保存されない）。
3. **#410 — reviewer 出力の不正 JSON が無言でハングに見える停止に化ける**: Checker LLM review
   （`loop_driver.py` の reviewer 実行、`_reviewer_prompt`）の出力が CheckResult JSON として
   parse できないと、無言で `infrastructure_failure=True`・signature None になり、3 回で
   `infrastructure_failure_exhausted` → exit_failure に至る。生出力は保存されず、原因調査が
   できない。reviewer は 17 リクエスト・$2.35 を消費して exit 0 だった（= reviewer 自体は
   正常終了しているのに、出力形式の不整合だけで検証不能になっていた）。

### 2026-09-06 の実証実験と 2026-09-07 の訂正

2026-09-06 時点では、コンテナ内で以下を実測し「`.git` pointer overlay だけで git 解決が成立する」
と結論づけていた: scenario image `sha-f36cbd1fb911`、`--read-only --cap-drop=ALL --user <uid:gid>`、
tmpfs noexec、worktree ro + `.git` ファイル overlay（**`gitdir: /work/eph`**、コンテナ内で到達可能な
ephemeral パスを指す overlay）+ ephemeral dir rw、**環境変数に `GIT_*` を一切設定しない**状態で、
`git rev-parse --git-dir` → `/work/eph` 解決・`git status`/`git diff`/`--show-toplevel` の正常動作・
`/tmp` 配下での `git init` 成功を確認した。

**2026-09-07 訂正**: Docker E2E（`test_maker_commit_round_trip_uses_production_profile_and_cleanup`）
で本番相当の spec を検証した結果、上記の実証は**本番の overlay 内容と乖離していた**ことが判明した。
現行の pinned `.git` overlay（`loop_git_ephemeral.build_maker_git_mount_spec` /
`prepare_ephemeral_git` の `pinned_git_pointer`）は **host の `.git` ファイルをそのままコピー**して
おり、コンテナ内では到達不能な **host gitdir**（`<project>/.git/worktrees/<name>`）を指す。
したがって現行設計では:

- `GIT_DIR`/`GIT_WORK_TREE` env が git 解決の**主制御**であり、
- `.git` overlay は「host 側事後処理が汚染された gitdir を踏まない」という**改ざん防止のみ**を
  担っていた（`design:loop-harness-isolation` §4.3.2 Fix-3 補足のとおり。コンテナ内からの git 解決
  には寄与しない、到達不能なパスを指すため）。

2026-09-06 の実証実験（`gitdir: <ephemeral_dir>` を指す overlay）は本番構成とは異なる合成 overlay
で行われており、「overlay だけで解決が成立する」という結論はそのままでは本番構成に適用できない。

## 決定

### 1. `.git` overlay の内容を ephemeral gitdir に変更し、git 解決の主制御に昇格させる

pinned `.git` overlay の内容を、host gitdir のコピー（`gitdir: <common_dir>/worktrees/<name>`）から
**`gitdir: <ephemeral_dir>`**（ephemeral 側は `core.bare=false` に設定し、worktree 相当として解決
できるようにする）に変更する。これにより `.git` overlay 自体がコンテナ内で到達可能な参照になり、
**git 解決の主制御**に昇格する。

`GIT_DIR`/`GIT_WORK_TREE` env は、この主制御に対する belt-and-braces（env が汚染・欠落しても
overlay が解決を保証する冗長化）として位置づけを変え、`claude -p` を起動する `docker exec` の env
にのみ付与する（Maker/Checker 両方）。`docker run` のコンテナ全体 env、および
`mechanical.commands`（pytest/ruff 等の機械検証）を起動する exec には付与しない。

- 根拠: 機械検証の exec がコンテナ全体 env 経由で `GIT_DIR`/`GIT_WORK_TREE` を継承すると、
  worktree 内で `git init` を行うテスト等が ephemeral repo 側へ誤誘導され、大量の失敗を生む
  （#409 で実測 656 failed / 429 errors）。overlay を主制御に昇格させたことで、機械検証 exec には
  env を付与しなくても worktree 内の通常の git 解決（`.git` → `gitdir: <ephemeral_dir>` → 正しい
  index/ref）が成立する。
- 改ざん検知（`_verify_git_pointer`、`packages/loop-harness/lib/loop_git_ephemeral_support.py`
  551 行付近）は、host `.git` の実体を「元の内容のスナップショット」
  （コンテナ起動前に取得した、host gitdir を指す host 側オリジナルの `.git` 内容）と比較する形に
  変わる。overlay としてコンテナへ書き込む合成内容（`gitdir: <ephemeral_dir>`）とは別に、この
  オリジナル内容のスナップショットを保持し、host 側 `.git` が一連の処理中に触られていないことを
  確認する——という検証の目的自体は変わらない。

### 2. exec 可の TMPDIR を新設する

新しい tmpfs `/tmp/exec`（rw, nosuid, nodev、**noexec なし**、uid/gid はコンテナユーザー、
size 512m）を追加し、コンテナ全体の `TMPDIR` をそこへ向ける。既存の `/tmp` と `$HOME` の
noexec は維持する。

- 根拠: Checker（mechanical.commands）・Maker（claude -p が生成したコード実行）のいずれも
  Maker が作成した Python 等を実行する場面が主であり、noexec は実質的な防御になっていない。
  一方で noexec は CLI バイナリを生成・実行する正当なテスト 47 件を落とし、Maker がこの
  「幻の失敗」を追いかけて反復するコストを生んでいた（1 反復 ≈ $7）。
- 正直な整理として、`/tmp`・`$HOME` の noexec は「`TMPDIR` を尊重しない直書きへの残余防御」に
  格下げされる（主防御ではなくなる）。

### 3. broker 既定値を実測に基づき較正する

`packages/loop-harness/lib/loop_docker_config.py` の既定値を以下に変更する（1 アクションあたりの
上限。反復上限 × アクション数が loop 全体の理論上限になる）。

| キー                    | 旧値       | 新値        |
| ----------------------- | ---------- | ----------- |
| `budget_usd`            | 3.0        | 25.0        |
| `max_requests`          | 64         | 400         |
| `max_total_tokens`      | 500000     | 30000000    |
| `max_upstream_bytes`    | 50000000   | 500000000   |

予算式自体（入力上限 = body bytes / input_bytes_per_token、cache_read も total に計上する仕様）は
変更しない。値のみを実測（Maker 31 リクエスト・$6.68・total_tokens 2M 超過、reviewer 17 リクエスト・
$2.35）に対して十分な余裕を持つよう較正する。

### 4. 観測性を追加する

- アクション終了時（`finish`。lease 喪失時の `discard_after_lease_loss` 経路では書かない。
  EV-50 準拠）に broker の `--print-metrics` を
  `artifacts/<action_id>/broker_metrics.json` として保存する。
- `claude` プロセスが非 0 終了したときは stdout 末尾と stderr を `artifacts/<action_id>/` に
  保存する。
- infrastructure failure の journal payload に broker metrics 要約
  （requests / estimated_cost_usd / anomaly_reasons）を載せる。

これにより #405 のような「429 で全拒否されても痕跡が残らない」状態を解消する。

### 5. reviewer 出力の扱いを寛容化しつつ、決定的停止のセマンティクスは維持する

- JSON 抽出を段階的に寛容化する: 全文 JSON → ` ```json ` フェンス → `"layer"` を含む最初の
  balanced `{...}`。
- それでも不正な場合は signature を `reviewer_output_invalid` に固定し、
  `infrastructure_failure=True` は維持する（3 回で決定的に停止する現行セマンティクスは変えない。
  無限リトライにしない）。
- 生 stdout/stderr を `artifacts/<action_id>/llm_review_<reviewer>.raw.json` /
  `.stderr.log` に保存する。
- reviewer プロンプトに「Bash は `git diff` / `git log` の単発コマンドのみ（パイプ・`&&` 不可）、
  テストは実行しない、JSON のみを返しフェンスや前置きを付けない」ことを明記する。

### 6. ソースツリーを書き換える e2e テストは skip とする

`tests/e2e/`（`test_e2e_facet.py`, `test_e2e_lifecycle.py`, `test_e2e_sync.py`）の
`REPO_ROOT` 書き込み前提の 5 テストは、`REPO_ROOT` が書込不可なら skip とする。読み取り専用
worktree は Checker の仕様であり、これはテスト側の衛生問題として扱う。

### 7. スコープ外を明記する

ai-orchestra 自身のフルスイートを Docker Checker で全 green にすることは目標にしない
（#393 の srt 依存・メタハーネスの環境依存は別 Issue）。Checker が「verdict（pass または
実指摘つき fail）に到達すること」を完了条件とする。以後、検証運転で見つかる新規事項は
新規 Issue ではなく既存 Issue #274 のコメントに集約する。

## 却下した代替案

- **env をコンテナ全体に残し、機械検証の exec だけ `GIT_DIR`/`GIT_WORK_TREE` を unset する**:
  overlay を主制御に昇格させる前提（決定1）を採らない場合、この代替案は「機械検証 exec が
  worktree 内の git を一切解決できなくなる」ため単純に不成立である。旧設計の overlay は
  host 側 unreachable gitdir を指しており、機械検証で env を unset すると env にも overlay にも
  git 解決の手段が残らない。Docker E2E（`test_maker_commit_round_trip_uses_production_profile_and_cleanup`）
  で実証済み。overlay の内容を `gitdir: <ephemeral_dir>` に変更し主制御へ昇格させる採用案でのみ、
  機械検証 exec への env 付与省略が安全に成立する。
- **broker 予算式（入力上限の算出方法）自体の変更**: 実測との乖離は式ではなく既定値の
  古さが原因であり、式を変えると再現性・監査可能性が下がる。式は維持し既定値のみ較正する。
- **Checker で ai-orchestra 自身のフルスイートを全 green にする**: `#393` の srt 依存・
  メタハーネスの環境依存など、loop-harness の隔離設計とは無関係な要因で恒久的に fail する
  テストを含んでおり、これを全 green 化の対象にすると LP-2 の完了条件が無期限に遠のく。
  Checker の責務は「verdict に到達すること」に限定する。

## 影響

- 変更対象: `packages/loop-harness/lib/loop_git_ephemeral.py`（`build_maker_git_mount_spec` /
  `prepare_ephemeral_git` の overlay 内容を `gitdir: <ephemeral_dir>` へ）、
  `packages/loop-harness/lib/loop_git_ephemeral_support.py`（`_verify_git_pointer`、551 行付近。
  改ざん検知用スナップショットを host オリジナル内容へ分離）、
  `packages/loop-harness/lib/loop_docker_action.py`（env 付与を
  exec 単位へ、`/tmp/exec` tmpfs 追加）、`packages/loop-harness/lib/loop_docker_config.py`
  （broker 既定値の較正）、`packages/loop-harness/lib/loop_driver.py`（reviewer 出力の寛容化・
  artifacts 保存・broker_metrics 保存）、`tests/e2e/test_e2e_facet.py` /
  `test_e2e_lifecycle.py` / `test_e2e_sync.py`（skip 条件追加）。これらの実装・対応するテスト・
  評価セット（`docs/evaluation/loop-harness.md`）・CHANGELOG は、本 ADR と同一ブランチ上で
  別担当のエージェントが並行して更新する（本 ADR は決定の記録のみを担う）。
- `design:loop-harness-isolation` は本 ADR に追従して §3（tmpfs/noexec）・§4.3.2/§4.3.4
  （git env スコープ）・観測性（artifact 保存）の記述を改訂する（本 PR で実施済み）。
- ADR-20260712-035 が決めていたのは「scenario コンテナは read-only rootfs で、書き込みは
  対象 mount と tmpfs のみに限定する」ことであり、noexec 自体は継承元の meta-harness
  `scenario_docker_profile.py`（`design:loop-harness-isolation` §3「確定方針 4」）の
  設定に由来する（noexec を 035 が明示的に決めたわけではない）。broker サイドカーの
  token tmpfs（`/run/secrets`、noexec/nosuid）は 035 の決定どおり変更しない。本 ADR が
  部分的に supersede するのは「scenario コンテナの tmpfs は noexec のみで構成する」という
  **継承された運用の含意**であり、`/tmp/exec` という exec 可能な tmpfs を追加で切り出す点に
  限定される。broker の資格情報隔離・dual-homed sidecar・egress 制限など、ADR-035 の他の
  決定は本 ADR の対象外で存続する。
