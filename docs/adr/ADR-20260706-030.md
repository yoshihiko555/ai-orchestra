# ADR-20260706-030: メタハーネス機構の導入（population ベースのハーネス最適化基盤）

- **ステータス**: proposed
- **日付**: 2026-07-06
- **決定者**: yoshihiko

## コンテキスト

arXiv:2603.28052 "Meta-Harness: End-to-End Optimization of Model Harnesses"（Stanford/KRAFTON/MIT,
2026-03）は、LLM ハーネス（プロンプト足場・メモリ・検索・ツールオーケストレーション）の構成が
性能を最大 6 倍左右すること、既存の自動プロンプト最適化はフィードバックを圧縮しすぎて失敗原因を
診断できないこと、そして「生トレースへのフルアクセス」が改善効果を決定づけること（ablation:
フルアクセス 50.0 vs スコアのみ 34.6）を示した。

この repo では、ハーネスに相当する実行トレースが skill-evolution metrics / fail-logs /
codex-harness runs の 3 系統に分断されており、セッション横断でフルトレースを永続保持する仕組みが
ない。また、skill-evolution（ADR-20260701-027）のオフライン反復改善層は設計のみで未実装
（Issue #139）であり、単一系譜の漸進改善にとどまる想定だった。population ベースの探索や
品質×コストの Pareto frontier という考え方は、この既存設計には含まれていない。

## 検討した選択肢

### 選択肢 A: skill-evolution オフライン層を設計どおり単一系譜で実装

- メリット: 追加設計コストが小さい。既存の ADR-027 設計をそのまま実装するだけで済む。
- デメリット: population・フルトレース永続ストア・Pareto frontier という論文の中核的な便益を
  得られない。後から meta-harness 相当の基盤が必要になった際、単一系譜前提の実装を作り直す
  ことになる。

### 選択肢 B: meta-harness を sibling パッケージとして新設し、skill-evolution オフライン層は委譲で実現（採用案）

- メリット: ADR-027 の決定（D1 二層構成・D2 二軸 judge・D3 人間承認ゲート）を保存しつつ、
  スキル対象の改善を population ベース探索へ一般化できる。トレース永続ストア・evaluator・
  proposer・promotion を全ハーネス面（スキルに限らず facet/config 全般）で共用できる。
- デメリット: パッケージ間 I/F（`target=skill` 委譲）の設計コストが発生する。

### 選択肢 C: 論文どおり任意 Python プログラムを候補とするフルスクラッチ探索

- メリット: 探索の自由度が最大になり、論文が示す性能改善幅をそのまま再現できる可能性がある。
- デメリット: 安全性・レビュー性の面でこの repo の宣言的ハーネス面（facet/config）との乖離が
  大きい。任意コード実行の sandbox・権限設計、レビュー困難な diff、コスト過大（1 イテレーション
  約 10M トークン）などのリスクが大きく、既存の変更ガードレール（後方互換・小さく安全な
  ステップ）と相容れない。

## 決定

選択肢 B を採用する。

- ハーネス候補は任意コードではなく **宣言的オーバーレイ**（facets/instructions, facets/policies,
  facets/compositions, rules の facet ソース、config の allowlist されたキー）に限定する。
- 永続ストア `.claude/meta-harness/` は gitignore 対象とし、`SessionEnd` によるクリーンアップの
  対象外とする。
- 永続ストアと評価用 worktree の配置は、実行元 worktree に関わらず `git rev-parse --git-common-dir`
  から導出した**メイン（root）worktree のルート**に解決する。feature worktree の削除によって
  蓄積データが失われることを防ぐ（worktree ベースの開発運用との整合）。
- 改善の反映（promotion）には人間承認ゲートを必須とし、無人での facet/config への直接反映は
  行わない。
- 導入は Phase 1（計測基盤: register/evaluate/ledger/frontier）→ Phase 2（提案・昇格: propose/
  promote、人間起動）→ Phase 3（自動探索ループ + 対象拡大）の段階導入とする。
- skill-evolution オフライン層（Issue #139）は独自実装せず、`meta-harness target=skill` への
  委譲として実現する。ADR-20260701-027 の D1（二層構成）・D2（二軸 judge）・D3（改善反映先の
  出自による塩梅、facet 自動昇格は当面しない）は本決定後も保存する。

基本設計は `design:meta-harness`（`docs/design/meta-harness.md`）、実装レベルの詳細設計は
`design:meta-harness-detailed`（`docs/design/meta-harness-detailed.md`）、要件は `req:meta-harness`
（`docs/requirements/meta-harness.md`）を参照。

## 影響

- 新規パッケージ `packages/meta-harness/` を追加する（`orchex meta` サブコマンド群: init /
  register / evaluate / frontier / propose / loop / promote / status / purge）。
- Issue #139（skill-evolution オフライン層）は、独自実装ではなく meta-harness への委譲として
  再スコープする。
- `docs/evaluation/<pkg>.md` に対応する `docs/evaluation/<pkg>.checks.yaml` sidecar を段階的に
  追加し、must 観点の oracle 化を進める。
- `.gitignore` に `.claude/meta-harness/` を追記する。
- 既存の後方互換（CLI コマンド・config キー）には影響しない。新規追加のみで既存挙動は変更しない。
