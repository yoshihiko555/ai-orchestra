# 評価セット（Evaluation Sets）

**各パッケージの「あるべき状態」を自然言語で定義した評価基準集。**

テストコード（特に AI 生成テスト）をレビューする際の判断基準として使う。
テストの妥当性をテスト自体に依存させず、先に「正しい状態とは何か」を仕様として明文化する。

## 目的

- パッケージの責務・期待する入出力・副作用を自然言語で定義する
- 重要な正常系・異常系・境界条件を評価観点として列挙する
- AI が生成したテストが「実装の都合」ではなく「あるべき仕様」に沿っているかを判定可能にする

## 使い方

1. **テストを追加・改修するとき**: 対象パッケージの評価セットを読み、変更後のテストが評価観点とギャップなく対応していることを確認してから完了する（運用ルール: `.claude/rules/evaluation-set-policy.md`）
2. **AI 生成テストをレビューするとき**: 下記「テストレビュー判断基準（共通）」と各評価セットの観点 ID を突合する
3. **突合するとき**: `EV ID | 対応テスト | 優先度 | covered/gap` のマトリクスをレビュー時の一時成果物として生成し、gap 行のみをパッケージ単位の GitHub Issue（チェックリスト形式）に転記する。マトリクス自体は評価セットに恒久記録しない（陳腐化するため）
4. **仕様が変わったとき**: 評価セットを先に更新し、テストを追従させる。評価セットと実装が矛盾する場合は評価セットを正とし、評価セット自体が誤っていると思われる場合は人間に確認する

## ファイル構成

| ファイル              | 内容                                                     |
| --------------------- | -------------------------------------------------------- |
| `README.md`           | 本書。共通フォーマット・類型別観点・共通レビュー判断基準 |
| `_template.md`        | 各パッケージ評価セットの雛形                             |
| `<package>.md`        | パッケージごとの評価セット（packages/ 配下と 1:1 対応）  |
| `skills/_template.md` | スキルフロー評価セットの雛形                             |
| `skills/<flow>.md`    | スキルフロー単位の評価セット（下記「二層構造」参照）     |

## 二層構造（パッケージ / スキルフロー）

評価セットは強制力の異なる 2 層に分けて管理する。

| 層                         | 配置                      | 単位                                             | 強制力                                                                                           |
| -------------------------- | ------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **パッケージ評価セット**   | `docs/evaluation/` 直下   | パッケージ（`packages/` と 1:1）                 | **pytest で強制**。テスト改修時の突合が MUST（`evaluation-set-policy`）                          |
| **スキルフロー評価セット** | `docs/evaluation/skills/` | フロー（複数スキルが成果物を介して連続する単位） | **振る舞い仕様書**。pytest 突合の対象外。検証は PR レビュー時の突合・`/config-analyze`・実行観察 |

- スキル（facets 由来の Markdown 指示書）は pytest で強制できないため、パッケージと同じ棚に混ぜない
- スキルフロー評価セットは「スキル単体」ではなく「フロー単位」で作る（スキル単位に細分化するとパッケージ粒度の SSOT と混同しやすいため）
- スキルフローの仕様を変更する PR では、該当する `skills/<flow>.md` と矛盾しないかを突合し、仕様変更の場合は評価セットを先に更新する

## 共通フォーマット

各評価セットは `_template.md` に従い、以下のセクションで構成する。

| セクション                | 内容                                                               |
| ------------------------- | ------------------------------------------------------------------ |
| 1. 責務定義               | パッケージが「正しい状態」であることの定義（2〜5 文）と Non-Goals  |
| 2. 期待する入出力・副作用 | 構成要素（hook / コマンド / スキル等）ごとの入力・期待出力・副作用 |
| 3. 評価観点               | 正常系 / 異常系 / 境界条件のチェックリスト（観点 ID 付き）         |
| 4. 類型別観点             | 本書の類型別チェックリストのうち該当するものの具体化               |
| 5. テストレビュー判断基準 | パッケージ固有の判断基準（共通基準への追加分のみ）                 |

### 観点 ID 規約

- 形式: `EV-NN`（ファイル内で一意の連番。例: `EV-01`）。パッケージをまたぐ参照は `<package> EV-NN` と表記する
- 各観点に分類を併記する: `正常` / `異常` / `境界`
- 優先度を併記する: `must`（テストで必ず担保）/ `should`（担保が望ましい）
- 各観点に仕様根拠（参照ドキュメント・ルール・ADR 等）を付記する。根拠が実装コードしかない観点は「根拠: 実装挙動」と明示し、実装追認でないか人間レビューで重点確認する
- 1 観点 = 1 振る舞い。複数の振る舞いを 1 つの ID に詰め込まない
- 削除した ID は欠番として残し、再利用しない（テスト・Issue からの参照を壊さないため）
- テストとの突合・ギャップ Issue のチェックリストはこの ID で参照する

## パッケージ類型

パッケージは主たる構成物により 3 類型に分類する（複合パッケージは主類型 + 副類型を併記）。

| 類型         | 主な構成物                                     | 該当パッケージ例                                                                                           |
| ------------ | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| hook 型      | SessionStart / PreToolUse 等の hook スクリプト | core, quality-gates, audit, cocoindex, codex-suggestions, antigravity-suggestions, tmux-monitor, fail-logs |
| CLI ツール型 | lib + scripts で提供されるコマンド             | codd, skill-evolution, audit（scripts）                                                                    |
| スキル型     | スキル指示書 + エージェント定義                | image-generation, reverse, git-workflow                                                                    |

## 類型別観点チェックリスト

各評価セットの「4. 類型別観点」は、該当類型の以下の項目をパッケージの実情に合わせて具体化する。
該当しない項目は「N/A: 理由」として明示する（黙って省略しない）。

### hook 型

- stdin/stdout 契約: hook 入力 JSON の想定スキーマと、出力（additionalContext / block 等）の形式が定義通りか
- exit code 規約: 正常 / 警告 / ブロックの exit code が Claude Code の hook 仕様に沿っているか
- fail-safe 方針: hook 内部エラー時にセッションを壊さない（fail-open / fail-closed の選択が明示されているか）
- 冪等性: 同一入力での再実行が二重書き込み・二重注入を起こさないか
- config 駆動: enabled フラグ・`*.local.yaml` / `*.local.json` 上書きを尊重して無効化できるか
- 秘匿情報: ログ・注入コンテキストに秘密情報を出力しないか（マスキング）
- 性能: 同期 hook がセッション開始・ツール実行を著しく遅延させないか

### CLI ツール型

- コマンド契約: 引数・オプション・exit code が定義通りで、後方互換性が保たれているか
- 入力バリデーション: 不正な引数・存在しないパス・壊れた入力ファイルで適切なエラーメッセージを返すか
- 破壊的操作の安全策: 上書き・削除を伴う操作に確認・dry-run・バックアップ等の防護があるか
- 出力の安定性: 機械可読出力（JSON / JSONL 等）のスキーマが安定しているか
- 設定レイヤリング: ベース設定と `*.local.*` 上書きの解決順序が `config-loading` ルール通りか

### スキル型

- 対話規約: 対話フェーズが AskUserQuestion を使い、Dialog Rules Policy に沿っているか
- 非対話完結性: 外部 CLI 呼び出しが stdin 封じ・タイムアウト・exit code 判定を守り、ハングしないか
- フォールバック: 外部 CLI（Codex / Antigravity）不能時に claude-direct へフォールバックするか
- ルーティング尊重: `cli-tools.yaml`（+ `.local.yaml`）の enabled / tool 設定に従うか
- 成果物規約: 生成物の置き場所・命名がスキル定義通りか

### 共通（全類型）

- 後方互換性: 既存の設定キー・コマンド・出力形式を壊していないか
- 生成物の同期: テンプレート・facet 由来の生成物は正本を編集し、build / sync で再生成されているか
- ドキュメント整合: README / packages.md 等の記述と実際の振る舞いが一致しているか
- 配布ライフサイクル: install / update / uninstall（sync による配布・削除）を通じて壊れた中間状態を残さないか。部分失敗時に導入先プロジェクトの既存設定（`*.local.*` 等）を破壊しないか

## テストレビュー判断基準（共通）

AI 生成テストのレビューでは、全パッケージ共通で以下を確認する。

1. **観点対応**: 各テストがどの観点 ID（`EV-NN`）を担保するか説明できるか。どの観点にも対応しないテストは目的を確認する
2. **must 網羅**: `must` の観点がいずれかのテストでカバーされているか。未カバーはギャップとして Issue 化する
3. **実装追認の排除**: 期待値が「現状の出力をコピーしただけ」になっていないか。仕様（評価セット）から期待値を導出しているか
4. **異常系の独立性**: 異常系・境界条件が正常系のついでではなく、独立したテストケースとして検証されているか
5. **失敗の意味**: テストの失敗が仕様違反を意味するか。環境依存・実行順依存で不安定に失敗しないか
6. **過剰なモック**: モックが検証対象の振る舞いまで置き換えて、テストが空洞化していないか
